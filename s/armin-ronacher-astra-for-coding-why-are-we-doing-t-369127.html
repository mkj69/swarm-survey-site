一句话

这次无人值守软件工厂实验提示：agent 能持续工作、分派任务并大量提交代码，并不意味着交付价值随运行规模增长。

主要内容

  • 作者让 Astra 自主安排工作流、维护笔记并调用子 agent，目标是为 Python 引入虚拟线程与词法作用域；运行约 35 小时后由作者终止。
  • 系统净增约 7.5 万行代码、产生 79 次提交，agent 间交换约 1400 条消息，但作者认为没有得到有价值的成果。
  • 作者关注的不只是正确性，而是可理解性：工具调用大量使用紧凑的 Python 字符串替换及多层程序调用；类似风格又进入测试和正式代码，伴随硬编码操作编号、以列表下标保存状态等设计。
  • 任务笔记的编号逐渐复杂，系统持续衍生工作。作者据此质疑：长时间坚持执行是否反而放大了失控成本。
  • 作者仍认可模型的能力，但认为更高费用和更多人工审查削弱了其在软件工程中的投资回报。

证据与可信度

  • 这是作者自述的单次实验，附有工具调用、测试及实现片段。它们支持具体代码风格问题的存在，但不能证明问题在全部产出中的比例；材料未提供独立核验或受控对照。
  • 35 小时、净增 7.5 万行、79 次提交、约 1400 条消息及约 1200 美元原始 API 成本，均来自作者报告。按列出的近似数计算，每次提交约 15.2 美元，与文中约 15.5 美元略有差异。
  • token 口径不一致：前文估计一次额度重置约 40 亿 token，后文称本次运行消耗约 10 亿，材料没有解释两者关系。
  • 两段测试压缩写法比格式化后节省约 10% token，是作者报告的局部比较；不能据此推出整体效率提升。
  • “毫无价值”属于作者评价；关于训练奖励偏向 token 效率、任务完成而忽略可读性的解释属于推测，没有训练证据。

对 swarm scaling 的意义

这份材料提供的是扩展失败的案例，而非规模收益曲线：没有 agent 数量、并行度变化或单 agent 基线，无法判断增加 agent 的边际效果。

它揭示了值得验证的风险：执行时长、通信量和代码产量可以同时增长，维护性与交付价值却未必改善。评估 swarm 应把可验收成果、审查负担和总成本纳入指标，并检查任务是否持续膨胀。该实验支持设置预算与人工检查节点的必要性，但不足以断言所有多 agent 软件工厂都无效。
