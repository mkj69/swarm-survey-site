一句话

这场讨论把 agent 编程的规模问题，从“能生成多少代码”转向“能否用验证、上下文管理和集成机制，把大量生成转化为可靠交付”。

主要内容

  • 讨论围绕 OpenAI 的工程案例展开：原文引述称，团队约五个月形成百万行仓库，合并约 1500 个 PR，工程师从三人增至七人。争议集中在代码量、PR 数与产品价值之间缺少直接对应关系。
  • 自称原文作者的 zbrock 补充：项目主要是 Electron 应用及少量托管后端，属于类似当前 Codex 应用的内部原型，并影响了后续产品。工程师的主要工作是调整技能、文档和提示，对不达标的运行结果直接弃用；他估计超过一半未达标准。
  • 并发集成并未消失，而是引入更多自动化处理：作者提到，部分团队尝试由 agent 协调的集中集成队列，也使用普通合并队列及监控 CI、处理冲突的 Codex 会话。
  • 实践者强调可执行验证、架构约束、独立工作环境与仓库内工作记录。另一些人提醒，小文件和按需读取可能减少无关上下文，但日志中的旧错误、过期文档也可能误导后续会话。
  • 成本与 CI 负载被明确提为自主运行的限制。评论同时质疑：维护 harness 是否真正改善交付，还是形成了另一层需要持续调试的系统。

证据与可信度

  • 百万行、约 1500 个 PR、每人每天 3.5 个 PR，均来自讨论引用的厂商案例，并非论坛独立测量。材料缺少完整工时、人数变化及统计口径，无法重算人均吞吐，也无法据此推导效率倍数。
  • 评论用百万行除以 1500 个 PR，得到每个 PR 约 650 行的粗略估算；这混合了仓库存量与变更次数，不能作为实际 PR 大小或质量指标。与 Firefox 的比较也存在范围不一致问题。
  • 作者身份在本材料中未经独立核验，其回复属于当事人自述；其他工作流、成本瓶颈和小文件收益主要是个人经验。虽有公开仓库链接，材料未提供审计结果。
  • 当前依据是讨论镜像文本，未读到被讨论文章全文；没有受控实验、完整成本数据或长期质量追踪。

对 swarm scaling 的意义

它提供了扩展工程的候选机制，而非 agent 数量增加就能提高净产出的证明：隔离环境降低资源冲突，集成队列处理并发提交，自动验证承担部分检查，上下文整理支持跨会话延续。

值得继续验证的是：扣除失败运行、返工、审查、集成和维护成本后，增加 agent 能否提升合格交付。材料显示这些成本确实存在，但没有给出 agent 数量与净收益的关系，不能据此宣称 swarm 已实现线性或超线性扩展。
