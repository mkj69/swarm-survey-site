一句话

Osmani认为，多 agent 并行提高了产出速度，也可能让人的理解与审核能力成为瓶颈；扩容必须同时建设验证机制，并保留人的判断与责任。

主要内容

  • 委托工作不等于放弃判断。 作者区分任务外包、默认接受输出、彻底放弃核查三个层次。风险在于这种滑落往往逐步发生：结果越流畅、明显错误越少，人越容易停止追问。
  • 理解债务可能被表面质量掩盖。 代码整洁、测试通过，并不代表团队理解系统。作者接受按需重建局部理解，但强调必须知道自己缺少哪些理解。
  • 验证也需要被审查。 功能和测试可能共享同一个错误假设，因此绿灯只能证明检查覆盖的性质。应提前明确完成标准，先看实际执行及其结果，再看 agent 的总结。
  • 审核应覆盖隐含决策。 除了代码差异，还要追问 agent 选择了哪些默认值、删去了哪些范围、如何处理需求冲突。新增会话无法自动消化已经堆积的待审产出。
  • 输入质量与信息来源同样关键。 人应明确目标、约束和完成条件；多个 agent 连续传递摘要，可能使后续参与者脱离原始材料。作者也建议用反方论证、独立上下文复核及人工练习维持判断能力。

对 swarm scaling 的意义

文章提出了一个值得检验的扩容约束：agent 产出可以并行增长，人的注意力与可承担责任的审核量却未必同步增长。因此，评估 swarm 不应只看任务完成速度，还应考察验证覆盖、待审积压，以及人能否解释关键决策。

它也提示两类协作风险：共享错误假设可能让自动检查失效，摘要接力可能丢失原始依据。独立复核、保留可追溯证据、抽查原始材料，以及按后果分配人工审核，都是作者论述支持的设计方向；本文没有证明这些措施的实际扩容收益。
