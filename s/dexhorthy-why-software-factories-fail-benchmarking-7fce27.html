一句话

这项小样本实验提示：模型能完成初始功能，不代表能在需求持续变化时保持正确；但它尚不能证明多智能体软件工厂必然失败。

主要内容

  • SlopCodeBench 逐步揭示需求，让模型修改已有代码，并用隐藏黑盒测试检查新增功能与历史功能，考察持续演进能力。
  • 作者选取简单、中等、困难各一道题，共 17 个检查点；三个模型使用相同提示与 Claude Code，每个检查点开启新上下文，代码沿用。
  • Opus 5 严格通过 4/17，约 24%；Opus 4.8、Sonnet 5 各通过 1/17，约 6%。全部九次题目运行均未在终点实现全测试通过。
  • 各模型随需求推进出现复杂度或冗长程度上升。Opus 5 的函数数量约为 Opus 4.8 的五倍，但生产代码量约为其 1.8 倍，部分增长来自测试。
  • 作者提出用“强模型搭建、弱模型接手”的方式评估可维护性，并建议加入时间、费用和 token 成本；这些仍是待验证方案。

证据与可信度

  • 结果属于作者自报实验，所给材料未提供独立复现。24% 与 6% 来自检查点通过数除以 17；正文另有一次“23%”，与最终计数不一致。
  • 严格通过要求当前及历史测试全部通过，因此早期缺陷会持续压低后续得分；17 个检查点不能视为相互独立的样本。
  • 原论文的 Opus 4.6 为 17%、GPT-5.4 为 11%，这里只是转引；作者的小子集不能与原论文成绩直接比较。
  • 代码质量指标由确定性工具计算，但其与真实维护难度的关系尚未确立。跨语言“超过十一倍”的规则触发比较，存在规则数量与等价性未核验等限制。
  • 实验未测试审查循环、质量反馈等护栏，作者也有 HumanLayer 产品推广背景。结论应限于本次配置与样本。

对 swarm scaling 的意义

  • 材料测的是模型持续维护代码的能力，并非协作 swarm 的规模收益；按模型并行运行只是评测调度。
  • 对 swarm 的启示是：增加并发之外，还需验证修改能否保留历史正确性，以及代码能否被后续执行者顺利接手。
  • “强模型写、弱模型改”可作为分工与交接质量的候选评测，但尚无实验结果。
  • 作者估计九个会话并行可将运行时间从六小时缩至一至两小时。这说明评测可以加速，不能据此推断软件质量随 agent 数量提升。
