一句话

这篇文章把多智能体选型归结为上下文隔离、并行执行和状态管理的权衡，而非单纯增加 agent 数量；其性能示例有参考价值，但部分百分比与表格不符。

主要内容

  • 先确认是否需要多智能体：作者建议从单 agent 和工具开始，只有专业知识难以装进统一上下文，或多个团队需要独立维护能力时，再增加架构复杂度。
  • Subagents：集中调度。主 agent 调用专业子 agent 并汇总结果，支持并行和上下文隔离；代价是结果返回主 agent 带来的额外调用。
  • Skills：按需加载知识。本质上仍是单 agent，通过逐步加载专业指令控制初始上下文，也便于分工维护；但已加载内容会留在对话中，增加后续 token 消耗。
  • Handoffs：按状态交接。适合分阶段收集信息、满足前置条件后开放能力的对话流程，主要负担是跨轮状态管理。
  • Router：分流后汇总。适合跨知识域并行查询，通常逐请求独立处理；连续对话可能需要额外的有状态外层。
  • 模式优劣随工作负载变化：简单任务和重复请求偏向 Skills、Handoffs，多领域大上下文任务偏向 Subagents、Router。

证据与可信度

给定抓取内容包含正文、架构说明和性能表，可据此分析。文章来自 LangChain 官方博客，兼有产品推广；性能数字属于厂商提供的场景分析，抓取内容未交代完整实验配置、重复次数及误差，也未提供独立核验。

  • 单次“买咖啡”示例中，Subagents 为 4 次模型调用，其余模式为 3 次。这反映特定流程的调用开销，不能直接等同于实测延迟或费用。
  • 重复请求中，Skills、Handoffs 总调用数由 Subagents 的 8 次降至 5 次，按总量计算减少 37.5%；若只比较第二轮，则由 4 次降至 2 次，减少 50%。正文的百分比表述混用了比较口径。
  • 多领域示例中，Subagents 约 9K token，Skills 约 15K，按表计算前者减少约 40%，并非正文所称的 67%；反过来，15K 比 9K 多约 67%。
  • 文中引用 Anthropic 内部研究评估的 90.2% 提升，但未展开指标与评估方法，不能视为通用多智能体收益。

对 swarm scaling 的意义

文章提供的是架构选择框架，而非“agent 越多越强”的规模定律。扩展收益来自可拆分任务的并行处理，以及隔离无关上下文；扩展成本则包括调度、汇总、重复路由和状态维护。

对 swarm 实验，更有用的启示是区分工作负载，并同时记录质量、调用数、token 和延迟。本文没有比较不同 agent 数量下的表现，无法据此判断最优规模或扩展收益何时饱和。
