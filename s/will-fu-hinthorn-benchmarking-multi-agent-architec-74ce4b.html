一句话

这项实验显示，按领域拆分 agent 能缓解无关工具与指令带来的干扰，但不能据此证明增加 agent 数量会提升复杂协作能力。

主要内容

  • 作者在 τ-bench 零售测试集前 100 个案例上，逐步加入 6 个无关领域；每个领域配置 19 个工具及领域说明。这些新增领域均不参与任务求解，只用于制造干扰。
  • 全部实验使用 GPT-4o，对比单体、Swarm 和 Supervisor。单体接收全部工具与说明；Swarm 通过 agent 间交接控制权，任一时刻仅一个 agent 活跃；Supervisor 负责派单并统一回复用户。
  • 单体在仅有一个干扰领域时略占优势，干扰领域达到两个及以上后表现明显下降。Swarm 整体略优于 Supervisor。
  • 随干扰增加，单体的 token 消耗持续上升，两种多 agent 结构则大致持平；Supervisor 比 Swarm 消耗更多。
  • 作者将 Supervisor 的主要损失归因于中间转述，并通过清除交接消息、直接转发子 agent 回复、调整交接工具命名改善表现。

证据与可信度

  • 这是 LangChain 团队对自家框架实现的基准测量，提供了修改后的数据与实验代码入口；所给材料没有独立复现或核验结果。
  • 100 个案例、6 个干扰领域、每领域 19 个工具均来自实验设置，不能理解为真实业务规模。
  • 文中宣称 Supervisor 优化后性能提升接近 50%，但正文未给出对应绝对分数、计算口径或各项改动的单独贡献，无法据此计算百分点增益。
  • 抓取内容缺少图表具体数值，评分说明还保留“XYZ”占位符；未见重复次数、误差范围或显著性检验。因此，趋势比提升幅度更有参考价值，对错误机制的解释也仍需进一步验证。

对 swarm scaling 的意义

  • 材料支持的是“领域与工具增加时，通过上下文隔离维持表现”，而非依靠更多 agent 获得并行加速：这里的 Swarm 是串行交接。
  • 所有任务只需一个领域 agent，几乎不要求跨 agent 协作。作者也将其称为最佳情形测试；结果不能外推到多跳依赖、共享状态或复杂协同任务。
  • 可借鉴的设计重点是减少无关上下文和信息转述。架构名称本身不足以解释表现，交接消息、回复路径等实现细节可能显著影响结果。
  • Swarm 要求成员彼此知晓，Supervisor 对子 agent 的假设更少；接入异构或第三方 agent 时，还需权衡可接入性与协调开销。
