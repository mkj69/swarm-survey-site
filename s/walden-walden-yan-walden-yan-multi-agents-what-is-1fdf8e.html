一句话

作者修正了此前对多智能体的否定立场：当前更实用的路线是集中写入、分散思考，以明确分工和上下文管理扩展能力。

主要内容

  • 并行写入仍有协调难题。 多个 agent 会在代码风格、边界处理和实现模式上作出隐含选择，局部成果未必能组成一致产品。作者认为，模型能力提升并未消除这一问题。
  • 编码与审查循环已有实际应用。 编码 agent 负责修改，审查 agent 从干净上下文检查差异，再由编码方结合用户要求筛选反馈。这里刻意减少上下文共享，以获得独立视角；关键是避免误报引发反复修改或范围扩张。
  • 强模型顾问的效果受主模型制约。 较弱主模型需要识别自身局限、提出有效问题并传递上下文。作者承认 SWE-1.5 未能胜任这一角色；SWE-1.6 有改善，但仍未达到预期。Claude 与 GPT 搭配则被报告在困难场景中有效，更像按能力路由。
  • 更大任务采用管理层级。 manager 拆分任务、子 agent 执行、manager 汇总。实际难点包括过度指挥、误以为共享状态，以及子 agent 不主动传播影响其他任务的发现。

证据与可信度

  • 作者称，Devin 最大企业客户分组的使用量在过去六个月增长约 8 倍；未说明使用量定义、基数或统计方法，属于厂商自报，也不能据此推导多智能体的增益。
  • Devin Review 被报告平均每个 PR 发现 2 个 bug，其中约 58% 属严重问题。材料未给出样本量、判定流程、误报率或对照实验，不能直接视为已验证的质量提升幅度。
  • Smart Friend 的收益及管理型 agent 的表现主要来自作者参与产品开发的经验。披露失败和限制有助于理解适用边界，但缺少可复现评测与独立核验。
  • 浏览器、编译器等大规模演示仅作为例子出现。作者强调其验收标准较明确，不能自动代表真实软件中的需求判断与协作难度。

对 swarm scaling 的意义

本文将扩展重点从 agent 数量转向决策一致性：增加审查、咨询和任务分解能力，同时控制写入与结果整合的责任边界。

上下文策略也应随角色变化：审查需要独立视角，顾问需要足够背景，管理者需要可靠的状态与发现回传。因此，“共享越多越好”不是通用规则。

这是一份有实践细节的反面立场材料，支持优先探索结构化协作；但它没有证明无结构 swarm 必然无效，也未量化规模扩大后的成本、延迟和收益曲线。
