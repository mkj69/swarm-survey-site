一句话

Zvi 的评测汇编提示：多智能体可以缩短完成时间，却未必提高同等成本下的质量；Opus 5 更适合做边界明确的执行者，其统筹能力仍有争议。

主要内容

  • 扩展收益取决于任务。 作者转述官方评测：BrowseComp 中，多智能体能更快取得较好结果，低推理强度的子智能体似乎有益；ProgramBench 中，多智能体虽然提速，但多数价位的结果反而更差。
  • 执行能力与统筹能力需要分开看。 作者认为 Opus 5 擅长局部推理和明确任务，但复杂长任务可能需要其他模型或人持续纠偏。文中多位用户采用 Fable 统筹、Opus 执行的组合，也有人报告它遗漏项目规范、偏离指令。
  • 增加推理预算可能适得其反。 文中报告，高推理强度有时带来绕圈、过度设计和额外改动。FrontierCode 的部分分数下降被解释为模型做了未要求的工作并受到扣分，修正后曲线恢复正常，说明评测规则也会影响扩展结论。
  • 单价不等于任务成本。 文中转述 Vals 的 Vibe Code Bench：Opus 每任务花费 33.88 美元，Fable 为 41.71 美元。尽管宣传强调 token 单价优势，更多 token 消耗会压缩实际节省。

对 swarm scaling 的意义

这份材料支持的是有条件的扩展：更快完成、质量更高、成本更低需要分别验证，不能用并行速度代替整体收益。

它也提供了异构分工的实践线索：让较强的统筹模型管理擅长局部任务的执行模型。但现有证据不足以证明这种组合普遍优于单智能体。后续应在相同成本下比较质量，同时记录耗时、返工和指令遵循情况；尤其应把 ProgramBench 的负收益现象作为反例检查。
