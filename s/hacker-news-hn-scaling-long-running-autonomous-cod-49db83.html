一句话

这场讨论把 Cursor 长时自主编码实验的核心问题，从“能生成多少代码”转向“产物能否构建、验证并持续维护”。

主要内容

  • 讨论围绕自主构建浏览器展开。支持者认为，智能体能长期迭代、整合组件，本身已显示能力进步；质疑者则要求可复现的运行结果。
  • 多名评论者称，本地构建失败，仓库持续集成长期报错，无法确定哪个提交对应展示中的可运行版本。也有人先假定能够编译，随后承认没有验证。
  • “从零构建”的含义受到挑战：评论者查看依赖后指出，项目使用了现有 JavaScript 引擎、图形、窗口及解析库。争议并非组件复用是否合理，而是宣传是否准确描述了实际工作。
  • 维护性与交付成为另一焦点：目录难以理解、文档不足、大规模改动难以审查，以及后续修改是否会持续引入退化。
  • 少数参与者分享规划者分派任务、用 git 子树并行工作的经验；另有人强调人工引导、独立检查和测试约束。

对 swarm scaling 的意义

材料提示，扩展智能体数量与运行时间，不等于可用软件产出同比增长。更有价值的评估对象是：固定版本能否复现构建、测试是否通过、功能是否达标、后续改动是否仍可审查和维护。

讨论还提出一种值得检验的风险：并行生成越快，集成与纠错负担也可能越大。因此，规划与分工之外，验证门槛、共享架构理解和收敛机制同样关键。但这只是社区提出的问题与经验，材料没有受控对照，不能据此得出 swarm scaling 的收益曲线或规模上限。
