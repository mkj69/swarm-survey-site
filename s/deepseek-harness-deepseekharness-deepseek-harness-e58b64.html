一句话

这篇架构文把多任务 agent 的扩展瓶颈指向人类注意力，主张以统一 Router、隔离 Worker 和事件驱动机制，接管用户手工管理会话的负担。

主要内容

  • 问题定位：作者认为，单任务主要受模型能力限制，多任务则受人类跟踪会话的能力限制；“通常只能关注 3—5 个活跃会话”来自其经验。
  • 两层分工：Router 负责跨渠道交互、全局记忆与任务分派，不亲自执行任务；Worker 拥有独立上下文和执行工具，也可在内部组织子 agent。这里主要扩展的是多个任务的并发，而非把一个任务拆给更多角色。
  • 减少协调开销：先用确定性规则过滤事件，再交给模型判断；同一讨论线程的后续事件通过订阅直接送达 Worker，减少 Router 转发。Router 对积压事件批量处理。
  • 维持长期运行：上下文采用摘要、引用和按需检索；耗时工具异步运行；计算、持久状态与执行环境分离；外部 Watchdog 检查故障和任务是否偏离目标。
  • 尚未解决：强耦合任务何时需要 Router 分片、Worker 直接通信、长期记忆、跨权限边界协作，仍是开放问题。文章明确定位为架构探索，并非现有功能说明。

证据与可信度

实验属于作者团队自报，无独立核验。端到端实验每种设计运行 5 次，每次约 300 条消息、约 20 个工作请求；编码由耗时工具模拟，因此测量的是调度与协调，不是真实代码质量。

Super-agent 的任务完成时间 p50 为 12.4 分钟、p95 为 15.7 分钟；中性提示的单会话方案 p95 为 29.5 分钟，但比较结果明显受委派提示影响。取消直通后，完成时间接近，Router 决策数约增 30%，缓存读取 token 从 23.2M 增至 31.8M，约增 37%。

独立 Router 压测中，需决策事件从约每分钟 1 个增至 40 个，平均批量从 1.0 增至 2.8，摊销推理时间从每决策 6.4 秒降至 1.6 秒。这不等于端到端响应延迟。作者也承认负载合成、环境简化，结果仅具指示性。元数据中的传播量不能证明技术结论。

对 swarm scaling 的意义

它提供的关键视角是：扩展收益不只来自增加 agent 数量，还来自减少人的上下文切换，以及降低事件过滤、转发和汇报成本。将“必须委派”落实为架构职责，比依赖模型每次自行判断更可控。

但现有证据主要支持松耦合多任务的调度效率，尚不能证明复杂协作 swarm 的规模收益。全局记忆、强耦合协调与权限边界，仍可能成为下一阶段瓶颈。
