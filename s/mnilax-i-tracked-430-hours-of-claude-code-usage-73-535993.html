一句话

这篇个人使用审计认为，Claude Code 的效率损失主要来自重复上下文与配置开销；它提供了值得测量的方向，但“73% 浪费”不能直接推广到其他用户或多智能体系统。

主要内容

  • 作者称连续记录了 90 天、430 小时的使用，涉及 600 万输入 token、1,340 美元 API 支出，通过 HTTP 代理采集请求、响应、缓存、延迟及模型信息。
  • 九类开销包括：项目规则膨胀、历史消息重复输入、hook 注入、缓存失效、无关 skill 加载、工具定义、简单任务的额外推理、错误方向生成，以及插件启动消息。
  • 前四类分别占总 token 的约 14%、13%、11%、10%，共同指向反复携带上下文的成本。
  • 作者主张精简常驻规则，按需加载技能与工具，压缩长对话，并及时中断偏离目标的输出；同时承认彻底清空上下文或禁用技能可能增加返工。
  • 优化后，“有效 token”占比据称从 27% 升至约 65%。核心建议是先记录实际请求，再判断哪些配置值得保留。

证据与可信度

  • 属于单人自报的使用记录与经验总结。代理日志原则上可以支持用量统计，但提供的内容没有原始日志、完整审计脚本、任务样本或独立核验。
  • 九项比例相加确为 73%，但分类存在潜在重叠：规则、hook、工具定义也可能进入缓存或历史上下文。文中未说明如何去重，“直接帮助任务”的判断也带有主观性。
  • 600 万明确是输入 token，而各项占比又涉及输出和推理 token，统计分母不清楚。token 数、账单成本、订阅额度也被混合讨论。
  • 文中将缓存命中标成免费，后面却写读取价格为基础价格的 0.1 倍；技能数量也出现 9 个与 11 个两种说法。这些不一致削弱了精确数字的可信度。
  • 关于缓存故障、官方表态及普遍用户行为的说法，仅有作者转述；“同一套餐获得 2—3 倍容量”也未展示可复核验证。

对 swarm scaling 的意义

  • 可作为成本拆解清单：若多个 agent 都重复携带规则、工具定义和历史记录，增加 agent 数量时，这些开销可能随之放大。
  • 可借鉴的工程方向是按角色分配上下文、按需开放工具，并分别记录输入、输出、缓存费用和任务完成情况。
  • 材料没有多 agent 对照实验，也没有测量协调、通信、并发或成功率，不能据此推导 swarm 的扩展规律。
  • 对 swarm 更关键的验证是：精简上下文后，每个成功任务的总成本是否下降，质量和返工是否恶化；“有效 token 占比”本身不足以证明系统效率提升。
