一句话

Claude Code 的团队机制展示了小规模多智能体协作的工程实现，但其规模建议属于官方实践指导，不能作为 swarm 随规模增长而提升性能的实验证据。

主要内容

  • 团队由固定主会话统筹，成员各有独立上下文，可直接互发消息；具备任务工具时，通过共享任务列表认领工作、处理依赖，并用文件锁避免重复认领。
  • 适合独立研究、多视角审查、竞争性假设排查，以及边界清楚的模块开发。顺序任务、频繁修改同一文件或依赖密集的工作，官方更建议单会话或子代理。
  • 官方建议多数工作流从 3—5 名成员起步；即使有 15 个独立任务，也可先用 3 名成员。每名成员分配 5—6 个任务，便于持续工作和重新调度。
  • 功能仍属实验性，默认关闭。成员不继承主会话的对话历史，需要额外提供任务背景。
  • 架构限制包括：每个会话仅有一个团队、成员不能再创建团队、负责人不能转移。进程内成员无法随会话恢复，任务状态可能滞后，成员与负责人也可能提前停止。

证据与可信度

材料来自 Anthropic 官方文档，适合了解其声明的机制与限制；本文仅依据所给抓取内容，未做独立核验，元数据未提供发布日期。

上述人数与任务数均直接来自文档的最佳实践建议，没有附带样本、实验设计、耗时或成功率数据。“三名专注成员常优于五名分散成员”也是厂商经验性判断。文档称 token 成本随成员数线性增长，但未展示测量方法或数据，也未量化协调开销与收益递减的拐点。因此，不能据此推导加速比、最优规模或性价比曲线。

对 swarm scaling 的意义

这份材料更能说明“扩群需要哪些协调设施”：任务依赖、互发消息、状态同步、质量门禁和人工干预共同支撑并行工作。文件锁能避免重复领任务，却不能解决同一文件的编辑冲突，任务划分仍是关键。

其规模化思路是让少量成员处理更多边界清楚的任务，仅在确有同时推进需求时增加成员。固定负责人和禁止嵌套团队，也限定了它对层级式 swarm 的参考范围。评估此类系统时，需要同时考察完成质量、总 token、耗时与协调失败；本材料提供了观察维度，尚未提供规模收益的验证结果。
