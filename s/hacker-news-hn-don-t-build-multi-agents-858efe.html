一句话

这场讨论的核心并非该不该使用多个 agent，而是如何在上下文隔离、信息共享与并行协作之间取得平衡。

主要内容

  • 子 agent 可充当信息过滤器。 一位开发者称，短信食谱助手直接搜索网页后容易偏离短信格式要求；让子 agent 搜索并只返回候选食谱后，主 agent 更能遵守格式。这提示上下文质量问题可能早于窗口耗尽出现。
  • 共享上下文存在取舍。 完整轨迹有助于保留任务背景，但也可能把先前错误和判断框架传给评审者。有评论主张让评审子 agent 使用独立上下文，以获得较少受既有结论影响的反馈。
  • 系统结构比名称更重要。 有人倾向固定流水线或“主 agent 加工具”，认为模型调用也可以封装成具有明确输入输出的工具；另有人主张共享知识库、按任务组织上下文，并由编排服务调度执行。
  • 并行难点是任务边界会变化。 评论者报告过按不同组件并行修改代码的成功经验，但仍需人工纠偏。另有评论指出，实施中的新发现会改变其他任务的定义，使并行结果逐渐偏离。
  • 可靠性仍有分歧。 有人认为独立复核与反馈迭代能修正错误，也有人认为监督成本会抵消委派收益。

材料是 HN 讨论抓取文本，未读到所链接的 Cognition 原文全文，不能据此完整概括原文立场。页面显示的 123 分、89 条评论是抓取时的社区互动计数，不是技术效果指标。

短信助手、并行编码及复核效果均属评论者个人经验，缺少模型配置、对照实验和可复现记录。“约 50k token 后丢失目标”等说法也未附测量方法，不能作为通用阈值。共享知识库与编排架构的优势主要是设计主张；材料未提供独立核验或系统性能基准。

对 swarm scaling 的意义

这份讨论适合用于提炼扩展瓶颈，不能证明 agent 越多越好或越差。值得检验的变量包括：子任务接口是否清晰、任务定义能否保持稳定、哪些信息需要共享、哪些推理过程应隔离，以及纠偏需要多少人工介入。

它尤其提醒：上下文隔离带来的收益，不等同于增加并行 agent 的收益。评估 swarm scaling 时，应分别衡量过滤信息、独立复核和并行执行的效果，并计入协调与返工成本。
