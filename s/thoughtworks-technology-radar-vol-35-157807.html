一句话

Thoughtworks 本期更强调由开发者直接掌控的多会话并行，并指出：扩大 agent 使用规模，首先会遇到人的审查能力与交付流程的容量限制。

主要内容

  • 材料区分了三种组织方式：开发者分别管理多个会话；按预设角色和流程协作的 agent 团队；由编排 agent 自行拆分、分配任务的 swarm。后两者把更多决策权交给 agent。
  • Thoughtworks 团队目前主要采用直接控制多个会话的方式，并认为这是合理的起点。另一种实践是让 agent 承担运行更久的大块任务，例如开发者定义任务、事后审查的夜间无人值守构建。
  • 并行会话工具通过状态收件箱集中展示待回答、待批准事项；Git worktree 隔离工作副本，但可能积累难以合并的分支。会话内的 subagent 则承担窄任务，减少探索与重试对主上下文的干扰。
  • 扩容压力会沿流程传递：开发者注意力不足，可能使人工监督流于形式；多个开发者同时使用多个 agent，也可能让变更超过交付流水线的处理能力。
  • 配套能力包括持续维护和评估 agent 的运行环境，以及按任务选择、路由模型。成本还受批处理、数据移动和底层基础设施效率影响。

对 swarm scaling 的意义

这份材料提供的是扩容约束框架：增加 agent 之前，需要同时考察任务隔离、上下文管理、审查容量、分支整合和上线队列。更多并行产出能否转化为更多已交付成果，取决于整条流程。

它也提醒调研者区分“人管理更多会话”和“swarm 自主协调”：两者的授权程度与协调机制不同，不能用前者的实践经验直接证明后者有效。
