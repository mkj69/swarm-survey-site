一句话

这篇复盘说明：独立任务可以靠大量代理快速铺开，但规模上限很快转移到共享资源、结果验收和审查队列，PR 数量也不等于完成交付。

主要内容

  • 作者称，在 35 个仓库上运行 200 多个 Claude Code 子代理，一天创建 219 个 PR，主要处理跨仓库迁移。
  • 有效的任务约束是：每个代理限定仓库、分支和 PR 目标，按清单执行；不符合迁移条件就退出。约 40 次运行选择跳过，避免制造无用改动。
  • 共用检出目录导致分支和提交互相干扰；独立临时克隆缓解了这类冲突，但没有消除主机资源竞争。
  • 故障包括：清理进程误杀其他代理的构建、克隆及依赖安装耗尽磁盘、工作目录错误造成空差异 PR，却被运行日志标成成功。
  • 后续改进包括共享资源加锁、克隆失败时使用本地缓存、预先筛选目标仓库，并将流程固化为可复用 skill。
  • 作者估计约 70% 的 PR 可直接合并，其余需要修正。人工审查、Devin 二次审查队列及 GitHub Actions 额度成为后续瓶颈。

证据与可信度

提供的内容包含正文与 FAQ，并非仅摘要；正文标注更新于 2026 年 5 月 6 日。

219 个 PR、35 个仓库、200 多次运行、约 40 次跳过，以及磁盘用量超过 60GB，均为作者自报，材料未附完整运行日志、PR 清单或资源监控。约 70% 可直接合并属于作者估计；约第 180 个 PR 时触及 Actions 额度，也无账单记录佐证。没有独立核验。

并发口径尤其含糊：文章同时使用“每仓库一个代理”“200 多次运行”和“200 多个并发代理”，未解释批次与峰值并发的关系，不能据此确认实际同时运行数量。串行耗时与“一周缩至一下午”的说法也缺少对照测量，不能算作已验证的加速比。

对 swarm scaling 的意义

这是独立仓库任务的扇出案例，能支持任务分解、执行隔离和资源治理的实践判断，不能证明复杂协作任务也能获得同样收益。

关键启示是：扩容要同时处理任务准入、共享资源限流和结果验收。运行成功状态不足以证明产物有效；空差异 PR 与后续修改需求说明，应把有效产物和审查完成情况纳入评价。案例显示，代理生成速度提升后，系统吞吐仍可能受磁盘、CI 额度及审查队列限制。
