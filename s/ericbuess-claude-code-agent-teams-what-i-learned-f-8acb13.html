一句话

这篇个人实测的核心判断是：Agent Teams 的价值在于并行探索与相互审查，但额外 token 和协调开销是否划算，作者没有做定量验证。

主要内容

  • 协作结构：一个主会话负责分工与汇总，多个独立 Claude Code 实例各有上下文窗口，通过共享任务板和直接消息协作。成员加载项目配置，但不继承主会话的对话历史。
  • 与 subagents 的区别：后者主要向调用者返回结果；Agent Teams 允许成员互相讨论、自行领取任务，更适合需要交叉验证的工作。作者所说的“swarm mode”是社区对 Agent Teams 的称呼。
  • 适用任务：作者最认可研究和审查，也看好边界清晰的模块开发、跨层协作及多假设调试。简单修复和顺序任务的收益较弱。
  • 成本来源：各成员分别加载上下文，消息交换和任务轮询也消耗 token。作者感觉并行确实更快、成本也更高，但没有提供加速比或费用对照。
  • 运行摩擦：实测涉及任务状态未更新、依赖被阻塞、关闭延迟及分屏窗格失效。关于同一会话能否连续运行多个团队，作者明确保留疑问。
  • 记忆功能需分开看：文章后半介绍的持久记忆属于 subagents，不能当作 Agent Teams 已具备群体长期学习能力的证据。

证据与可信度

材料是 EricBuess 于 2026 年 2 月 6 日发表的个人测试与文档整理，未给出标准任务集、重复次数、耗时记录、token 账单或质量评分，也未对同一任务比较单会话、subagents 和团队。因此，“更快”“更贵”“研究审查最合适”属于个人经验，不能推出规模收益曲线。

文中的“先用 2 名成员、再考虑 5 个 agent”是入门建议，并非测得的最优规模。架构与限制部分混合了作者观察和对官方文档的转述；本文未独立核验。元数据中的 295 次点赞、45320 次浏览只反映传播情况。

对 swarm scaling 的意义

这份材料提示，扩展收益取决于任务能否拆成相对独立、又能通过交流互相纠错的部分。研究和审查较容易满足这一条件；并行实现则更依赖边界划分和协调可靠性。

它同时暴露了扩展的负担：重复上下文、通信、状态同步和会话管理。材料支持把这些列为评测维度，但不足以证明增加成员后收益如何变化，也无法确定成本与质量的最佳平衡点。
