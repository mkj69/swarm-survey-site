一句话

这篇二手综述把“设计循环”解释为从手动指挥单个 agent，转向编写能调度、验证和终止多个 agent 的持续运行系统，但没有证明 agent 数量增加能带来多少收益。

主要内容

  • 作者区分了几种常被混称为 loop 的机制：模型调用工具的反馈循环、自主追逐目标、反复重置上下文执行任务，以及监督其他循环的多 agent 编排。
  • 文中认为，编排层的关键变化是定时启动、并发监督、持久化状态与崩溃恢复。人的工作随之转向定义目标、组织流程和判断完成条件。
  • 定时器只负责启动；模型依据当前状态选择行动，验证结果后继续或停止，才构成作者强调的闭环。
  • 文章把端到端验证放在核心位置，并提出最大迭代次数、停滞检测和费用上限，防止错误与成本持续累积。
  • 作者最终认为，可复用且经过测试的技能才是长期资产；循环负责反复调用这些能力。

证据与可信度

  • 这是社交讨论、访谈与项目案例的二手汇编，没有受控实验，也没有统一的任务、成本或质量评估。
  • Cherny 的“30 天合入 259 个 PR、贡献全部由 Claude Code 编写”属于经转述的个人自报，不能据此推断生产率提升幅度。作者夜间处理约 30 个仓库也是个人经验。
  • Gas Town 协调 20—30 个实例属于文中项目描述；“数百或数千 agent”是使用建议或规模主张，不是经过验证的有效并行度。
  • Uber 费用限制、Gartner 部署比例等数字均为文章转述，所给材料没有足够原始证据供独立核验。“循环成为最昂贵部分”因此更接近观点。
  • 检索统计存在口径差异：开头称找到 15 个 Reddit 线程、21 条 X 帖子，末尾列出 47 个线程、56 条帖子，未解释差异。互动量反映传播度，不能证明技术结论。

对 swarm scaling 的意义

它提供的是工程问题清单：规模扩大后，需要把任务分派、共享状态、验证反馈、故障恢复和终止条件一起设计。单纯增加 agent 数量并不等于有效扩展。

其最有价值的启发是：应考察整个闭环能否稳定交付，以及每份合格成果消耗多少成本。材料没有给出串行与并行对照、协调开销或收益曲线，因此只能支持这种研究方向，不能作为 swarm scaling 已获实证的依据。
