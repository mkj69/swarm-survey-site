一句话

这份工程实践复盘表明：增加 coding agent 数量之前，应先解决任务依赖、代码可见性、决策传递和真实产品验证，否则并发只会增加人的协调负担。

主要内容

  • 作者自述是 MiniMax MCode 后端工程师，曾用 Agent Lord 将功能拆给多个 CLI，在独立 worktree 中实现，再统一集成、交叉审查。
  • 一次八模块任务耗时 14 小时，约 76% 的时间只有一个 CLI 工作。问题在于模块被排成依赖链，且下游仍从原始代码出发，无法看到上游成果，最终合并才暴露接口问题。
  • 作者进一步审计此前一个月的会话，发现两类反复出现的瓶颈：模块测试通过却无法完成真实用户流程；已有决策在交接中丢失，迫使人反复解释、检查和催促。
  • 新流程以一个 agent 负责端到端交付，允许委派子任务，但由负责人整合结果。先明确需求，把决策和验收场景写入文件，经另一模型家族检查及人工确认后冻结，再开始实现。
  • agent 必须能启动、操作和观察真实应用；进度持续写入仓库文件。最终由另一模型家族独立验收，脚本检查规格未变、报告对应待合并代码、验收通过及验证者身份。
  • 作者也反思规则膨胀：工作流经历密集迭代后，主动删减脚本和指令，强调复杂度需要证明收益。

证据与可信度

  • 并发数字来自作者对单次任务的自报审计：最高同时运行 4 个 CLI，平均 1.27 个；76% 指该任务中仅一个 CLI 工作的时间占比，不能解读为全部任务的利用率。
  • 月度审计据称覆盖约 1,700 个会话，细读 40 条任务链并核对原始日志；同期编排器调度了 214 个任务、490 次操作。这些计数描述使用规模，不能直接证明效率。
  • 故障案例和跨模型检查发现遗漏的问题，属于个人工程经验。材料未提供可复算日志、对照实验或新旧流程的交付耗时、成本及缺陷率比较。
  • 作者明确将外部吞吐量数字视为自报。本文引用其他团队经验作为设计依据，并不构成对新流程的独立核验；作者任职及推荐 MCode 的背景也应纳入判断。

对 swarm scaling 的意义

  • 可并行的任务结构比 agent 数量更关键。 依赖链限制并发，隔离 worktree 若缺乏上游代码传递机制，还会把集成风险推迟到最后。
  • 人的决策带宽也是扩展上限。 固化规格、保留进度、让 agent 自行操作产品，旨在减少每增加一个任务所需的人类介入。
  • 单一负责人可以组织多 agent。 本文支持有选择地并行，并通过独立验证约束交付；但尚不足以证明这种组织方式在更大规模上更快或更便宜。
