一句话

可信的 agent 扩展，关键不是增加并发数量，而是把验证、隔离、交接和失败停止做成可复用的流水线。

主要内容

  • 作者借早餐生产线说明瓶颈：如果复现与验证仍依赖人，增加代码产出只会积压审查和返工。
  • 在 Cursor 性能排查中，作者通过技能让 agent 使用浏览器调试工具，完成复现、性能采样、修改和复测；再为各 agent 隔离代码检出、端口、进程和用户状态，减少并发干扰。
  • 工具可用仍不等于工程质量可靠。作者把反复出现的失败整理为 pstack 技能，包括先复现、比较假设、检查改动影响，以及保存测试和决策证据。
  • 维护流程被拆成分诊、复现、修复：复现阶段要求两次进入相同故障状态；修复阶段继承环境和证据，提交草稿 PR。每个阶段都能因证据不足或风险过高停止。
  • StyleX 大规模迁移暴露了验证覆盖的边界：已捕获状态的视觉一致，仍漏掉层叠、全局类依赖和样式优先级问题。后续改为逐个叶子组件迁移，把检查和失败提前。
  • 对机械步骤，作者主张生成迁移脚本与检查器；agent 主要处理假设选择、证据解释和需要判断的部分。

证据与可信度

这是参与者的工程经验总结，同时介绍其工具及 Cursor Automations，不能视为独立评测。

文中自报：迁移 PR 接近 40 万行，其中大量是生成的验证证据；生成 CSS 从超过 3 万行降至约 6000 行；最近几天自动化每天迁移一个组件。这些数字分别描述改动体量、代码体积和局部工作节奏，不能直接证明开发效率或质量提升。材料未提供原始统计、对照组、失败率、人工审查耗时或独立核验。

“两次复现”是流程门槛，不是可靠性测量。元数据中的 978 次点赞、197354 次浏览只反映传播情况。

对 swarm scaling 的意义

文章把扩展问题从“能启动多少 agent”转向“人能验收多少可信结果”。隔离环境解决资源碰撞，结构化证据降低交接与审查成本，可复用工具让后续运行继承经验，阶段停止机制则抑制错误向下游累积。

其价值是提供可操作的扩展设计思路，而非证明 swarm 的规模收益：材料没有并发规模与吞吐、成本、缺陷率之间的实验。尤其值得保留的教训是，局部检查通过并不代表系统行为完整正确；缩小任务单元，也是在缩小验证盲区和返工成本。
