一句话

A2A 正从跨平台通信协议走向云平台基础设施，但生态扩张尚不能证明大规模 swarm 的性能与协作收益。

主要内容

  • Linux Foundation 宣布，A2A 支持组织从 2025 年 4 月的 50 多家增至 150 多家，覆盖主要云厂商及企业软件公司；“支持组织”不能直接等同于生产用户。
  • 1.0 稳定规范加入多协议、多租户、安全流程及迁移路径，并通过签名 Agent Card 验证身份，支持沿用常见的安全与负载均衡机制。
  • 微软将其集成到 Azure AI Foundry 和 Copilot Studio，AWS 通过 Bedrock AgentCore Runtime 提供支持。文章也称 Google 平台已深度集成。
  • 不同框架构建的 agent 可在不共享内部记忆的情况下委派子任务、协调工作流。A2A 负责 agent 间通信，MCP 负责连接工具与数据。
  • 文章宣称供应链、金融、保险及 IT 运维已有生产部署，但未列出具名客户或案例细节。

证据与可信度

  • 这是项目托管方发布的周年新闻稿，适合了解官方采用口径与功能进展，存在宣传倾向。
  • 150 多家组织、超过 22,000 个 GitHub stars、五种生产可用语言 SDK，均为官方汇总；文中未提供逐项统计方法或独立核验。起止组织数都是下限，不能据此算出准确增长倍数。
  • AP2 获 60 多家组织支持，属于支付相关倡议的另一项统计，不能并入 A2A 生产采用数。
  • “生产就绪”和“已进入生产”属于官方判断与自报。文中没有并发 agent 数、吞吐、延迟、成本或任务成功率测量，也没有独立验证部署效果。

对 swarm scaling 的意义

A2A 针对的是异构 agent 扩张时的连接与协调门槛：统一发现、通信和身份机制，有望减少跨框架、跨厂商集成的定制工作；云平台支持则提供了部署入口。

但互通只是规模化的前提。材料没有证明增加 agent 数量能提高任务质量，也未说明通信开销、冲突处理和故障传播如何随规模变化。路线图仍包含互操作规范、注册机制及测试工具，说明生态支持数量与可验证的大规模协作能力需要分开评估。
