一句话

这篇博客汇集多项研究与游戏实验，主张 swarm 的瓶颈在协调与信息整合，但其证据主要是二手转述，不能据此断言增加 agent 必然降低性能。

主要内容

  • 作者以一个含 49 个角色的游戏开发仓库为引子，质疑组织层级和角色数量能否转化为实际产出。
  • 据文中转述，Civ50 将 50 个 agent 放入 Minecraft，运行 3 小时，产生约 5,900 条消息，并出现重复编写捕鱼脚本、围绕少量资源长时间协商等现象。作者将其解释为协调成本挤占执行时间。
  • 博客称，Silo-Bench 在信息分散的算法任务中发现：相较掌握相同信息的单 agent，两个 agent 的表现下降 15%—49%，50 个下降 80%—100%；核心困难是整合已获得的信息。
  • 对《When 20 Agents Fail to Sort》，文章只概述了分布式排序中的共享状态、约定对齐与终止判断问题，并称 CAMOC 可改善结果，没有给出具体实验数据。
  • 文中转述的 Google 研究呈现任务差异：集中协调在可并行任务上提升表现，而被测试的多 agent 方案在顺序任务上均退步。这比“多 agent 普遍无效”更有解释力。

以上数字均来自博客转述，本页未独立核验原始报告、论文或日志。涉及《When 20 Agents Fail to Sort》的原文未找到，未读到全文；它目前只能作为待查线索，不能据此确认论文结论或 CAMOC 的效果。

性能下降百分比属于作者转述的基准测量，但材料未交代指标、计算口径和不确定性。“协调开销超线性增长”“实时消息优于书面记忆”“无人接近解决”等判断，强于本文展示的证据。评论区关于消息时机与 token 成本的解释属于个人观点或经验。

对 swarm scaling 的意义

这份材料适合提出实验问题：扩容时，应同时测量任务产出、消息成本、重复劳动、共享状态一致性和错误传播，而不能只统计 agent 数量。

它也提示应按任务可分解性比较单 agent、集中协调和其他结构。游戏中的官僚化现象可作为失效案例，但不足以证明集中管理总是最优，或短期群体行为代表长期稳定表现。对仓库而言，本文最有价值的是提供研究线索与待验证假设，而非充当规模定律的直接证据。
