TokenDance：通过集体 KV 缓存共享扩展多智能体 LLM 推理服务TokenDance: Scaling Multi-Agent LLM Serving via Collective KV Cache Sharing
摘要。Abstract.
多智能体 LLM 应用以同步轮次组织执行，由中央调度器收集所有智能体的输出，并将合并后的上下文重新分发。 Multi-agent LLM applications organize execution in synchronized rounds where a central scheduler gathers outputs from all agents and redistributes the combined context. 这种全收集（All-Gather）通信模式造成了大量 KV 缓存冗余，因为每个智能体的提示词都包含相同的共享输出块，而现有复用方法无法高效利用这种冗余。 This All-Gather communication pattern creates massive KV Cache redundancy, because every agent’s prompt contains the same shared output blocks, yet existing reuse methods fail to exploit it efficiently.
我们提出 TokenDance，该系统利用 All-Gather 模式实现集体 KV 缓存共享，从而扩大并发智能体的规模。 We present TokenDance, a system that scales the number of concurrent agents by exploiting the All-Gather pattern for collective KV Cache sharing. TokenDance 的 KV Collector 通过一次集体操作，在整个轮次范围内完成 KV 缓存复用，因此，无论智能体数量多少，复用一个共享块的开销都只需承担一次。 TokenDance’s KV Collector performs KV Cache reuse over the full round in one collective step, so the cost of reusing a shared block is paid once regardless of agent count. 其 Diff-Aware Storage 将同源缓存编码为相对于单个主副本的块稀疏差分，在代表性工作负载上实现了 $11$ – $17\times$ 的压缩比。 Its Diff-Aware Storage encodes sibling caches as block-sparse diffs against a single master copy, achieving $11$ – $17\times$ compression on representative workloads. 在 GenerativeAgents 和 AgentSociety 上的评估表明，在满足服务级别目标（SLO）要求的条件下，TokenDance 支持的并发智能体数量最高可达启用前缀缓存的 vLLM 的 $2.7\times$，将每个智能体的 KV 缓存存储需求最多降至原来的 $1/17.5$，并且相较于逐请求的位置无关缓存，实现最高 $1.9\times$ 的预填充加速。 Evaluation on GenerativeAgents and AgentSociety shows that TokenDance supports up to $2.7\times$ more concurrent agents than vLLM with prefix caching under SLO requirement, reduces per-agent KV Cache storage by up to $17.5\times$ , and achieves up to $1.9\times$ prefill speedup over per-request position-independent caching.
1. 引言1. Introduction
大语言模型（LLMs）是许多面向编程（Qian et al., 2024; Hong et al., 2024）、搜索（Wu et al., 2023; Li et al., 2023; Li et al., 2026）和仿真（Park et al., 2023; Piao et al., 2025; Puig et al., 2018; Li et al., 2024）的多智能体平台的执行引擎。 Large language models (LLMs) are the execution engine of many multi-agent platforms for coding (Qian et al., 2024; Hong et al., 2024), search (Wu et al., 2023; Li et al., 2023; Li et al., 2026), and simulation (Park et al., 2023; Piao et al., 2025; Puig et al., 2018; Li et al., 2024). 社会仿真将多智能体推理服务推向极限：它需要大量智能体同时运行，需要开展复杂的多轮交互且每个智能体的上下文随时间不断增长，还需要使用工具，从而进一步增加提示词长度。 Social simulation pushes multi-agent serving to its limits: it requires many agents running simultaneously, complex multi-round interactions where each agent’s context grows over time, and tool use that further extends prompt length. 随着这些应用在生产部署中从少数几个智能体扩展到数十乃至数百个智能体，GPU 显存成为制约规模扩展的主要因素。 As these applications grow from a handful of agents to tens or hundreds in production deployments, GPU memory becomes the dominant scaling constraint. 每个智能体都维护一个跨交互轮次持续保留的 KV 缓存，而所有活跃智能体的缓存必须同时驻留在 GPU 显存中。 Each agent maintains a KV Cache that persists across interaction rounds, and all active agents’ caches must coexist in GPU memory simultaneously. 因此，多智能体 LLM 推理服务的核心挑战，是在固定显存预算下最大化可并发运行的智能体数量。 The central challenge for multi-agent LLM serving is therefore maximizing the number of agents that can run concurrently under a fixed memory budget.
这种显存压力有其结构性根源。 This memory pressure has a structural root cause. OpenClaw（OpenClaw contributors, 2026）和 MoltBook（moltbook, 2026）等多智能体框架以同步轮次组织执行：每个智能体生成一个输出，中央调度器收集所有输出，并将合并后的上下文重新分发给每个智能体，供下一轮使用。 Multi-agent frameworks such as OpenClaw (OpenClaw contributors, 2026) and MoltBook (moltbook, 2026) organize execution in synchronized rounds: each agent produces an output, a central scheduler gathers all outputs, and redistributes the combined context to every agent for the next round. 我们借用分布式计算中相应集体操作的名称，将这种反复出现的数据流称为 All-Gather 模式。 We call this recurring data flow the All-Gather pattern, after the corresponding collective in distributed computing. 这种模式直接解释了显存问题的成因。 The pattern directly explains the memory problem. 如图 1 所示，每个智能体在第 $t{+}1$ 轮的提示词都将私有历史（$H$）与完整的共享输出块集合（$O$）组合在一起。 As Figure 1 shows, each agent’s prompt for round $t{+}1$ combines a private history ( $H$ ) with the full set of shared output blocks ( $O$ ). 由于私有历史的长度各不相同，相同的共享块在不同提示词中处于不同的绝对位置，使推理服务引擎无法识别这些重叠内容。 Because private histories differ in length, the same shared blocks land at different absolute positions across prompts, preventing the serving engine from recognizing the overlap. 结果是 GPU 显存中存在 $N$ 个几乎相同的 KV 缓存。 The result is $N$ near-identical KV Caches in GPU memory. 因此，显存用量随智能体数量增长，而非随不重复上下文的数量增长。 Therefore, memory grows with agent count rather than with the amount of unique context.

2.1. All-Gather 模式2.1. The All-Gather Pattern
如第 1 节所述，All-Gather 模式将多智能体执行组织为同步轮次，由调度器收集所有智能体的输出，并重新分发合并后的上下文。 As introduced in Section 1, the All-Gather pattern organizes multi-agent execution in synchronized rounds where a scheduler gathers all agent outputs and redistributes the combined context. 下面我们对这一结构进行形式化描述。 We now formalize this structure. 对于一个包含 $N$ 个智能体的系统，每个智能体 $i$ 都维护一份私有历史 $H_{i}^{t}$，其中包含其系统提示词以及截至第 $t$ 轮的先前交互。 For a system with $N$ agents, each agent $i$ maintains a private history $H_{i}^{t}$ containing its system prompt and prior interactions up to round $t$ . 在第 $t$ 轮中，每个智能体 $j$ 生成一个输出块 $O_{j}^{t}$。 In round $t$ , each agent $j$ produces an output block $O_{j}^{t}$ . 该轮输出的共享集合为： The shared set of round outputs is: 
| (1) | | $\mathcal{O}^{t}=\{O_{1}^{t},O_{2}^{t},\ldots,O_{N}^{t}\}$ |
于是，智能体 $i$ 在第 $t+1$ 轮的提示为： The prompt for agent $i$ in round $t+1$ is then: 
| (2) | | $P_{i}^{t+1}=H_{i}^{t}\|\Pi_{i}(\mathcal{O}^{t})$ |
其中，$\Pi_{i}$ 是调度器为智能体 $i$ 定义的共享输出块布局。 where $\Pi_{i}$ is the scheduler-defined layout of the shared output blocks for agent $i$ . 该轮中的每个提示都包含相同的共享输出块和一份私有历史记录；由于私有历史记录的长度不同，共享块在不同请求中的绝对位置也不同。 Every prompt in the round contains the same shared output blocks and one private history, and the shared blocks appear at different absolute positions across requests because the private histories differ in length.
2.2. LLM 推理服务中的 KV 缓存复用2.2. KV Cache Reuse in LLM Serving
LLM 推理服务受内存瓶颈制约：系统存储 KV 缓存，以避免重新计算先前词元的注意力键和值，而管理这些缓存是扩展系统容量的首要挑战。 LLM serving is memory-bound: the system stores KV Caches to avoid recomputing attention keys and values for prior tokens, and managing these caches is the primary challenge for scaling system capacity. 现有的复用方法分为两类。 Existing reuse methods fall into two categories.
vLLM (Kwon et al., 2023) 和 SGLang (Zheng et al., 2024) 使用的前缀缓存，仅在新请求与已存储序列具有完全相同的词元前缀时才复用缓存张量。 Prefix caching, used by vLLM (Kwon et al., 2023) and SGLang (Zheng et al., 2024), reuses cached tensors only when a new request shares an exact token prefix with a stored sequence. 这种方法适用于共享同一系统提示的请求，但一旦各智能体的私有历史记录导致前缀出现差异，它就会失效。 This works well for requests that share a common system prompt but fails once per-agent private histories cause the prefix to diverge.
位置无关缓存（PIC）方法 (Yao et al., 2025; Hu et al., 2024; Ye et al., 2025a; Yang et al., 2025) 通过在任意偏移位置恢复共享块，消除了这一限制。 Position-independent caching (PIC) methods (Yao et al., 2025; Hu et al., 2024; Ye et al., 2025a; Yang et al., 2025) remove this constraint by recovering shared blocks at arbitrary offsets. 其核心思想是校正位置编码的差异：PIC 方法首先应用 RoPE 旋转，将缓存的键与新请求中的目标位置对齐，然后计算旋转后的缓存键值与新计算的键值之间的差异，以识别重要位置，即二者差异显著的词元位置。 The key idea is to correct for positional encoding differences: a PIC method first applies RoPE rotation to align cached Keys with the target positions in the new request, then computes key differences between the rotated cached values and freshly computed values to identify important positions—token positions where the two differ significantly. 仅对这些重要位置进行选择性重新计算，其余位置则直接复用旋转后的缓存值。 Only these important positions are selectively recomputed, while the remaining positions reuse the rotated cached values directly. 这使得前缀之外的共享得以恢复，代价是旋转和重新计算所需的额外计算开销，以及在未经重新计算而直接复用的位置上略微损失准确性。 This recovers sharing beyond the prefix at the cost of additional compute for rotation and recomputation, and a minor accuracy trade-off at positions that are reused without recomputation.

2.3. 现有推理服务系统的局限性2.3. Limitations of Existing Serving Systems
All-Gather 模式产生了一种特定的冗余组合，而现有推理服务系统未能利用这种冗余。 The All-Gather pattern creates a specific combination of redundancy that existing serving systems fail to exploit. 我们将已有工作分为两类，并解释各自的不足。 We group prior work into two categories and explain why each falls short.
感知智能体、以计算为中心的调度器。 Agent-Aware, Compute-Centric Schedulers. Parrot (Lin et al., 2024)、Autellix (Luo et al., 2025) 和 Teola (Tan et al., 2024) 将应用级依赖图引入推理服务后端，以优先处理关键请求并减少队头阻塞。 Parrot (Lin et al., 2024), Autellix (Luo et al., 2025), and Teola (Tan et al., 2024) inject application-level dependency graphs into the serving backend to prioritize critical requests and reduce head-of-line blocking. ScaleSim (Pan et al., 2026) 估计未来调用间距，以指导仿真工作负载中的预取。 ScaleSim (Pan et al., 2026) estimates future invocation distances to guide prefetching in simulation workloads. 这些系统决定每个请求何时运行，但不控制由此产生的 KV 缓存如何计算或存储。 These systems decide when each request runs, but they do not control how the resulting KV Caches are computed or stored. 底层内存分配器仍将每个智能体的缓存视为独立对象。 The memory allocator underneath still treats every agent’s cache as an independent object. 因此，无论如何调度，非关键智能体的突发涌入都可能导致关键智能体的缓存被驱逐。 A burst of non-critical agents can therefore evict a critical agent’s cache regardless of the schedule. 这些系统均未检测到 All-Gather 轮次中的 $N$ 个请求共享相同的输出块，因此既未减少复用所需的计算工作，也未降低存储占用。 None of these systems detects that the $N$ requests in an All-Gather round share the same output blocks, so neither the reuse work nor the storage footprint is reduced.
以 KV 缓存为中心、不感知智能体的引擎。vLLM (Kwon et al., 2023) 和 SGLang (Zheng et al., 2024) 通过前缀匹配复用缓存张量，而一旦私有历史记录从位置零开始出现差异，这种方式就会失效。 KV-Cache-centric, Agent-Agnostic Engines. vLLM (Kwon et al., 2023) and SGLang (Zheng et al., 2024) reuse cached tensors through prefix matching, which breaks as soon as private histories diverge from position zero. CacheBlend (Yao et al., 2025) 和 EPIC (Hu et al., 2024) 通过在任意偏移位置复用 KV 缓存块来消除这一位置限制，但它们仍然分别分析每个请求：$N$ 个智能体会对相同的共享块触发 $N$ 次独立的复用处理。 CacheBlend (Yao et al., 2025) and EPIC (Hu et al., 2024) lift this positional constraint by reusing KV Cache blocks at arbitrary offsets, but they still analyze each request separately: $N$ agents trigger $N$ independent reuse passes over the same shared blocks. Mooncake (Qin et al., 2024) 和 CacheGen (Liu et al., 2024a) 通过解耦和压缩来扩展缓存池，但其策略由全局内存压力驱动，而非由轮次结构驱动。 Mooncake (Qin et al., 2024) and CacheGen (Liu et al., 2024a) expand the cache pool through disaggregation and compression, yet their policies are driven by global memory pressure, not by round structure. Tokencake (Bian et al., 2025) 在以 KV 缓存为中心的后端之上增加了感知智能体的调度，主动卸载停滞的智能体，并为关键智能体预留内存。 Tokencake (Bian et al., 2025) adds agent-aware scheduling on top of a KV-Cache-centric backend, proactively offloading stalled agents and reserving memory for critical ones. 所有这些系统的最终结果都相同：每个智能体都持有一份稠密、独立的 KV 缓存副本，即使同一轮中各智能体之间超过 90% 的缓存块完全相同，也不会释放任何存储空间。 Across all of these systems, the final outcome is the same: every agent holds a dense, independent KV Cache copy, and no storage is freed even when over 90% of cache blocks are identical across agents in the same round.

4. TokenDance 设计4. TokenDance Design
TokenDance 的设计始于 All-Gather 应用结构与推理服务系统之间的不匹配。 The design of TokenDance starts from a mismatch between the All-Gather application structure and the serving system. 多智能体应用按轮次通信，但推理服务系统接收到的是扁平的 token 流，丢失了私有块与共享块之间的逻辑边界，并将每个请求视为相互独立。 Multi-agent applications communicate in rounds, but the serving system receives a flat token stream, loses the logical boundary between private and shared blocks, and treats every request as independent.
这种不匹配造成了三种相互叠加的低效问题。 This mismatch creates three compounding inefficiencies. 首先，运行时无法识别不同请求间的共享块，因为基于位置的索引将内容身份与绝对偏移混为一谈。 First, the runtime cannot identify shared blocks across requests because position-based indexing conflates content identity with absolute offset. 其次，位置无关的复用方法会针对该轮次中的每个请求重复执行相同分析，尽管所有请求使用的都是相同的共享块。 Second, position-independent reuse methods repeat the same analysis for each request in the round, even though all requests consume the same shared blocks. 第三，即使完成复用，得到的 KV Cache 也几乎完全相同，但系统仍为每个请求存储一份完整的稠密副本。 Third, even after reuse, the resulting KV Caches are nearly identical, yet the system stores one full dense copy per request. 这些问题累积起来，导致每个智能体的 KV Cache 成本过高，直接限制了并发智能体的数量。 The cumulative result is an inflated per-agent KV Cache cost that directly caps the number of concurrent agents.
TokenDance 通过两条设计原则解决这些低效问题。 TokenDance addresses these inefficiencies with two design rules. 首先，它使轮次结构始终保持可见，直到运行时能够利用该结构。 First, it keeps the round structure visible until the runtime can use it. 其次，它为每个请求保留一份正确的缓存状态，同时共享该轮次中真正共通的工作与状态。 Second, it preserves one correct cache state per request while sharing the work and state that are truly common across the round. 第一条原则催生了轮次感知接口（第 4.1 节）和集体 KV Cache 复用（第 4.2 节）。 The first rule leads to a round-aware interface (Section 4.1) and collective KV Cache reuse (Section 4.2). 第二条原则催生了差异感知存储与融合差异恢复（第 4.4 节）。 The second rule leads to diff-aware storage and fused diff restore (Section 4.4). 本节其余部分将详细介绍各个组件。 The rest of this section describes each component in detail.
4.1. 轮次感知的提示接口4.1. Round-Aware Prompt Interface
如果运行时仅接收到扁平的 token 流，就无法利用 All-Gather 模式。 The runtime cannot exploit the All-Gather pattern if it only receives a flat token stream. TokenDance 提供了一种轮次感知的提示接口，用于保留每个提示的逻辑块结构，使运行时即使在共享块位于不同请求中的不同绝对位置时也能识别它们。 TokenDance provides a round-aware prompt interface that preserves the logical block structure of each prompt, so the runtime can recognize shared blocks even when they appear at different absolute positions across requests.
任何遵循 All-Gather 模式的多智能体框架，只需极少的代码改动即可采用这一接口。 Any multi-agent framework that follows the All-Gather pattern can adopt this interface with minimal code changes. 如果应用不遵循该模式，TokenDance 则回退到标准的单请求路径，且不会造成性能损失。 If the application does not follow the pattern, TokenDance falls back to the standard single-request path with no performance loss.
应用为每个智能体组装一个提示，并在相邻逻辑块之间插入保留的分隔 token <TTSEP>。 The application assembles one prompt per agent and inserts a reserved separator token <TTSEP> between adjacent logical blocks. 图 6 展示了一个轮次中包含三个智能体的示例。 Figure 6 shows an example for three agents in one round. 每个提示包含一个私有历史块和同一组共享输出块，各块之间由分隔 token 隔开。 Each prompt contains a private history block and the same set of shared output blocks, with separator tokens in between. 这些具有明确边界的块使请求之间的复用关系显式化：私有历史、每条共享的智能体更新以及轮次任务在分词后均可被单独识别。 The delimited blocks make the reusable relationship between requests explicit: the private history, each shared agent update, and the round task are all individually identifiable after tokenization.
一旦块边界可见，运行时便从固定大小的分块哈希切换为基于片段的哈希。 Once block boundaries are visible, the runtime switches from fixed-size chunk hashing to segment-based hashing. 每条共享更新都按其自身的内容片段建立索引，而不是按其在一个长提示中的绝对位置建立索引。 Each shared update is indexed by its own content segment rather than by its absolute position in one long prompt. 因此，包含相同共享更新的两个请求会将该更新映射到同一个缓存对象，即使它们的私有历史长度不同。 Two requests that contain the same shared update therefore map that update to the same cache object, even when their private histories differ in length. 这是将 All-Gather 模式转化为推理服务优化的第一步：运行时现在知道哪些块是共享的，并且能够在块级别而非前缀级别分析复用。 This is the first step that turns the All-Gather pattern into a serving optimization: the runtime now knows which blocks are shared and can reason about reuse at the block level rather than the prefix level.

4.2. 集体 KV Cache 复用4.2. Collective KV Cache Reuse
轮次结构可见后，下一个问题是重复执行的复用工作。 Once the round structure is visible, the next problem is repeated reuse work. 现有的位置无关缓存（position-independent caching，PIC）方法（Yao et al., 2025; Hu et al., 2024; Yang et al., 2025; Ye et al., 2025a）能够恢复前缀之外的共享，但仍然独立处理每个请求。 Existing position-independent caching (PIC) methods (Yao et al., 2025; Hu et al., 2024; Yang et al., 2025; Ye et al., 2025a) can recover sharing beyond the prefix, but they still process each request independently. 在包含 $N$ 个智能体的轮次中，运行时会针对同一组共享块分别执行 $N$ 次复用处理。 In an $N$ -agent round, the runtime performs $N$ separate reuse passes for the same set of shared blocks. 每次处理都会应用 RoPE、计算键差异并选择重要位置——由于共享块的内容完全相同，这些操作在不同请求中产生的结果几乎一致。 Each pass applies RoPE, computes key differences, and selects important positions—all operations that produce nearly identical results across requests because the shared blocks are content-identical. 这种逐请求的冗余与 All-Gather 模式并不匹配，因为在该模式下，同一轮中的共享更新对该轮所有请求都是相同的。 This per-request redundancy is a poor match for the All-Gather pattern, where the shared round updates are common to every request in the round.
TokenDance 通过集体 KV 缓存复用消除这种冗余，如图 7 所示。 TokenDance resolves this redundancy with collective KV Cache reuse, illustrated in Figure 7. KV Collector 不再独立处理每个请求，而是将一轮中的 $N$ 个请求分组，执行一次共享的 RoPE 旋转和一次共享的重要位置选择，然后仅更新各请求缓存中存在差异的位置。 Rather than processing each request independently, the KV Collector groups the $N$ requests in a round and performs one shared RoPE rotation and one shared important-position selection pass, then updates only the differing positions in each request’s cache. 图 7 将这种集体处理路径（T3）与完全重新计算（T1）及逐请求 PIC 复用（T2）进行了对比。 Figure 7 contrasts this collective path (T3) with full recomputation (T1) and per-request PIC reuse (T2).
对兼容请求进行分组。 Grouping Compatible Requests. KV Collector 从同一 All-Gather 轮次中收集提示词区间兼容、可进行集体处理的请求。 The KV Collector collects requests from the same All-Gather round whose prompt spans are compatible for collective processing. 兼容性要求这些请求具有相同的有效提示词长度、对缓存层可见的相同缓存区间，以及在执行引擎中互不重叠的槽位映射。 Compatibility requires that the requests have the same active prompt length, the same cached span visible to the cache layer, and non-overlapping slot mappings in the execution engine. 这些执行约束确保了逐层同步处理；不满足这些约束的请求会退回到独立分组或单请求处理路径。 These are execution constraints that ensure lockstep layerwise processing; requests that do not satisfy them fall back to separate groups or to the single-request path.
逐层集体复用。 Layerwise Collective Reuse. 对于每个兼容组，运行时以同步方式驱动逐层检索和模型执行。 For each compatible group, the runtime drives layerwise retrieval and model execution in lockstep. 在每一层，KV Collector 将组内所有请求的 Q 和 K 张量拼接为一个合并张量，并执行一次批量 RoPE 调用。 At each layer, KV Collector concatenates the Q and K tensors from all requests in the group into one combined tensor and applies a single batched RoPE call. 在配置的检查层上，运行时通过一次批量差异计算，将整个组中旋转后的键与缓存的键进行比较。 On the configured check layer, the runtime compares the rotated Keys against the cached Keys for the entire group in one batched difference pass. 这次计算会同时为每个请求识别重要位置，即缓存值与新计算值存在显著差异的词元位置。 This pass identifies the important positions—the token positions where the cached values diverge significantly from the freshly computed values—for each request simultaneously. 随后，运行时仅刷新各请求缓存的 K 和 V 张量中的这些重要位置。 The runtime then refreshes only those important positions in each request’s cached K and V tensors. 后续各层直接复用检查层识别出的重要位置集合，无需重复计算差异。 Later layers reuse the important-position set identified on the check layer directly, without repeating the difference computation.
因此，开销较大的操作——RoPE 旋转和键差异分析——对整个组仅执行一次，而非对每个请求各执行一次。 The expensive operations—RoPE rotation and key-difference analysis—are therefore performed once for the group rather than once per request. 只有最终的缓存更新仍需针对各请求单独进行，因为各请求的私有历史会使需要刷新位置上的值有所不同。 Only the final cache update remains request-specific, because each request’s private history produces different values at the positions that need refreshing. 在以请求为中心的处理路径中，复用分析的开销随智能体数量线性增长。 In a request-centric path, the reuse-analysis overhead grows linearly with the number of agents. 在 TokenDance 中，每层的整个组只需承担一次共享 RoPE 处理和一次共享差异分析的开销，只有逐位置刷新的开销随智能体数量增长。 In TokenDance, the group pays one shared RoPE pass and one shared diff-analysis pass per layer, and only the per-position refresh scales with agent count. 随着一轮中智能体数量的增加，这种开销分摊会减少每轮复用工作的总量。 As the number of agents in a round grows, this amortization reduces the total reuse work per round. 这种减少体现了扩展收益在计算方面的来源。 That reduction is the compute side of the scaling gain.
集体处理的开销分摊与底层的逐位置恢复方法相互解耦。 The collective amortization is decoupled from the underlying per-position recovery method. 当前原型使用 CacheBlend (Yao et al., 2025) 的选择性重新计算作为默认后端，但任何接受一组词元位置并返回修正后 K/V 张量的 PIC 方法，都可以通过适配器接口直接替换该后端。 The current prototype uses CacheBlend (Yao et al., 2025)’s selective recomputation as the default backend, but any PIC method that accepts a set of token positions and returns corrected K/V tensors can serve as a drop-in replacement through an adapter interface.
复用计划输出。 Reuse Plan Output. 集体 KV 缓存复用还会生成元数据，供后续的差异感知存储（Diff-Aware Storage）使用。 Collective KV Cache reuse also produces metadata that Diff-Aware Storage later consumes. 复用路径会记录组成员、各请求累计的偏差分数，以及被选为 Master 的请求。 The reuse path records the group membership, the accumulated per-request deviation scores, and the request chosen as the Master. Master 在语义上并无特殊之处。 The Master is not semantically special. 它只是恢复结果最接近组内共同结构的请求，通常是与共享块的总偏差最小的请求。 It is simply the request whose recovered result is closest to the group’s common structure, typically the one with the lowest total deviation from the shared blocks. 选择合适的 Master 可以尽量减少差异感知存储必须为其余请求保留的稀疏修正数据量。 Selecting a good Master minimizes the size of the sparse corrections that Diff-Aware Storage must keep for the remaining requests. 因此，复用计划充当了本小节的计算优化与下一小节的存储优化之间的桥梁。 The reuse plan therefore serves as the bridge between the compute optimization in this subsection and the storage optimization in the next.

4.3. 差异感知存储4.3. Diff-Aware Storage
集体 KV 缓存复用消除了冗余计算，但并未消除冗余存储。 Collective KV Cache reuse removes redundant compute, but it does not remove redundant storage. 一轮复用完成后，系统仍为每个请求保留一份稠密 KV 缓存。 After reuse completes for one round, the system still holds one dense KV Cache per request. 这会造成浪费，因为同一 All-Gather 轮次中的请求共享大部分逻辑块，仅在私有历史和少量位置敏感更新上存在差异。 This is wasteful because the requests in one All-Gather round share most of their logical blocks and differ only in a private history and a small number of position-sensitive updates. 如果系统完整存储每个恢复结果，就只是将冗余从预填充计算转移到了内存容量占用上。 If the system stores every recovered result in full, it merely shifts redundancy from prefill compute to memory capacity.
这一问题在多智能体服务中尤为突出，因为轮次会反复进行，而智能体状态在各轮之间始终保持活跃。 This problem is especially acute for multi-agent serving because rounds repeat and agent states stay live across rounds. 在一个由 $N$ 个智能体运行 $R$ 轮的系统中，若为每个智能体在每一轮都存储一份完整缓存，内存消耗将按 $O(N\times R)$ 增长。 In a system with $N$ agents running over $R$ rounds, storing one full cache per agent per round leads to memory consumption that grows as $O(N\times R)$ . 如果系统存储大量近乎重复的 KV 缓存（KV Cache），内存压力就会迅速上升，活跃智能体的数量也会随之减少。 If the system stores many near-duplicate KV Caches, memory pressure rises quickly and the number of active agents falls. 因此，存储必须利用与复用所利用的相同的 All-Gather 结构：同一轮中的请求在结构上相似，仅在一组可预测的位置上存在差异。 Storage must therefore exploit the same All-Gather structure that reuse exploits: the requests in a round are structurally similar and differ only at a predictable subset of positions.
主副本—镜像（Master-Mirror）布局。 Master-Mirror Layout. TokenDance 使用 Master-Mirror 布局来压缩每一轮的缓存集合，如图 8 所示。 TokenDance uses a Master-Mirror layout to compress the per-round cache family, as shown in Figure 8. 差异感知存储（Diff-Aware Storage）保留一份稠密缓存作为 Master，并将其余每份缓存存储为仅包含其与该 Master 之间差异的 Mirror。 Diff-Aware Storage keeps one dense cache as the Master and stores each remaining cache as a Mirror that contains only the difference from that Master. 适配器将集合式 KV 缓存复用的复用计划传递到存储路径，使存储层预先知道应将哪个请求作为 Master，以及每个 Mirror 中哪些位置存在差异。 The adapter forwards the reuse plan from collective KV Cache reuse into the store path, so storage already knows which request should become the Master and which positions differ in each Mirror. 当没有显式复用计划可用时，例如某个请求在已识别的 All-Gather 轮次之外到达，后端会回退到基于词元相似度的启发式方法，从现有缓存条目中寻找可复用的 Master。 When no explicit reuse plan is available—for example, when a request arrives outside a recognized All-Gather round—the backend falls back to a token-similarity heuristic to find a reusable Master among existing cached entries.
块稀疏差分表示。 Block-Sparse Diff Representation. Mirror 的修正量以块稀疏 K/V 差分的形式存储。 The Mirror correction is stored as a block-sparse K/V diff. 恢复后的各份缓存之间的差异集中在一部分词元位置上，这些位置的值因私有上下文或依赖位置的 RoPE 旋转而发生了变化。 The differences among recovered caches are concentrated in a subset of token positions whose values changed because of private context or position-dependent RoPE rotation. 这些存在差异的位置往往聚集成连续的块，对应于私有历史片段或共享块之间的边界区域。 These differing positions tend to cluster in contiguous blocks that correspond to the private history segment or to the boundary regions between shared blocks. 块粒度表示能够捕捉这种聚集特征，其元数据开销远低于细粒度的逐元素差分。 A block-granular representation captures this clustering with much lower metadata cost than a fine-grained element-wise diff. 它也与现代服务引擎采用的基于块的内存管理，以及第 4.4 节所述的按分块对齐的恢复流水线自然契合。 It also aligns naturally with the block-based memory management used by modern serving engines and with the tile-aligned restore pipeline described in Section 4.4.
读取时，存储层不会立即重建稠密的 Mirror 张量。 On read, the storage layer does not eagerly rebuild a dense Mirror tensor. 相反，它会返回一个轻量级镜像对象，其中保留了对 Master 的引用和稀疏差分元数据。 Instead, it returns a lightweight mirror object that keeps a reference to the Master and the sparse diff metadata. 这既为调用方保留了标准的逻辑 KV 缓存抽象，又将物化推迟到运行时实际需要数据之时。 This preserves a standard logical KV Cache abstraction for the caller while delaying materialization until the runtime actually needs the data. Mirror 仅占完整缓存的 10–20%，因此系统可以立即节省内存，而恢复开销则延后至执行时才产生。 The Mirror occupies only 10–20% of a full cache, so the system saves memory immediately without paying the restore cost until execution time.
这种布局的效果取决于提示中共享部分与私有部分各自所占的比例。 The strength of this layout depends on how much of the prompt is shared versus private. All-Gather 模式天然适合这种布局，因为上一轮的共享输出块占据了提示的主要部分，只有私有历史和本轮任务是每个智能体独有的。 The All-Gather pattern is a natural fit because the shared output blocks from the previous round dominate the prompt, and only the private history and round task are unique per agent. 如果请求之间的差异更大，例如在某个系统中，每个智能体接收到的共享输出子集差别显著，那么 Mirror 的修正量就会增大，存储收益也会随之降低。 If requests diverge more strongly—for example, in a system where each agent receives a substantially different subset of the shared outputs—then the Mirror corrections grow larger and the storage benefit diminishes. 我们在第 6.4 节中对这一关系进行量化。 We quantify this relationship in Section 6.4.

4.4. 融合式差分恢复4.4. Fused Diff Restore
只有在关键路径上的恢复开销保持较低时，压缩才有价值。 Compression is useful only if restore stays cheap on the critical path. 一种朴素的 Mirror 恢复方法会加载完整的 Master，将其复制到新缓冲区，再覆盖存在差异的块，这会为一个系统从不保留的对象额外增加一次稠密数据先写后读的往返。 A naive Mirror restore would load the full Master, copy it into a new buffer, and overwrite the differing blocks—adding an extra dense write-then-read round trip for an object the system never keeps.
TokenDance 通过在现有的逐层传输路径内部应用稀疏修正来消除这一开销，该路径本就负责将缓存的 KV 数据移入分页 GPU 内存。 TokenDance eliminates this overhead by applying the sparse corrections inside the layerwise transfer path that already moves cached KV data into paged GPU memory. 算法 1 展示了这一过程。 Algorithm 1 shows the procedure. 两个 GPU 缓冲区以乒乓方式交替承担角色：一个接收来自存储的 Master 数据块，另一个则进行原地修正和写回。 Two GPU buffers alternate roles in a ping-pong fashion: one receives Master chunks from storage while the other undergoes in-place correction and writeback. 在每一层，该路径都会应用块稀疏差分（第 8 行）、恢复 RoPE 位置（第 10 行），并将结果写入分页 KV 缓存内存（第 11 行），所有操作都在普通缓存加载本就执行的同一遍处理中完成。 At each layer, the path applies the block-sparse diff (line 8), recovers RoPE positions (line 10), and writes the result into paged KV Cache memory (line 11)—all within the same pass that ordinary cache loads already perform. 整个过程中都不会单独物化出稠密的 Mirror。 No separate dense Mirror is ever materialized.

总体而言，差分感知存储与融合恢复共同解决了扩展问题中内存方面的挑战。 Taken together, diff-aware storage and fused restore address the memory side of the scaling problem. 存储机制减少了每增加一个智能体所带来的内存占用。 Storage reduces how much state each additional agent contributes to the memory footprint. 融合恢复确保这种压缩在在线执行期间仍然可用，而非仅适用于静态存储。 Fused restore ensures this compression remains usable during online execution rather than only at rest. TokenDance 正是通过这种方式，将 All-Gather 模式固有的结构相似性转化为本地 GPU 上更高的活跃智能体承载能力。 This is how TokenDance turns the structural similarity inherent in the All-Gather pattern into higher active-agent capacity on local GPUs.

5. 实现5. Implementation
TokenDance 基于 LMCache 和 vLLM 实现。 TokenDance is implemented on top of LMCache and vLLM. 我们在四个部分中新增了约 3K 行 Python 代码和 500 行 CUDA/C++ 代码：轮次感知的分段索引、集合式 KV 缓存复用、差分感知存储以及融合稀疏恢复。 We add approximately 3K lines of Python and 500 lines of CUDA/C++ across four parts: round-aware segment indexing, collective KV Cache reuse, diff-aware storage, and fused sparse restore.
轮次感知的分段索引。 Round-Aware Segment Indexing. 应用程序按照第 4.1 节所述，在逻辑块之间插入 <TTSEP> 分隔符。 The application inserts <TTSEP> separators between logical blocks as described in Section 4.1. 在运行时侧，我们将固定大小的分块哈希表替换为基于分段的哈希表，后者在分隔符边界处切分提示词，并对每个片段独立建立索引。 On the runtime side, we replace the fixed-size chunk hash table with a segment-based hash table that splits prompts at separator boundaries and indexes each segment independently.
集合式 KV 缓存复用。 Collective KV Cache Reuse. vLLM V1 适配器在每个调度步骤中扫描请求，并将每组请求分派到第 4.2 节所述的集合式处理路径。 The vLLM V1 adapter scans requests in each scheduler step, and dispatches each group to the collective path described in Section 4.2. 在内部，KV Collector 为每个请求创建一个计算生成器和一个检索生成器，并驱动它们逐层同步推进。 Internally, the KV Collector creates one compute generator and one retrieval generator per request and drives them in lockstep across layers.
差分感知存储。 Diff-Aware Storage. 我们新增了一个差分感知后端，对常规 LMCache 存储后端进行封装。 We add a diff-aware backend that wraps the normal LMCache storage backend. 当存在可用的复用计划时，存储路径会利用该计划选择 Master，并直接确定 Mirror 的位置。 When a reuse plan is available, the store path uses it to select the Master and identify Mirror positions directly. 当没有可用的复用计划时，后端会回退到基于 token 相似度的启发式方法。 When no reuse plan is available, the backend falls back to a token-similarity heuristic. Master 分块按原样写入。 Master chunks are written unchanged. 每个 Mirror 分块都被序列化为块稀疏的 K/V 差分：后端记录涉及的块索引，以及这些块的 K/V 修正值。 Each Mirror chunk is serialized as a block-sparse K/V diff: the backend records the touched block indices and the K/V correction values for those blocks. 当 K 和 V 两个平面涉及相同的块时，实现会让二者共享块索引列表，以减少元数据大小。 When both K and V planes touch the same blocks, the implementation shares the block-index list between them to reduce metadata size. 读取时，后端返回一个轻量级镜像对象，而非稠密张量，将实体化操作推迟到恢复路径中执行。 On read, the backend returns a lightweight mirror object rather than a dense tensor, deferring materialization to the restore path.
融合稀疏恢复。 Fused Sparse Restore. 我们扩展了 GPU 连接器的逐层乒乓传输路径，使其能够识别镜像对象。 We extend the GPU connector’s layerwise ping-pong transfer path to recognize mirror objects. 连接器将 Master 分块加载到其临时缓冲区，合并当前层的稀疏差分元数据，并在 RoPE 恢复和分页内存写回之前，调用成对的 K/V 差分内核进行原地更新。 The connector loads Master chunks into its temporary buffer, merges the sparse diff metadata for the current layer, and invokes a paired K/V diff kernel in place before RoPE recovery and paged-memory writeback. CUDA 扩展提供了两个内核：一个用于单个 KV 平面，另一个用于同时更新 K 和 V。 The CUDA extension provides two kernels: one for a single KV plane and one that updates K and V together. 当稀疏元数据对齐良好时，使用成对内核；否则，连接器会回退到稠密恢复。 The paired kernel is used when the sparse metadata is well aligned; otherwise the connector falls back to dense restore. 如第 4.4 节所述，目前融合发生在注意力计算之前的传输流水线中，而非注意力分块加载器内部。 As discussed in Section 4.4, fusion currently occurs in the transfer pipeline before attention, not inside the attention tile loader.

LLM 推理服务系统。vLLM (Kwon et al., 2023)、SGLang (Zheng et al., 2024)、Orca (Yu et al., 2022) 和 Sarathi-Serve (Agrawal et al., 2024) 改进了 LLM 推理的批处理、调度和内存管理。 LLM Serving Systems. vLLM (Kwon et al., 2023), SGLang (Zheng et al., 2024), Orca (Yu et al., 2022), and Sarathi-Serve (Agrawal et al., 2024) improve batching, scheduling, and memory management for LLM inference. 这些系统针对单个请求优化执行，但未利用 TokenDance 所针对的轮次级 KV 缓存冗余。 These systems optimize execution for individual requests but do not exploit the round-level KV Cache redundancy that TokenDance targets.
以请求为中心的 KV 缓存复用。 Request-Centric KV Cache Reuse. 当新请求与已存储序列具有完全相同的前缀时，SGLang (Zheng et al., 2024) 和 vLLM (Kwon et al., 2023) 中的前缀缓存机制会复用已缓存的状态。 Prefix caching in SGLang (Zheng et al., 2024) and vLLM (Kwon et al., 2023) reuses cached state when a new request shares an exact prefix with a stored sequence. TokenDance 的不同之处在于将智能体轮次作为复用单元：它在一轮中的所有智能体之间共享复用操作，并压缩这种集体执行所产生的 KV 缓存集合。 TokenDance differs by treating the agent round as the reuse unit: it shares reuse work across all agents in a round and compresses the resulting set of KV Caches that this collective execution produces.

HCache (Gao et al., 2025)、InfiniGen (Lee et al., 2024)、CacheGen (Liu et al., 2024a)、MoonCake (Qin et al., 2024) 和 CachedAttention (Gao et al., 2024) 通过重计算、卸载、压缩或解耦来降低长上下文推理服务的成本。 HCache (Gao et al., 2025), InfiniGen (Lee et al., 2024), CacheGen (Liu et al., 2024a), MoonCake (Qin et al., 2024), and CachedAttention (Gao et al., 2024) reduce the cost of long-context serving through recomputation, offloading, compression, or disaggregation. 这些方法针对的是单个缓存。 These methods target individual caches. TokenDance 则利用同一轮次中同级缓存之间的相似性。 TokenDance instead exploits similarity across sibling caches from the same round. Master-Mirror 布局和融合差分路径围绕跨缓存冗余进行设计，而非仅针对单个缓存的压缩。 The Master-Mirror layout and fused diff path are designed around cross-cache redundancy rather than single-cache compression alone.

TokenDance 与这些方法正交：它首先消除同级缓存之间的重复数据，随后还可以在此基础上对各个缓存进行压缩。 TokenDance is orthogonal: it removes the duplicated data across sibling caches first, and per-cache compression can be applied on top.

8. 结论8. Conclusion
我们提出了 TokenDance，这是一个通过集体式 KV Cache 共享来扩展多智能体 LLM 推理服务规模的系统。 We presented TokenDance, a system for scaling multi-agent LLM serving through collective KV Cache sharing. 该设计基于两项核心观察。 The design follows two core observations. 现有复用方法在智能体轮次场景中效率较低，而且即使进行了轮次级 KV Cache 复用，所得 KV Cache 仍具有很高的可压缩性。 Current reuse methods are inefficient for agent rounds, and even after round-level KV Cache reuse the resulting KV Caches remain highly compressible. TokenDance 将这些观察转化为一种渐进式设计，包含集体式 KV Cache 复用、Master-Mirror 存储和融合式差分检索。 TokenDance turns these observations into a progressive design with collective KV Cache reuse, Master-Mirror storage, and fused diff retrieval. 在具有代表性的多智能体工作负载上，与启用前缀缓存的 vLLM 相比，它将端到端延迟最多降低至原来的 $2.3\times$ 分之一，并将 KV Cache 存储占用减少 $94\%$。 On representative multi-agent workloads, it reduces end-to-end latency by up to $2.3\times$ and KV Cache storage by $94\%$ compared to vLLM with prefix caching.
更广泛地说，我们的工作主张，通信结构应成为 LLM 推理服务中的一等概念。 More broadly, our work argues that communication structure should become a first-class concept in LLM serving. All-Gather 模式是一个自然的起点，因为它已出现在许多智能体工作负载中。 The All-Gather pattern is a natural starting point because it already appears across many agent workloads. 随着智能体系统持续多样化，其他反复出现的通信模式很可能也会带来类似的优化机会。 As agent systems continue to diversify, other recurring communication patterns will likely expose similar opportunities. 能够感知通信模式的推理服务栈，对于使未来的多智能体平台在大规模运行时保持高效至关重要。 A communication-pattern-aware serving stack will be important for making future multi-agent platforms efficient at scale.
