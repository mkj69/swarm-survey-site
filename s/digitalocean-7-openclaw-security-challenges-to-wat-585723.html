一句话

这篇厂商博客提示：扩大 agent 部署时，权限、凭证、技能供应链与共享平台的安全治理，会成为与算力同样需要考虑的约束；但它没有测量 swarm 的规模收益或风险增长曲线。

主要内容

  • 文章发表于 2026 年 2 月 27 日，由 DigitalOcean 发布、Fadeke Adegbuyi 撰写，将风险归为七类：远程代码执行、实例暴露、恶意技能、凭证明文存储、持久记忆中的提示注入、企业未经批准的部署，以及 Moltbook 数据库暴露。
  • 核心问题是权限集中：agent 能执行命令、访问文件、控制浏览器并连接通信平台，一旦入口或技能被攻破，影响便可能延伸到这些资源。
  • 文中以 CVE-2026-25253 说明网页如何通过 WebSocket 来源校验缺失窃取令牌并取得执行能力，同时称该问题已在 2026.1.29 版本修复。早期默认配置与后续修复应分开看。
  • 持久记忆使恶意指令可能跨会话保留、延迟触发；技能市场则把安装扩展变成引入第三方可执行行为的过程。
  • 建议集中于隔离运行、限制权限、网关认证、补丁、技能审查和凭证轮换。文章同时推广 DigitalOcean 的部署服务，具有明确商业目的。

证据与可信度

  • 本文属于二手厂商汇编，并非统一实验。所给内容未展示原始扫描数据、完整方法或独立复核结果。
  • “超过 30,000 个互联网暴露实例”归于 SecurityScorecard；暴露数量不能直接当作已遭入侵数量。
  • Koi 的统计为 2,857 个技能中发现 341 个恶意技能；Bitdefender 的另一项扫描称接近 900 个、约占 20%。两者样本范围与时间未交代清楚，不能合并或直接比较。
  • “22%”指 Token Security 企业客户中存在员工未经批准运行 OpenClaw 的客户比例，不代表全部企业或员工。
  • Moltbook 的 150 万个 API 令牌、35,000 个邮箱归于 Wiz 的发现；这些是记录数量，不能等同于独立用户数或已被接管的 agent 数。
  • 开篇“512 个漏洞、其中八个严重”缺少方法说明；云部署的安全优势也主要由服务提供方自述。

对 swarm scaling 的意义

  • 共享技能、凭证和平台可能形成共同故障点：增加 agent 数量的同时，也扩大了同一缺陷可能触达的范围。
  • 扩容需要同步设计权限边界、凭证分离、技能准入与统一更新；仅把 agent 搬到云端，仍无法消除恶意技能和提示注入。
  • 这份材料适合作为规模化部署的风险清单，不能证明风险随 agent 数量线性或超线性增长，也不能用于比较不同 swarm 架构的性能。
