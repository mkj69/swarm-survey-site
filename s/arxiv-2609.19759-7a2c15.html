一句话

多 agent 的收益取决于任务能否有效拆分：长流程、稀疏依赖更有利于协作，紧密串联的任务则可能被协调成本拖累。

主要内容

  • 作者把执行轨迹建模为依赖图，用“桥边”连接可分离的子任务，将编排问题理解为执行过程中预测拆分边界。
  • 理论分析认为，若提前知道完整轨迹并正确拆分，可以降低累计上下文成本；这一结论不直接等于实际运行中更省 token 或表现更好。
  • 提出的 SAIGE 根据执行反馈按需创建子 agent，并在需要时检索依赖信息，避免提前固定整个协作结构。
  • 作者报告：在 Terminal Bench 2.1、NL2Repo Bench 这类密集依赖任务上，通用多 agent 方法弱于单 agent，SAIGE 大致持平；在 Deep Research Bench II、AgentIF-OneDay 这类稀疏依赖任务上，拆分更有收益。
  • 消融实验的文字结论是：扩大 agent 数量、增加递归深度通常带来更多 token 消耗，性能却不稳定增长。失败分析将紧耦合协作的问题归为等待、依赖循环和资源冲突等局部死锁。

对 swarm scaling 的意义

这份材料支持把扩容单位从“agent 数量”转向“可独立执行的任务边界”。工程上可据此优先采用按需分工、有限上下文交接和依赖检索，并同时观察任务得分与总 token。

其证据尚不能推出普遍最优的 swarm 规模：实验集中于单一基础模型，且缺少可见的完整结果表。更稳妥的判断是，任务依赖结构应成为扩容前的判断依据，规模增长本身不是能力增长的保证。
