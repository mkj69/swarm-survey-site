一句话

Crabbox 把并行编码的扩展问题从“多开 agent”推进到“隔离运行环境、自动验证并提交证据”，但材料没有证明它能提高多少合并吞吐。

主要内容

  • 作者认为，并行 agent 增多后，瓶颈会转向 PR 的验证与合并；让 agent 提供测试结果、截图和录像，可以为人工审查提供依据。
  • Git worktree 只隔离代码副本。多个会话仍可能争用数据库、端口、Docker daemon 和本机资源，一个迁移操作就可能影响其他会话。
  • Crabbox 为每个 worktree 配置独立云沙箱，承载各自的数据库和开发服务。流程覆盖启动、同步代码、执行测试、上传证据及销毁环境。
  • 关键设计是执行命令前同步本地未提交的改动，让 agent 修改后继续在云端测试，减少临时提交及重建环境的需要。
  • 文章还推广 AI Builder Club 的开源插件，将环境配置与 agent 工作循环打包；演示采用 Daytona，提供商可以配置。

证据与可信度

  • 作者称自己通常同时运行至少十个会话，并转述 Peter 展示过十五个以上并行会话的截图。这些属于个人经验及截图描述，不是受控扩展实验，也不能等同于有效任务吞吐。
  • 功能说明主要来自文章所述的演示视频和项目仓库。本文仅依据所给材料，未独立核验代码、视频或实际运行结果。
  • “数秒内重测”、快速启动及生产使用等说法缺少测试条件、统计结果和对照数据。材料没有提供成本、失败率、合并耗时或吞吐曲线。
  • 文章同时销售课程和会员服务，具有推广属性；其架构分析可供参考，性能及可靠性判断仍需实测。

对 swarm scaling 的意义

这份材料强调了一个有用的区分：代码隔离与运行时隔离是两层扩展条件。只增加 agent 和 worktree，并不能消除共享服务造成的相互干扰。

独立沙箱与验证证据可以支撑更多任务同时测试，也可能减少人工重复验证的负担。但测试通过不代表多个 PR 合并后仍然兼容，截图也不能覆盖全部正确性。材料提出了扩展基础设施的路径，尚未证明端到端交付能力会随 agent 数量增长。
