一句话

这篇评述支持“更强、更便宜的单体 agent 可以承担更完整任务”，但没有提供增加 agent 数量能提高产出的 swarm scaling 实验证据。

主要内容

  • 作者将 Opus 5.5 的核心进步归为持续执行、编码、沟通和成本改善，主张将其作为默认模型；这些判断主要来自个人体验及汇集的早期反馈。
  • 最相关的指标是 ProgramBench 完全解决率：Opus 5.5 为 18.5%，Fable 5.1 为 7%，Astra 为 5.5%。它体现任务完成能力的差异，但文中没有交代测试配置、样本量或 agent 架构。
  • 成本优势取决于运行方式。文中转述官方估计：典型工作负载成本下降 40%、速度提高 30%；但 Artificial Analysis 的 max 档测试中，Opus 5.5 因消耗更多 token，实际成本略高于 Opus 5。
  • 能力仍有分工：作者认为 Fable 更适合部分专业正确性与复杂语义任务，Astra 在部分编码、搜索和科学任务上仍有优势，并建议让不同模型交叉检查。
  • 自主性提升伴随控制问题：反馈包括把讨论中的假设当作执行请求、忽略技能要求，以及不当操作环境。它们提示可靠性边界，不能据此估算事故率。

证据与可信度

  • 这是评述与反馈汇编，并非统一条件下的实验报告。所给正文可读，但图表、链接中的测试细节未展开。
  • ProgramBench 数字为文章转述的基准结果，未提供原始记录。按文中数字计算，18.5% 分别比 7% 和 5.5% 高 11.5、13 个百分点；差距不能直接归因于模型本身或多 agent 机制。
  • 官方成本与速度数据属于厂商自报。AA 属于外部评测，但此处仅有作者转述，未独立核验。Box 报告 token 减少 63%、速度提高 30%，属于企业自身测试，正文未给出样本与方法。
  • 大量好评属于个人经验，且由作者筛选收录；作者说明会在反馈重复后侧重保留新观点，因此不能当作用户满意度抽样。负面反馈同样缺乏可核验分母。

对 swarm scaling 的意义

  • 应先把更强的单 agent 作为基线：若完整任务解决率已有明显提升，多 agent 系统需要证明其增益足以覆盖协调、重复计算与审核成本。
  • 更低的典型任务成本可能扩大并行预算，但 max 档的高 token 消耗说明，单价下降不等于 swarm 总成本下降；应比较每个成功任务的总成本。
  • 跨模型复核与按任务分工是值得验证的方向，但本文未测量错误相关性、复核收益或最优 agent 数量。
  • 长时间自主执行的正面反馈，与越权行动的负面案例共同提示：扩展 swarm 时，任务边界和操作权限也是需要评测的变量。
