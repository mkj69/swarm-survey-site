并行编程智能体的协调验证：NP-Bench 与调度规划器Verifying Coordination in Parallel Coding Agents: NP-Bench and a Scheduling Planner
摘要Abstract
一个编程智能体团队中的每个智能体单独看来都可能表现良好，但团队整体仍可能失败：每个智能体都通过了自己的测试，合并后的结果却无法正常工作，而单智能体评估永远无法发现这一问题。 A team of coding agents can look fine agent by agent and still fail as a team: each one passes its own tests while the merged result is broken, and single-agent evaluation never catches it. 团队越来越多地在同一个代码库上并行运行多个 LLM 编程智能体，而这些智能体会相互干扰：两个智能体重写同一个函数，一个智能体基于队友刚刚修改的接口契约交付代码，等到工作全部完成后，集成却失败了。 Teams increasingly run several LLM coding agents in parallel on the same codebase, and the agents get in each other’s way: two rewrite the same function, one ships against a contract a teammate just changed, and integration fails after the work is already done. 大多数协调工具以被动响应的方式处理这一问题（监测冲突，然后发出警告），但在智能体运行速度下的并发场景中，警告到达时，无效的编辑早已发生。 Most coordination tools treat this reactively (watch for a conflict, then warn), but under agent-speed concurrency the warning arrives after the wasted edit. 我们认为，将这一问题表述为调度问题更为合适：获取每个工作项声明的作用范围，将工作划分为互不重叠的范围，并沿着生产者 $\rightarrow$ 消费者依赖图安排合并顺序，所有这些都预先完成。 We argue the problem is better posed as scheduling: take each work item’s declared scope, partition the work into disjoint scopes, and order merges along the producer $\rightarrow$ consumer dependency graph, all up front. 我们将这一规划器集成到 Nerveplane 这一面向编程智能体的本地优先系统中，并使用 NP-Bench 对其进行评估；NP-Bench 是一个以实际环境为依据、包含三个实验组（无协调、被动检测、主动规划）的基准，通过真实的 git 合并验证集成结果，评估既采用确定性模拟，也使用实际运行的智能体。 We build this planner into Nerveplane, a local-first system for coding agents, and evaluate it with NP-Bench, an environment-grounded, three-arm benchmark (no coordination; reactive detection; proactive planning) that verifies integration outcomes off a real git merge, both as a deterministic simulation and with live agents. 在确定性评估中，规划器将无故障集成成功的场景数从 1/9 提升至 9/9，并将合并冲突数从 13 降至 0；其优势随智能体数量的增加而扩大。 Deterministically, the planner lifts clean-integration success from 1/9 to 9/9 scenarios and drives merge conflicts from 13 to 0; its advantage grows with the number of agents. 在实际运行的智能体处理破坏兼容性的契约变更时，规划器实现了两种基线在所有随机种子下都未能实现的结果：无协调和被动检测下均为 0 的无故障集成率，在使用规划器后，前沿模型上升至 1.0，小型模型上升至 0.6，同时智能体遵守了分配给它们的作用范围（5 个智能体中无一越界）。 With live agents on a breaking contract change, the planner rescues an outcome that both baselines miss on every seed: a clean-integration rate of 0 under no-coordination and under reactive detection rises to 1.0 with the planner on a frontier model, and to 0.6 on a small one, while agents respect their assigned scopes (none of 5 strayed). 一项独立的记忆实验结果表明，在强模型和弱模型上，重复犯错率均从 1.00 降至 0.00：在一个会话中记录的决策能够阻止后续会话中的智能体重复犯下同一错误，这种信息效应无法通过任何程度的模型能力提升来替代。 A separate memory result collapses the repeated-mistake rate from 1.00 to 0.00 on both a strong and a weak model: a decision recorded in one session stops an agent in a later session from repeating it, an information effect no amount of model strength substitutes for. 我们也报告了未能奏效的做法：在内容能够容纳于上下文窗口的规模下，将事实路由给智能体并不能改善长上下文中的检索准确率；其价值在于成本和容量，而非注意力。 We also report what did not help: at window-fitting scales, routing facts to agents does not rescue retrieval accuracy over long contexts; its value is cost and capacity, not attention. 在方法论上，NP-Bench 也充当了一个以实际环境为依据的多智能体编程验证器：每个智能体都通过了自己的检查，集成后的系统却仍可能无法正常工作，而真实的合并与测试能够揭示这一问题。 Methodologically, NP-Bench doubles as an environment-grounded verifier for multi-agent coding: each agent passes its own checks, yet the integrated system can still be broken, and a real merge-and-test reveals it. 在我们测试的两个能力层级和两家供应商的模型中，这一收益并未随模型能力增强而减小，因为它源于工作的分配方式，而非模型的推理能力。 Across the two capability tiers and two vendors we tested, the benefit did not shrink as models got stronger, because it comes from how work is allocated rather than from model reasoning.
1 引言1 Introduction
运行一个编程智能体现已成为常规做法；同时运行多个智能体则是团队正在迈向的方向。 Running one coding agent is now routine; running several at once is where teams are headed. 工作树多路复用工具为每个分支启动一个智能体，CI 流水线将问题分发给智能体池，而单个开发者也可以同时监督多个智能体。 Worktree multiplexers spin up an agent per branch, CI pipelines fan issues out to a pool of agents, and a single developer can supervise a handful of them at a time. 一旦如此，瓶颈便不再是某个智能体编写代码的能力有多强，而是这些智能体是否会相互干扰。 Once that happens, the bottleneck stops being how well any one agent writes code and starts being whether the agents step on each other. 两个智能体编辑同一个文件并产生合并冲突；一个智能体重命名 API 中的某个字段，另一个却仍按照旧结构编写代码，集成后得到的结果虽然合并无冲突，却无法正常工作；上午作出的决策，到了下午又被一个从未见过该决策的智能体重新争论。 Two agents edit the same file and produce a merge conflict; one agent renames a field in an API while another codes against the old shape and integrates to something that merges cleanly but is broken; a decision made in the morning is re-litigated in the afternoon by an agent that never saw it. 这些都是协调失败，而且会随智能体数量的增加而增多。 These are coordination failures, and they scale with the number of agents.
目前主流的应对方式是被动响应。 The prevailing response is reactive. 协调层监测潜在问题（编辑范围重叠、契约发生变更），并在观察到变更后向受影响的智能体发出警告。 A coordination layer watches for trouble (overlapping edits, a changed contract) and warns the affected agent once the change is observed. 这与数十年来开发者“工作空间感知”（workspace awareness）工具 [3] 背后的理念相同，而且对于以小时为工作时间尺度的人类而言确实有用。 This is the same idea behind decades of developer “workspace awareness” tools [3], and it is genuinely useful for humans who work on the scale of hours. 但智能体的工作时间尺度是秒。 But agents work on the scale of seconds. 等到队友的编辑被感知到、警告被传递过去时，收到警告的智能体往往已经写出了存在冲突的代码。 By the time a teammate’s edit has been sensed and a warning routed, the warned agent has often already written the conflicting code. 此时，警告带来的只是事后清理，而非事前预防。 The warning then buys a cleanup, not a prevention.
本文采取了不同的立场：并行编程智能体之间的协调是一个调度问题。 This paper takes a different stance: coordination among parallel coding agents is a scheduling problem. 在智能体开始工作之前，获取每个工作项声明的作用范围，对工作进行划分，使并发运行的智能体具有互不重叠的作用范围，并沿着生产者 $\rightarrow$ 消费者依赖图安排合并顺序，确保修改契约者的变更先于使用该契约者的变更合入。 Before the agents start, take each work item’s declared scope, partition the work so that concurrently-running agents have disjoint scopes, and order the merges along the producer $\rightarrow$ consumer dependency graph so that whoever changes a contract lands before whoever consumes it. 被动检测器只能在事后告知智能体出现了问题，而调度则通过其构造方式预防问题的发生。 Where a reactive detector can only tell an agent it has a problem after the fact, a schedule prevents the problem by construction.
一个显而易见的反对意见是：“互不重叠的作用范围不会产生冲突”是一句同义反复。 There is an obvious objection: “disjoint scopes don’t conflict” is a tautology. 但这一反对意见实际上正是研究问题的另一种表述。 But that objection is the research question in disguise. 调度只有在以下条件成立时才有帮助：(a) 输入的作用范围准确；(b) 智能体确实遵守分配给它们的作用范围。 A schedule helps only if (a) its input scopes are accurate and (b) the agents actually respect the scopes they are handed. 本文中的作用范围是预先声明的（由每个工作项所述的文件及其使用的契约给出），因此我们假定 (a) 成立，并测量 (b)：即使被告知不要修改某个文件，智能体仍可能编辑它，而实际运行实验检验的正是它是否遵守要求。 In this paper the scopes are declared (given by each work item’s stated files and consumed contracts), so we assume (a) and measure (b): an agent told to stay out of a file may edit it anyway, and whether it complies is exactly what the live experiments check. 自动推断作用域是一个尚未解决的问题，我们指出了这一点，但并未加以解决。 Inferring scopes automatically is an open problem we flag but do not solve. 贡献在于对遵从程度的测量，而不在于这一同义反复。 The contribution is the compliance measurement, not the tautology.
这一测量中隐藏着一个验证问题。 There is a verification problem hiding in that measurement. 协调层是否确实有帮助，不能由智能体自行报告，单智能体评估也无法揭示这一点：在各自的分支上单独检查时，每个智能体看起来都是正确的；只有在分支集成时，问题才会显现。 Whether a coordination layer actually helps is not something an agent can self-report, and it is invisible to single-agent evaluation: each agent, checked on its own branch, looks correct; the breakage surfaces only when the branches are integrated. 要回答这一问题，需要一个以实际环境为依据的验证器，从真实的集成过程中读取真实基准信号（合并后的代码树能否构建、能否通过测试、使用方是否已适应新的契约），而不是相信任何智能体的说法。 Answering it takes an environment-grounded verifier that reads ground-truth signals (does the merged tree build, does it pass, did the consumer adapt to the new contract) off a real integration rather than trusting any agent’s word. NP-Bench 就是这样的验证器，其三组实验设计将“协调是否有帮助”从一种断言转变为可测量的问题。 NP-Bench is that verifier, and its three-arm design turns “did coordination help” from an assertion into a measurement.
我们提出四项主张，并为每项主张提供数据支持。 We make four claims and back each with data.
一个验证基准。 A verification benchmark. NP-Bench 对三个实验组（无协调 C0、反应式检测 C1-detect、主动式规划 C1-plan）进行评分，既采用确定性方式，也使用来自两个模型系列的实际运行智能体，从真实合并中读取真实基准集成信号，衡量 SWE-bench 等单智能体基准未能测量的协调维度（第 5 节）。 NP-Bench scores three arms (no coordination C0, reactive detection C1-detect, proactive planning C1-plan) both deterministically and with live agents from two model families, reading ground-truth integration signals off a real merge, the coordination axis that single-agent benchmarks like SWE-bench do not measure (Section 5). 我们将其定位为一项聚焦于协调何时有帮助的研究，而非一个综合性基准。 We present it as a focused study of when coordination helps, not a comprehensive benchmark.
一种形式化表述和一个规划器。 A formulation and a planner. 我们将协调形式化为互不相交的作用域划分与拓扑合并排序，并实现了一个小型、确定性的静态规划器（第 4 节）。 We cast coordination as disjoint-scope partitioning plus topological merge ordering, and implement a small, deterministic static planner (Section 4).
研究结果与坦诚的能力分析。 Results with an honest capability analysis. 在所评估的场景中，规划器严格优于两个基线；对实际运行的智能体而言，含糊的反应式警告几乎等同于没有警告；我们还区分了效果中在所测试的各能力层级上均成立的部分，以及随能力而变化的部分（第 6 节和第 8 节）。 In the evaluated scenarios, the planner strictly dominates both baselines; a vague reactive warning is worth about as much as nothing to a live agent; and we separate the part of the effect that holds across the tested capability tiers from the part that varies with capability (Sections 6 and 8).
未能奏效的尝试。 What did not work. 我们曾试图证明，将事实信息路由给智能体能够挽救长上下文中的检索准确率，但未能成功；我们报告了这一负面结果，以及在此过程中发现的测量缺陷（第 7 节）。 We tried to show that routing facts to agents rescues retrieval accuracy over long contexts and could not; we report that negative result and the measurement bug we caught along the way (Section 7).
2 相关工作2 Related work
多智能体 LLM 框架。Multi-agent LLM frameworks.
第一波系统通过角色和消息来编排多个 LLM 智能体：AutoGen 在群聊管理器的管理下组合可对话智能体 [18]；MetaGPT 运行一家由 SOP 驱动的智能体“软件公司” [9]；ChatDev 构建了一个由聊天驱动的开发组织 [17]；CAMEL 和 AgentVerse 研究角色扮演与涌现的多智能体行为 [13, 5]。 A first wave of systems orchestrates several LLM agents through roles and messages: AutoGen composes conversable agents under a group-chat manager [18]; MetaGPT runs an SOP-driven “software company” of agents [9]; ChatDev structures a chat-driven development organization [17]; CAMEL and AgentVerse study role-play and emergent multi-agent behavior [13, 5]. 这些系统按角色分工，并通过对话进行协调。 These divide labor by role and coordinate through dialogue. 它们都未提供调度保证，无法确保并发编辑的智能体不会因共享文件或过时的契约而发生冲突。 None offers a scheduling guarantee that concurrently-editing agents will avoid colliding on shared files or stale contracts. 本文的规划器与这些框架互为补充：它接收此类框架生成的工作项，并在执行前计算互不相交的作用域划分和合并顺序。 The planner here is complementary: it takes the work items such a framework produces and computes a disjoint-scope partition and merge order before execution. 我们关注的是底层机制（谁可以修改什么，以及按什么顺序修改），而不是角色层或对话层。 We target the substrate (who may touch what, and in what order), not the role or dialogue layer.
编码智能体基准。Coding-agent benchmarks.
编码智能体的评估主要关注单智能体在单个代码仓库中的任务成功率：SWE-bench 以解决真实的 GitHub 问题为任务 [11]，SWE-agent 研究推动此类问题解决的智能体与计算机交互接口 [19]，而 HumanEval [4] 和 LiveCodeBench [10] 等执行基准则对生成的代码进行评分。 Evaluation of coding agents is dominated by single-agent, single-repository task success: SWE-bench resolves real GitHub issues [11], SWE-agent studies the agent-computer interface that drives such resolution [19], and execution benchmarks like HumanEval [4] and LiveCodeBench [10] score generated code. 这些基准都不衡量并行工作的 $N$ 个智能体能否顺利完成集成。 None measures whether $N$ agents working in parallel integrate cleanly. NP-Bench 恰好补充了这一维度（并发智能体的无冲突合并成功率、无效工作量和作用域遵从程度），并且与单项任务的解决情况相互独立。 NP-Bench adds exactly that axis (clean-merge success, wasted work, and scope compliance for concurrent agents) and is orthogonal to per-task resolution.
冲突检测与开发者协调。Conflict detection and developer coordination.
通过监测并行编辑来主动预测合并冲突，是软件工程领域长期以来的一条研究路线 [3]。 Proactively predicting merge conflicts by watching parallel edits is a long line in software engineering [3]. 这是 C1-detect 实验组的思想源头：它有价值，但属于反应式机制：只有观察到变更后才会触发警告，而在智能体速度的并发执行下，此时往往已经产生了无效编辑。 This is the intellectual ancestor of the C1-detect arm: valuable, but reactive: the warning fires once a change is observed, which under agent-speed concurrency is frequently after the wasted edit. 我们通过实证表明，主动式调度优于反应式检测，而对于实际运行的智能体而言，含糊的反应式警告与无协调几乎没有区别。 We show empirically that a proactive schedule dominates reactive detection, and that a vague reactive warning is close to no coordination for a live agent.
调度与依赖感知排序。Scheduling and dependency-aware ordering.
将协调视为调度，使其与经典的任务图研究联系起来：依赖 DAG 的拓扑排序 [12]，以及划分/着色子问题的 NP 难性 [7]。 Framing coordination as scheduling connects to classic task-graph work: topological ordering of a dependency DAG [12] and the NP-hardness of the partitioning/coloring subproblem [7]. 软件结构映射团队结构，这是 Conway 的观察 [6]；而向并发工作中增加人员（或智能体）会提高协调成本，这是 Brooks 的观察 [2]。 That software structure mirrors team structure is Conway’s observation [6], and that adding people (or agents) to concurrent work raises coordination cost is Brooks’s [2]. 我们将互不相交的划分与拓扑合并相结合的方法应用于 LLM 智能体声明的代码作用域，而本文研究的新实证问题是：智能体是否会遵守由此产生的任务分配。 We adapt disjoint-partition-plus-topological-merge to the declared code scopes of LLM agents, where the novel empirical question studied here is whether agents will respect the resulting assignments. 自动推断这些作用域仍有待未来研究。 Inferring those scopes automatically remains future work.
智能体协议与记忆。Agent protocols and memory.
智能体工具正在采用标准化的模型与工具通信协议以及智能体间通信协议——Model Context Protocol [1] 和 Agent2Agent [8]。 Agent tooling is standardizing on protocols for model-to-tool and agent-to-agent communication—the Model Context Protocol [1] and Agent2Agent [8]. Nerveplane 通过 MCP 提供协调接口，同时补上了这些协议尚未解决的一环：路由什么、路由给谁，以及按什么顺序路由。 Nerveplane exposes its coordination surface over MCP but adds the missing piece those protocols leave open: what to route, to whom, and in what order. 在记忆方面，MemGPT [15] 和生成式智能体（generative agents）[16] 等系统使智能体能够在自身任务中进行长期回忆。 On memory, systems such as MemGPT [15] and generative agents [16] give an agent long-term recall within its own task. 我们的记忆实验结果具有跨会话和跨智能体的特性：一个会话记录的决策能够防止后续会话中的智能体重犯错误，而且我们将其分离为一种信息效应，该效应在强模型和弱模型上同样成立。 Our memory result is cross-session and cross-agent: a decision recorded by one session prevents an agent in a later session from repeating a mistake, and we isolate it as an information effect that holds equally on strong and weak models.

3 协调平面3 The coordination plane
规划器并非在真空中运行；它需要知道有哪些智能体、它们正在修改什么，以及各项服务之间如何相互依赖。 The planner does not run in a vacuum; it needs to know what agents exist, what they are touching, and how services depend on one another. Nerveplane 提供了这一基础。 Nerveplane supplies that substrate. 它是一个面向编码智能体的本地优先系统：每台机器运行一个守护进程，使用一个 SQLite 存储，并通过 MCP 暴露一组工具（register、sync、publish、decision、discover、chat、memory 和 task）；规划器在守护进程内部运行，并通过 register/sync 向各个智能体下发任务分配。 It is a local-first system for coding agents: a single per-machine daemon, a SQLite store, and a set of tools exposed over MCP (register, sync, publish, decision, discover, chat, memory, and task); the planner runs inside the daemon and delivers each agent’s assignment through register/sync. 它不依赖特定的智能体：Claude Code、Codex 和 OpenCode 均通过同一套接口连接。 It is agent-agnostic: Claude Code, Codex, and OpenCode all connect through the same surface.
对协调而言，关键的设计选择在于：守护进程主动观测状态，而不是等待状态被告知。 The design choice that matters for coordination is that the daemon observes state rather than waiting to be told about it. 被动感知循环会轮询每个已注册智能体的 git 工作树，并在已更改文件集合实际发生变化时发出事件，因此协调从不依赖于智能体记得通报自己的工作。11 1 该系统和 NP-Bench 测试框架均为开源（Nerveplane v0.17.0）。 A passive sensing loop polls each registered agent’s git worktree and emits an event when the changed-file set actually changes, so coordination never depends on an agent remembering to announce its work.11 1 The system and the NP-Bench harness are open source (Nerveplane v0.17.0). 随后，路由引擎决定哪些对象需要获知某项变更：受影响任务的负责人、同一代码仓库中的其他智能体，以及通过服务图识别出的、位于其他代码仓库中且使用已变更 API 契约的智能体。 A routing engine then decides who needs to hear about a given change: the owner of an affected task, other agents in the same repository, and, through a service graph, agents in other repositories that consume a changed API contract. 需要持久保存的项目决策存放在独立于聊天历史的可查询账本中，而跨智能体记忆（默认基于关键词，也可选择基于语义）使一个会话中学到的事实能够在另一个会话中再次被检索出来。 Durable project decisions live in a queryable ledger separate from chat history, and a cross-agent memory (keyword by default, optionally semantic) lets a fact learned in one session resurface in another. 图 1 概述了这一循环。 Figure 1 sketches the loop.

4 将协调视为调度4 Coordination as scheduling
模型。Model.
令 $W$ 为一组工作项。 Let $W$ be a set of work items. 每个工作项 $w$ 都有一个声明的范围 $\sigma(w)$——即它将写入的文件（或符号）集合——以及一组它所使用的契约。 Each item $w$ has a declared scope $\sigma(w)$ —the set of files (or symbols) it will write—and a set of contracts it consumes. 当两个工作项的范围相交时，它们就会发生冲突，即 $\sigma(w_{i})\cap\sigma(w_{j})\neq\varnothing$。 Two items conflict when their scopes intersect, $\sigma(w_{i})\cap\sigma(w_{j})\neq\varnothing$ . 当 $w_{j}$ 使用了 $w_{i}$ 产出的契约时，即 $w_{i}$ 的范围与 $w_{j}$ 所使用的集合重叠时，工作项 $w_{j}$ 依赖于 $w_{i}$（边 $w_{i}\!\rightarrow\!w_{j}$）。 Item $w_{j}$ depends on $w_{i}$ (edge $w_{i}\!\rightarrow\!w_{j}$ ) when $w_{j}$ consumes a contract that $w_{i}$ produces, i.e. $w_{i}$ ’s scope overlaps $w_{j}$ ’s consumed set. 一个计划将 $W$ 划分为若干批次，每个批次内各工作项的范围两两不相交，同时包含一个遵循依赖边的合并顺序 $\pi$。 A plan is a partition of $W$ into batches whose members have pairwise-disjoint scopes, together with a merge order $\pi$ that respects the dependency edges.
命题（适用范围受假设限制）。Claim (assumption-scoped).
如果声明的范围准确，且依赖关系构成有向无环图（DAG），那么，范围互不重叠的划分加上拓扑合并顺序，就能从构造上保证结构性冲突为零：并发运行的工作项绝不会修改同一个文件，且任何使用方都不会先于其提供方被合并。 If the declared scopes are accurate and the dependency relation is a DAG, then a disjoint-scope partition plus a topological merge order yields zero structural conflicts by construction: concurrently-running items never touch the same file, and no consumer is merged before its producer. 反应式检测器无法作出这一保证，因为它只有在感知到冲突之后才会采取行动。 A reactive detector cannot make this guarantee because it acts only after a collision has been sensed. 范围的准确性通过人工声明的输入予以假定；智能体是否遵守范围，则是第 6 节通过实证测量的未知因素。 Scope accuracy is assumed through the hand-declared inputs; agent scope-compliance is the empirical unknown measured in Section 6.
算法。Algorithm.
算法 1 是静态规划器。 Algorithm 1 is the static planner. 它构建依赖图，标记不得按其朴素方案进行编辑的工作项（原因是它们争用已有归属的文件，或使用了其他工作项产出的契约），采用带有确定性破环机制的 Kahn 算法 [12] 计算稳定的拓扑顺序，并通过对范围重叠图进行贪心着色，将工作项划分为可并行执行的批次。 It builds the dependency graph, marks items that must not take their naive edit (either because they contend for an owned file or because they consume a produced contract), computes a stable topological order by Kahn’s algorithm [12] with deterministic cycle breaking, and greedily colors the scope-overlap graph into parallel batches. 求解精确的最小着色是 NP-hard [7]；该贪心遍历是一种已明确说明的近似方法，足以满足该测试套件的需求。 Exact minimum coloring is NP-hard [7]; the greedy pass is a documented approximation and is enough for the suite. 所有平局均按输入顺序打破，因此给定输入始终会产生相同的计划，这是实验可复现的必要条件。 Every tie breaks on input order, so a given input always yields the same plan, a requirement for reproducible experiments. 工作项的任务分配（其范围、合并顺位，以及在被重新分配时提供的便于人类理解的原因）会在 register/sync 时下发给智能体。 The item’s assignment (its scope, merge slot, and a human-readable reason when it was reassigned) is delivered to the agent at register/sync time.

5 NP-Bench5 NP-Bench
NP-Bench 比较三个实验组。 NP-Bench compares three arms. C0 表示无协调：各智能体在行动时对彼此的行为一无所知。 C0 is no coordination: agents act blind to one another. C1-detect 表示反应式协调：当感知到的队友变更涉及某个智能体关注的文件时，该智能体会收到警告；对于实际运行的智能体，警告被刻意设计得较为模糊（“一名队友可能正在编辑 $X$ ”），因为现实中的即时警告就是这种形式。 C1-detect is reactive coordination: an agent is warned when a teammate’s sensed change touches a file it cares about, and (for live agents) the warning is deliberately vague (“a teammate may be editing $X$ ”), because that is what a realistic just-in-time warning looks like. C1-plan 是主动式规划器：在开始之前，智能体会收到允许或禁止修改的范围；如果它是契约的消费方，则会收到确切的契约迁移内容，以及在生产方合并后按照新结构编写代码的指令。 C1-plan is the proactive planner: before starting, an agent receives either an allowed/forbidden scope or, for a contract consumer, the exact contract migration and an instruction to code against the new shape after the producer merges. 该计划还提供合并顺序。 The plan also supplies the merge order. 因此，实际运行比较评估的是时机、信息具体程度、范围分配和合并顺序的综合作用，而非单独考察其中某个组成部分。 Thus the live comparison evaluates the combined effect of timing, information specificity, scope assignment, and merge ordering rather than isolating any one component.
该测试套件分两个层级运行。 The suite runs at two tiers. 层级 A 是确定性模拟，在脚本化场景中驱动真实产品的基础功能——智能体注册、工作树感知、冲突检测和规划器核心——并通过真实的 git 集成操作对结果评分。 Tier A is a deterministic simulation that drives the real product primitives—agent registration, worktree sensing, conflict detection, and the planner core—over scripted scenarios, and scores the result with a real git integration. 当且仅当智能体及时收到警告（C1-detect）或被规划器重新分配任务（C1-plan）时，它才执行协调后的编辑；否则，它执行未经协调的朴素编辑。 An agent takes its coordinated edit exactly when it was warned in time (C1-detect) or reassigned by the planner (C1-plan); otherwise it takes its naive edit. 层级 A 被纳入 CI 门禁，且可复现。 Tier A is CI-gated and reproducible. 层级 B 用实际运行的智能体替代模拟智能体：在每个实验组中，真实的编码智能体在隔离的 git 工作树中以无头模式运行，其分支通过真实的合并操作进行集成，随后对结果评分。 Tier B replaces the simulated agents with live ones: real coding agents run headless in isolated git worktrees under each arm, their branches are integrated with a real merge, and the outcome is scored. 层级 B 具有非确定性，且需要花费资金，因此不作为 CI 门禁。 Tier B is nondeterministic and costs money, so it is not a CI gate.
我们报告以下指标。 We report the following metrics. CTSR（干净工作树成功率，clean-tree success rate）是既能无冲突合并、又能通过集成后验收检查的运行次数所占的比例。 CTSR (clean-tree success rate) is the fraction of runs that both merge without conflict and pass a post-integration acceptance check. 合并冲突数和浪费的代码行数（LOC）分别统计 git 冲突的数量，以及冲突编辑中必须返工的代码行数。 Merge conflicts and wasted LOC count git conflicts and the lines in conflicting edits that must be reworked. 范围越界率是被重新分配任务的 C1-plan 智能体中，编辑了被明确告知不得编辑的文件的智能体所占的比例；0 表示完全遵守要求。 Scope-leakage is the fraction of reassigned C1-plan agents that edited a file they were told not to; 0 means full compliance. 消费方适配率是扇出消费方中，合并后的代码使用了新契约字段的消费方所占的比例。 Consumer-adaptation rate is the fraction of fan-out consumers whose merged code uses the new contract field. 重复错误率等于一减去对先前会话中已记录决策的遵守率。 Repeated-mistake rate is one minus adherence to a prior session’s recorded decision. 合并顺序正确性用于检查每个生产方是否都排在其消费方之前。 Merge-order correctness checks that every producer is ordered before its consumers.
实际运行涵盖两个模型家族：能力差异显著的两个 Claude 模型——一个前沿模型（Claude Opus 4.8, claude-opus-4-8）和一个小型模型（Claude Haiku 4.5, claude-haiku-4-5）——以及 OpenAI 的 Codex（gpt-5-codex）。 Live runs span two model families: two Claude models of very different capability—a frontier model (Claude Opus 4.8, claude-opus-4-8) and a small one (Claude Haiku 4.5, claude-haiku-4-5)—and OpenAI’s Codex (gpt-5-codex). 两个 Claude 模型用于区分协调带来的作用与模型自身能力带来的作用；第二家供应商的模型则用于检验该效果是否只是 Claude 特有的现象。 The two Claude models separate what coordination does from what raw capability does; the second vendor’s model checks that the effect is not a Claude-specific quirk. 实际运行的样本量较小（每个实验单元有 $K\!=\!3$ – $15$ 个随机种子，关键契约实验单元为 $K{=}15$）；我们报告 Wilson 95% 区间，并将样本量较小的实验单元视为先导实验（第 9 节）。 Live sample sizes are modest ( $K\!=\!3$ – $15$ seeds per cell, the pivotal contract cell at $K{=}15$ ); we report Wilson 95% intervals and treat the smaller cells as pilots (Section 9).

6.3 记忆连续性：一种与能力无关的效应6.3 Memory continuity: a capability-independent effect
上述结果涉及工作分配。 The results above concern work allocation. 另一项独立实验涉及知识。 A separate experiment concerns knowledge. 任何模型，无论多强，都无法回忆起从未被告知的项目特定事实；如果某次会话发现并记录了一个易错点，那么后续会话中的智能体应当不再重复该错误——但前提是记忆将这一发现传递到了后续会话。 No model, however strong, can recall a project-specific fact it was never told; if one session discovers a gotcha and records it, an agent in a later session should stop repeating the mistake—but only if memory carries the discovery across sessions. 我们构建了一个沙箱代码仓库，其中有两个对称的身份验证后端，两者均导出相同的函数，而代码中没有任何地方说明哪一个是获准使用的；这是一项仅保存在记忆中的团队决策。 We built a sandbox repository with two symmetric authentication backends that both export the same function, where which one is sanctioned appears nowhere in the code; it is a team decision that lives only in memory. 会话 1 记录该决策；会话 2（一个全新的会话）被问及应导入哪个后端。 Session 1 records the decision; session 2 (a fresh session) is asked which backend to import. 在前沿模型和 Haiku 上，重复犯错率均从 1.00 降至 0.00（$K{=}5$）。 The repeated-mistake rate falls from 1.00 to 0.00 on both the frontier model and Haiku ( $K{=}5$ ). 由于无法从代码仓库中还原出正确选择，这一差距属于信息差距，而非推理差距，而且无论模型能力强弱，它都以相同方式消除。 Because the correct choice is not recoverable from the repository, the gap is an information gap, not a reasoning gap, and it closes identically regardless of model strength. 原始回复证实了这一点：没有记忆时，智能体称两个后端“确实不分伯仲”，然后进行猜测；有记忆时，它们引用回忆起的政策，并导入获准使用的模块。 The raw replies confirm it: without memory the agents call the two backends “a genuine tie” and guess; with memory they cite the recalled policy and import the sanctioned module.
7 未奏效的尝试7 What did not work
我们最初还假设了第二项结果：将所需事实路由给智能体，能够在冗长且充满干扰的上下文中挽救其准确率，形成一种“注意力挽救”（attention rescue）效应，以补充关于“中间信息丢失”（lost-in-the-middle）的文献 [14]。 We initially hypothesized a second result: that routing a needed fact to an agent would rescue its accuracy over a long, distracting context, an “attention rescue” to complement the lost-in-the-middle literature [14]. 这一假设未得到证实。 It did not hold. 我们仍然报告这一结果，因为它改变了人们对上下文路由所能提出的论断。 We report it anyway, because it changes what one should claim for context routing.
在我们最初测试的适中规模下，无论事实被埋在什么位置，前沿模型都能以 100% 的遵循率将其回忆起来，未出现 U 形低谷。 At the modest scales we first tested, a frontier model recalled a fact buried at any position with 100% adherence, with no U-shaped dip. 随后，我们构建了一项更难的、按规模梯度测试的任务：在膨胀至目标 token 预算的代码库中，单个智能体必须检索出当前的支付契约，该契约埋藏在约 $\sim$ 50% 的深度处，周围有四种作为困难负例的金额数据结构；与之对比的是通过路由提供唯一相关事实（$\sim$ 155 tokens）的方式。 We then built a harder, size-swept test: a single agent must retrieve the current payments contract, buried at $\sim$ 50% depth among four hard-negative money shapes, in a codebase inflated to a target token budget, against routing that delivered the one relevant fact ( $\sim$ 155 tokens). 准确率并未随信息稀释而下降：在 10k、50k 和 100k tokens 的规模下，前沿模型和小模型都能从干扰项中选出当前契约（前沿模型在高达 $\sim$ 280k 的规模下也能做到）。 Accuracy did not degrade with dilution: both the frontier model and the small one picked the current contract over the decoys at 10k, 50k, and 100k tokens (and the frontier model up to $\sim$ 280k). 一个更难的变体要求关联三条事实，并设有具名陷阱，结果仍然相同：即使对于小模型，也没有出现准确率差距。 A still-harder variant requiring a three-fact join with named traps gave the same answer: no accuracy gap opened, even for the small model.
真正存在且幅度很大的差异在于成本和容量。 What is real, and large, is cost and capacity. 路由只需 $\sim$ 155 tokens 即可提供所需事实，而直接塞入单个智能体提示中的内容则达到 10k–280k——每项任务所需的上下文减少了 68 $\times$ 至 1296 $\times$——并且，承载整个微服务世界的单智能体提示（$\sim$ 280k tokens）会直接超出小模型的 200k 上下文窗口（5/5 次失败），而经路由分配给各智能体的提示始终能容纳于窗口内。 Routing delivers the needed fact in $\sim$ 155 tokens versus 10k–280k dumped into a single agent’s prompt—68 $\times$ to 1296 $\times$ less context per task—and the single-agent prompt that carries an entire microservices world ( $\sim$ 280k tokens) overflows the small model’s 200k window outright (5/5 failures), while the per-agent routed prompt always fits. 因此，按代码仓库限定范围并结合路由，带来的是成本和可行性上的优势，而非对准确率的补救；我们据此表述，而不采用证据无法支持的更强论断。 So per-repo scoping plus routing is a cost-and-feasibility win, not an accuracy rescue; we state it that way rather than the stronger claim we could not support.
这里需要补充一项方法说明，因为它是我们信任上述数字的原因。 One methods note belongs here, because it is the reason we trust the numbers above. 早先一次决策遵循测试报告称，前沿模型出现了 70% 对 100% 的效果差异。 An earlier run of the decision-adherence test reported a 70% versus 100% effect on a frontier model. 这其实是评分器造成的假象：一个根据子字符串作出否定判定的正则表达式，将正确回复误判为错误。 It was a scorer artifact: a regular expression that negated on a substring false-flagged correct replies. 采用结构化输出评分并记录原始回复后，这一效果消失了，我们撤回该数字。 Structured output scoring plus raw-reply logging erased the effect, and we retract that number. 这一教训——对结构化字段评分并记录原始回复，而非对自然语言文本进行模式匹配——现已融入测试框架；这也是第 6 节的正向结果依据解析后的产物（实际的导入语句、合并后的字段）评分，而非依据文本中的提及来评分的原因。 The lesson—score structured fields and log raw replies rather than pattern-match prose—is now baked into the harness, and it is why the positive results in Section 6 are scored on parsed artifacts (the actual import line, the merged field) rather than on prose mentions.
8 讨论8 Discussion
实际运行中的契约实验结果清楚地分为两个方面。 The live contract result splits cleanly in two. 协调信号对所测试的各能力层级都有帮助：没有这一信号时，前沿模型、小模型以及另一家供应商的模型全部失败，得分均为 0.00，因为相关事实不在其上下文中，而非超出了它们的推理能力。 The coordination signal helps across the tested capability tiers: without it, a frontier model, a small model, and a second vendor’s model all fail at 0.00, because the fact is absent from their context, not beyond their reasoning. 依据信号采取行动则部分取决于能力：给定相同计划，前沿模型能完美完成适配（1.00），小模型在大多数情况下也能做到（0.60）；其失败可归因于执行能力较弱（一次多余的编辑、一次不完整的迁移），而非信息缺失。 Acting on the signal is partly capability-dependent: given the same plan, the frontier models adapt perfectly (1.00) and the small model most of the time (0.60), with the misses tracing to weaker execution (a stray edit, an incomplete migration) rather than to missing information. 对于担心更强模型会使协调变得不再必要的人而言，这一区分很重要。 That split matters for anyone worried that better models will make coordination unnecessary. 根据这里的证据，信息方面的缺口并未因规模扩大而弥合；执行方面则已经从规模扩大中受益。 On the evidence here the information half is not closed by scale; the execution half already benefits from it.
这也解释了何时反应式检测足够有效，何时又不够。 It also explains when reactive detection is enough and when it is not. 在确定性时序模型中，对于顺序依赖，警告能够及时送达，检测器的表现与规划器相当。 In the deterministic timing model, a warning lands in time on sequential dependencies and the detector matches the planner. 在脚本化的并发争用条件下，警告在编辑之后才到达，因此检测器的表现与无协调情形一致，而其与规划器之间的差距随 $N$ 增大。 Under scripted concurrent contention the warning arrives after the edit, so the detector tracks no-coordination and the gap to the planner grows with $N$ . 在实际运行研究中，时序和信息的具体程度同时发生变化，因此证据支持的是组合式主动干预，而非仅靠调度。 In the live study, where timing and information specificity change together, the evidence supports the combined proactive intervention rather than scheduling alone.
在真值明确无歧义的场景中，验证最为容易，例如形式化证明、竞赛编程以及通过测试套件。 Verification is easiest where ground truth is unambiguous—formal proofs, competitive programming, passing test suites. 多智能体代码集成也是这样的场景：合并后的代码树要么能够构建并通过验收检查，要么不能。 Multi-agent code integration is one more such place: the merged tree either builds and passes its acceptance check or it does not. NP-Bench 利用这一点对协调进行端到端验证——它在真实的 git 集成过程中运行真实智能体，并直接从合并后的代码树中读取真值信号（无冲突合并成功、范围遵循、契约适配、跨会话决策遵循），而不是相信各智能体的自我报告。 NP-Bench exploits that to verify coordination end to end—it runs real agents in a real git integration and reads ground-truth signals (clean-merge success, scope compliance, contract adaptation, cross-session decision adherence) directly off the merged tree, rather than trusting each agent’s self-report. 单智能体验证无法发现协调失败：单独评估时，每个智能体都表现良好；但系统在集成时仍然出了问题。 Coordination failures are invisible to single-agent verification: each agent, judged alone, did fine; the system still broke on integration. 三组实验设计（无干预 / 反应式 / 主动式）使我们能够测量协调层是否有帮助，而非仅仅断言它有帮助，同时，阴性对照组可防止夸大结论。 The three-arm design (nothing / reactive / proactive) lets us measure whether the coordination layer helped instead of asserting it, and the negative arm guards against overclaiming.
9 效度威胁9 Threats to validity
Tier A 对智能体反应进行确定性模拟；它驱动真实的感知、检测、路由和规划器，但智能体的编辑操作本身由脚本预设，因此验证的是机制和路由精度，而非智能体行为。 Tier A is a deterministic simulation of agent reaction; it drives the real sensing, detection, routing, and planner, but the agent edits themselves are scripted, so it validates mechanism and routing precision, not agent behavior. 验证智能体行为正是 Tier B 的用途。 That is what Tier B is for. 实际运行的实验单元覆盖两个模型家族（Claude frontier/Haiku 和 OpenAI Codex），从而防范单一供应商特性造成的假象；关键的契约实验单元以 $K{=}15$ 运行，其中规划器的 Wilson 区间 $[0.80,1.00]$ 与基线的 $[0.00,0.20]$ 清楚分离（Fisher 精确检验 $p<10^{-4}$）。 The live cells span two model families (Claude frontier/Haiku and OpenAI Codex), which guards against a single-vendor artifact, and the pivotal contract cell is run at $K{=}15$ , where the planner’s Wilson interval $[0.80,1.00]$ separates cleanly from the baselines’ $[0.00,0.20]$ (Fisher’s exact $p<10^{-4}$ ). 其余实际运行的实验单元均为 $K{=}5$ 的先导实验，区间更宽，且场景均为手工构建；下一步显然应在每个实验单元中采用更大的 $K$，并覆盖更广泛的场景集。 The remaining live cells are $K{=}5$ pilots with wider intervals, and the scenarios are hand-constructed; larger $K$ across every cell and a broader scenario set are the obvious next runs.
最重要的局限在于范围推断。 The most important limitation is scope inference. 在这些实验中，声明的范围由人工预先设定在测试框架中（各项任务所列的文件及其使用的契约），而非从自然语言任务中推断得出。 In these experiments the declared scopes are hand-seeded in the harness (each item’s stated files and consumed contracts), not inferred from natural-language tasks. 规划器的保证仅在这些作用域可靠的前提下才可靠，而自动推断作用域（根据符号图或服务图）仍是尚未实现的工作，并非已经解决的组件；我们主张的是调度方面的成果，而非自动作用域推断。 The planner’s guarantee is only as good as those scopes, and inferring them automatically (from a symbol graph or the service graph) is unbuilt work, not a solved component; we claim the scheduling result, not automatic scope inference. 作用域越界也是在简单的共享文件案例中测量的；对于更微妙的作用域，越界程度可能更高。 Scope-leakage is also measured on the simple shared-file case; leakage could be higher on subtler scopes. 最后，C1-detect 的警告被刻意设计得较为模糊。 Finally, the C1-detect warning is deliberately vague. 我们认为，这种设计符合实际，而非设置稻草人——反应式系统实际发出的正是即时的“可能有人正在修改 $X$”这类提示——但开展具体程度与时机之间的消融实验（提供详细但较晚的警告）将使比较更加清晰，这是未来的工作。 We argue this is realistic rather than a straw man—a just-in-time “someone may be touching $X$ ” is what reactive systems actually emit—but a specificity-versus-timing ablation (a detailed but late warning) would sharpen the comparison and is future work.

并行编程智能体在集成时发生冲突，而这种冲突是一个调度问题。 Parallel coding agents collide at integration, and that collision is a scheduling problem. 在给定已声明作用域的情况下，围绕这些作用域进行调度（并行工作的作用域互不重叠，生产者先于其消费者合并），就能将冲突清理转变为冲突预防。 Given declared scopes, scheduling around them (disjoint scopes for concurrent work, producers merged before their consumers) turns conflict cleanup into conflict prevention. 在 NP-Bench 上，规划器将确定性无冲突集成的成功率从 1/9 提升至 9/9；在使用来自两家供应商的实际运行智能体时，它成功应对了一项无协调和反应式检测均未能处理的破坏兼容性的契约变更（前沿模型上的表现为 0.00/0.00 $\rightarrow$ 1.00，小型模型上为 0.60），同时智能体遵守各自分配的作用域。 On NP-Bench the planner lifts deterministic clean-integration from 1/9 to 9/9 and, with live agents from two vendors, rescues a breaking contract change that no-coordination and reactive detection both miss (0.00/0.00 $\rightarrow$ 1.00 on the frontier models, 0.60 on a small one), while agents respect their assigned scopes. 跨会话记忆在强模型和弱模型上以相同的效果弥补了重复犯错方面的不足。 A cross-session memory closes a repeated-mistake gap identically on strong and weak models. 我们原本预期，将事实路由给智能体能够挽救长上下文准确率，但在内容可容纳于上下文窗口的规模下并非如此；其价值在于成本和容量。 Routing facts to agents, which we expected to rescue long-context accuracy, does not at window-fitting scales; its value is cost and capacity. 这一收益在我们测试的各个模型上均成立，因为它源于工作分配方式，而非模型推理。 The benefit held across the models we tested because it comes from how work is allocated, not from model reasoning. 尚待解决的问题包括：自动推断作用域而非手动预设作用域、随工作变化重新规划，以及将建议性的作用域转变为强制执行的作用域。 What remains open is inferring scopes automatically rather than hand-seeding them, re-planning as work changes, and moving from advisory scopes to enforced ones.
