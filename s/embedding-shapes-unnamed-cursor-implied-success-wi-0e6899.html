一句话

这篇批评文章指出：Cursor 展示了多 agent 大规模产出代码的能力，却未提供足以复现浏览器可运行状态的证据，不能据此确认工程成果随规模增长。

主要内容

  • Cursor 据称让数百个 agent 并发开发浏览器，接近一周生成逾百万行代码、约千个文件，并强调协作冲突较少。
  • 作者追问的是交付结果：代码能否编译，能否加载简单 HTML，以及展示画面对应哪个可运行版本。
  • 作者报告回查约 100 个提交，未找到能干净编译的版本；近期主分支 CI 也存在失败，包括工作流文件错误。
  • 文章承认 Cursor 没有明确宣称浏览器已经可用。其批评重点是：项目叙述和展示容易让读者推断成功，但缺少可复现演示、构建说明和已知可用提交。

证据与可信度

  • 并发 agent 数量、运行时长、代码行数及文件数均为文章转引的厂商自报，不是作者独立测量的成果指标。
  • 约 100 个提交无法干净编译，属于作者自述的独立复现结果；文中链接了测试提交记录及仓库问题。所示一次编译输出为 34 个错误、94 个警告，不能视为每个提交的统一统计。
  • 本解读仅依据所给正文及修订记录，未独立核验仓库、测试环境或链接内容。抽查范围内失败，不能证明全部历史版本从未成功构建。
  • 作者关于代码缺乏工程设计、agent 似乎未执行编译检查的说法属于判断或推测；编译失败本身不足以证明检查从未运行。

对 swarm scaling 的意义

这份材料提醒研究者区分“协作吞吐量”与“可验证成果”：更多 agent、更多代码和更少合并冲突，并不直接等于系统可用。评估扩展效果应同时给出明确版本、可复现构建和最小功能验证。

它提供了对成功叙事的反证线索，但没有不同 agent 规模下的对照实验，因此不能据此推出 swarm scaling 普遍无效，也无法确定失败来自并发规模、协调机制还是验证流程。
