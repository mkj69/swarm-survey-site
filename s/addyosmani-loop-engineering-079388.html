一句话

Osmani 将“循环工程”概括为让系统持续发现、分派、检查和推进任务；对多智能体扩展而言，关键是把验证、状态管理和人的判断一起纳入循环。

主要内容

  • 工作方式从人逐轮提示，转向人设计能够反复运行的任务系统。作者把它放在单个智能体的运行环境之上，负责触发工作、协调执行并决定下一步。
  • 作者归纳了五类组件：定时自动化负责发现任务，worktree 隔离并行修改，skills 保存项目知识，插件与连接器接入外部工具，子智能体分担探索、实现和检查。另需持久化状态，记录已尝试、已完成及待办事项。
  • 文中的示例循环是：定期读取 CI 失败、问题和近期提交，筛出任务，在独立工作区修复，由另一智能体审查，再创建 PR、更新工单，把无法处理的事项交给人。
  • 作者强调实施者与检查者分离，也将独立检查用于判断停止条件；但自动判定完成仍然需要验证。
  • 风险包括 token 开销、质量下降、人工审查瓶颈，以及人逐渐失去对代码的理解。直接提示智能体仍然有效，作者主张按任务寻找平衡。

证据与可信度

  • 这是一篇实践框架与个人判断文章，没有提供对照实验、成功率、成本统计或随智能体数量变化的性能曲线。
  • “五类组件加持久化记忆”是作者的分类方法，不是实验得出的最优配置。示例流程说明如何组合能力，不能据此认定收益已经得到验证。
  • 关于 Codex 与 Claude Code 功能相近、独立检查更有用等说法，来自作者描述、经验及转引；所给材料中没有独立核验。
  • 元数据记录了 8013 次点赞、2398337 次浏览，只能反映传播情况，不能证明技术效果。

对 swarm scaling 的意义

  • 提供了一个系统层面的扩展框架：增加智能体时，需要同时安排任务入口、工作隔离、共享知识、持久状态和验收机制。
  • worktree 能减少直接文件冲突，但不能消除审查与协调负担；作者明确将人的审查带宽视为并行规模的限制。
  • 分离生成与验证值得作为实验变量，但第二个智能体也增加 token 消耗，材料没有证明其净收益或最佳配比。
  • 对调研仓库，这篇材料适合作为架构与风险清单，不能作为“智能体越多，效果越好”的实证依据。
