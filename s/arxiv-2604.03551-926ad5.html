摘要。Abstract.
软件工程 3.0 标志着软件开发的范式转变，在这一范式下，AI 编码智能体不再只是辅助工具，而是主动的贡献者。 Software Engineering 3.0 marks a paradigm shift in software development, in which AI coding agents are no longer just assistive tools but active contributors. 尽管先前的实证研究已经考察了 AI 辅助开发中的生产力提升和接受模式，但人们对整合智能体生成的贡献所面临的挑战仍缺乏充分理解。 While prior empirical studies have examined productivity gains and acceptance patterns in AI-assisted development, the challenges associated with integrating agent-generated contributions remain less understood. 尤其是，合并冲突作为协作式软件开发的一个基本方面，在这一背景下仍未得到充分探索。 In particular, merge conflicts, a fundamental aspect of collaborative software development, remain underexplored in this context. 本文介绍 AgenticFlict，这是一个收录 AI 编码智能体拉取请求（Agentic PRs）中文本合并冲突的大规模数据集。 In this paper, we present AgenticFlict, a large-scale dataset of textual merge conflicts in AI coding agent pull requests (Agentic PRs). 该数据集包含从 59K+ 个仓库收集的 142K+ 个 Agentic PRs，其中 107K+ 个通过确定性合并模拟得到了成功处理。 The dataset comprises 142K+ Agentic PRs collected from 59K+ repositories, of which 107K+ are successfully processed through deterministic merge simulation. 我们的处理流水线识别出 29K+ 个存在合并冲突的 PR，冲突率为 27.67%，并从这些实例中提取出 336K+ 个细粒度冲突区域。 Our pipeline identifies 29K+ PRs exhibiting merge conflicts, yielding a conflict rate of 27.67%, and extracts 336K+ fine-grained conflict regions across these instances. 我们的初步探索性分析表明，在 AI 生成的贡献中，合并冲突不仅频繁发生，而且往往规模较大，不同智能体之间也存在明显差异，这凸显了更好地理解和管理 AI 辅助软件开发中整合挑战的必要性。 Our preliminary exploratory analysis indicates that merge conflicts are both frequent and often substantial in AI-generated contributions, with noticeable variation across agents, emphasizing the need to better understand and manage integration challenges in AI-assisted software development. 数据集、代码和补充材料可在 zenodo 获取：10.5281/zenodo.19396916 The dataset, code and supplementary materials are available in zenodo: 10.5281/zenodo.19396916

1. 引言1. Introduction
人工智能（AI）编码智能体的兴起正在重塑现代软件开发工作流。 The rise of Artificial intelligence (AI) coding agents is reshaping modern software development workflows. GitHub Copilot (GitHub Copilot, 2025)、OpenAI Codex (OpenAI, 2025)、Claude Code (Anthropic, 2025)、Cursor (Cursor, 2025) 和 Devin (Devin AI, 2025) 等多种 AI 编码工具通过生成代码、提出重构建议，以及日益增多地以拉取请求（PRs）的形式贡献变更，来协助开发者。 Several AI coding tools such as GitHub Copilot (GitHub Copilot, 2025), OpenAI Codex (OpenAI, 2025), Claude Code (Anthropic, 2025), Cursor (Cursor, 2025), and Devin (Devin AI, 2025) assist developers by generating code, suggesting refactorings, and increasingly contributing changes in the form of pull requests (PRs). 这一演进反映了从辅助工具向主动协作的更广泛转变，通常被称为软件工程 3.0 (Hassan et al., 2025; Hassan et al., 2024; Ogenrwot and Businge, 2026b)。 This evolution reflects a broader shift from assistive tooling toward active collaboration, often described as Software Engineering 3.0 (Hassan et al., 2025; Hassan et al., 2024; Ogenrwot and Businge, 2026b). 先前的研究考察了开发者如何与 AI 生成的代码交互，以及这些工具对生产力和软件质量的影响 (Vaithilingam et al., 2022; Li et al., 2025; Vaithilingam et al., 2023; Ogenrwot and Businge, 2025a; Ogenrwot and Businge, 2024)。 Prior work has examined how developers interact with AI-generated code and the impact of these tools on productivity and software quality (Vaithilingam et al., 2022; Li et al., 2025; Vaithilingam et al., 2023; Ogenrwot and Businge, 2025a; Ogenrwot and Businge, 2024). 这些研究凸显了人机协作带来的机遇与挑战。 These studies highlight both the opportunities and challenges associated with human–AI collaboration. 较近期的实证研究已开始考察 AI 辅助环境中的开发效率和代码审查动态 (Vijayvergiya et al., 2024; Ogenrwot and Businge, 2025a; Ziegler et al., 2022)。 More recent empirical research has begun to investigate development efficiency and code review dynamics in AI-assisted settings (Vijayvergiya et al., 2024; Ogenrwot and Businge, 2025a; Ziegler et al., 2022). 然而，协作式软件工程的一个基本方面，即合并冲突，在 AI 生成的贡献这一背景下仍基本未得到探索。 However, a fundamental aspect of collaborative software engineering, namely merge conflicts, remains largely unexplored in the context of AI-generated contributions.
在实践中，由于冲突的存在，在协作环境中整合代码很少能够一帆风顺 (Shen et al., 2023; Ogenrwot and Businge, 2025b; Businge et al., 2022; Businge et al., 2020; Businge et al., 2023)。 In practice, integrating code in a collaborative environment is rarely smooth due to conflicts (Shen et al., 2023; Ogenrwot and Businge, 2025b; Businge et al., 2022; Businge et al., 2020; Businge et al., 2023). 当并发修改影响到相互重叠的代码区域，且 Git 等版本控制系统无法自动协调这些修改时，就会产生合并冲突。 Merge conflicts arise when concurrent modifications affect overlapping regions of code and cannot be automatically reconciled by version control systems like Git. 先前的研究表明，合并冲突会带来大量协调开销，并对开发者的生产力产生负面影响 (Brun et al., 2013; Guimarães and Silva, 2012; Vale et al., 2022; McKee et al., 2017; Owhadi-Kareshk et al., 2019)。 Prior research has shown that merge conflicts introduce substantial coordination overhead and negatively impact developer productivity (Brun et al., 2013; Guimarães and Silva, 2012; Vale et al., 2022; McKee et al., 2017; Owhadi-Kareshk et al., 2019). Brun 等人 (Brun et al., 2013) 表明，在分布式开发环境中，协作冲突发生频繁且代价高昂。 Brun et al. (Brun et al., 2013) demonstrate that collaboration conflicts are frequent and costly in distributed development environments. Gousios 等人 (Gousios et al., 2014) 分析了基于拉取请求的开发工作流，并强调了通过 PR 整合贡献的复杂性。 Gousios et al. (Gousios et al., 2014) analyze pull-based development workflows and highlight the complexity of integrating contributions through PRs. 关于现代代码审查的研究进一步强调，整合阻力会影响审查延迟和决策 (Kononenko et al., 2016; Watanabe et al., 2025)。 Studies on modern code review further emphasize that integration friction influences review latency and decision making (Kononenko et al., 2016; Watanabe et al., 2025).
尽管该领域的实证研究不断增多，但专门针对合并冲突整理的数据集仍然有限。 Despite the growth of empirical research in this area, curated datasets specifically targeting merge conflicts remain limited. 尽管 Shen 和 Meng (2024) 推出了 ConflictBench，作为专门用于研究冲突的基准，但其他现有数据集通常是更广泛的协作开发研究的附带产物 (Ghiotto et al., 2020; Svyatkovskiy et al., 2022; Campos Junior et al., 2022)。 While Shen and Meng (2024) introduced ConflictBench as a dedicated benchmark for studying conflicts, other existing datasets have typically emerged as secondary artifacts of broader studies on collaborative development (Ghiotto et al., 2020; Svyatkovskiy et al., 2022; Campos Junior et al., 2022). 最近，Li 等人 (2025) 推出了 AIDev，这是一个收录涉及五种 AI 编码智能体的 PR（又称 Agentic PRs）、议题和讨论的大规模数据集。 More recently, Li et al. (2025) presented AIDev, a large-scale dataset capturing PRs (a.k.a Agentic PRs), issues, and discussions involving five AI coding agents. 然而，这些数据集未能为文本合并冲突提供明确且可复现的标签；它们优先关注的是接受率、时间动态和仓库的一般特征等指标。 However, these datasets fail to provide explicit, reproducible labels for textual merge conflicts; instead, they prioritize metrics such as acceptance rates, temporal dynamics, and general repository characteristics. Watanabe 等人 (2025) 报告称，超过 1.1% 的 Agentic-PR 拒绝案例是由合并冲突导致的。 Watanabe et al. (2025) report that merge conflicts account for over 1.1% of Agentic-PR rejections. openai/codex-PR#612 提供了一个具体案例，其中该拉取请求因贡献者无法解决合并冲突而被放弃。 A concrete example is observed in openai/codex-PR#612 , where the pull request was abandoned because the contributor was unable to resolve the merge conflict.
研究人员目前缺乏必要的资源，无法研究 AI 编码智能体在协作式软件工程环境中引入的集成摩擦。 Researchers currently lack the necessary resources to study integration friction introduced by AI coding agents in collaborative software engineering environments. 为填补这一空白，我们推出 AgenticFlict，这是一个源自 AIDev 数据集 (Li et al., 2025) 的大规模数据集，收录了 AI 编码智能体拉取请求（PR）中的文本合并冲突。 To address this gap, we introduce AgenticFlict, a large-scale dataset of textual merge conflicts in AI coding agent PRs derived from AIDev dataset (Li et al., 2025). 该数据集包含从 59,412 个仓库中收集的 142,652 个智能体 PR，其中 107,026 个处于开放状态和/或已关闭（未合并）状态的 PR 成功完成了确定性合并模拟。 The dataset comprises 142,652 Agentic PRs collected from 59,412 repositories, of which 107,026 are successfully processed through deterministic merge simulation of open and/or closed (unmerged) PRs. 我们的流水线识别出 29,609 个存在合并冲突的 PR，冲突率为 27.67%，并从这些实例中提取了 336,380 个细粒度冲突区域。 Our pipeline identifies 29,609 PRs exhibiting merge conflicts, yielding a conflict rate of 27.67%, and extracts 336,380 fine-grained conflict regions across these instances. 除二元冲突标签外，AgenticFlict 还提供详细的冲突区域元数据，包括受影响文件的路径、冲突区域及其行级范围。 Beyond binary conflict labels, AgenticFlict provides detailed conflict-region metadata, including affected file paths, conflict regions, and line-level spans. 该数据集涵盖五种不同 AI 编码智能体的贡献，支持对不同智能体的冲突发生率和严重程度进行比较分析。 The dataset spans contributions from five distinct AI coding agents, enabling comparative analysis of conflict prevalence and severity across agents.
据我们所知，AgenticFlict 是首个收录智能体 PR 中文本合并冲突的大规模数据集。 To the best of our knowledge, AgenticFlict is the first large-scale dataset of textual merge conflicts in Agentic PRs. 该数据集可支持多个研究方向，包括：(i) 对 AI 生成代码中合并冲突的发生率及特征开展实证研究；(ii) 对不同 AI 编码智能体的集成行为进行比较分析；(iii) 训练和评估自动冲突检测与解决模型；(iv) 分析拉取请求特征（例如规模、变更文件）与冲突发生可能性或严重程度之间的关系；以及 (v) 对 AI 辅助工作流中用于冲突预测、合并自动化和协作开发支持的工具进行基准评测。 This dataset can support several research directions, including: (i) empirical studies of merge conflict prevalence and characteristics in AI-generated code; (ii) comparative analysis of integration behavior across AI coding agents; (iii) training and evaluation of automated conflict detection and resolution models; (iv) analysis of the relationship between pull request characteristics (e.g., size, files changed) and conflict likelihood or severity; and (v) benchmarking tools for conflict prediction, merge automation, and collaborative development support in AI-assisted workflows.

2. 数据集整理方法2. Dataset Curation Methodology
图 1 概述了用于构建 AgenticFlict 数据集的多阶段工作流。 Figure 1 summarizes the multi-stage workflow used to construct the AgenticFlict dataset. 该流水线包含五个主要阶段：(1) 从 AIDev 数据集中收集智能体 PR，(2) 元数据获取，(3) 仓库准备，(4) 确定性合并模拟，以及 (5) 冲突提取。 The pipeline consists of five main stages: (1) Agentic PR collection from the AIDev dataset, (2) Metadata Retrieval, (3) repository preparation, (4) deterministic merge simulation, and (5) conflict extraction.

步骤 1：拉取请求收集。 Step 1: Pull Request Collection. 我们使用截至 2026 年 1 月 5 日从 Hugging Face 下载的 AIDev 数据集 (Li et al., 2025)。 We use the AIDev dataset (Li et al., 2025) downloaded from Hugging Face as of January 5, 2026. 该数据集包含 932,791 个智能体 PR。 The dataset contains 932,791 Agentic PRs. 在初始预处理步骤中，我们保留处于开放状态的 PR，以及已关闭但没有证据表明已被合并的 PR。 As an initial preprocessing step, we retain PRs that are either open or closed without evidence of having been merged. 当原始状态和合并时间戳可用时，这一筛选会在提取流水线启动前执行；否则，最终判定将推迟至流水线下一步从 GitHub 获取元数据时进行。 When raw state and merge timestamps are available, this filtering is performed before the extraction pipeline begins; otherwise, the final decision is deferred to GitHub metadata retrieval in next step of the pipeline. 这一筛选得到 142,652 个候选 PR。 This filtering yielded 142,652 candidate PRs. 尽管这一设计可能会略微降低数据集的覆盖范围，但它保证了所有保留的记录都对应可验证的 GitHub 产物。 Although this design may slightly reduce dataset coverage, it guarantees that all retained records correspond to verifiable GitHub artifacts. 每个拉取请求由形式为 (owner/repository) 的仓库名称 (repo_full_name) 和拉取请求编号 (pr_number) 标识。 Each pull request is identified by a repository name (repo_full_name), in the form (owner/repository) and a pull request number (pr_number). 我们将二者组合，构建形式为 repo_full_name#pr_number 的规范标识符 (pr_key)，以便在整个流水线中进行一致的跟踪。 We combine these to construct a canonical identifier (pr_key) of the form repo_full_name#pr_number, enabling consistent tracking throughout the pipeline.
步骤 2：元数据获取。 Step 2: Metadata Retrieval. 对于每个拉取请求，我们查询 GitHub GraphQL API (GitHub, Inc., 2026b)，获取仓库和拉取请求的元数据，包括拉取请求状态、时间戳、分支名称，以及基准提交和头部提交的对象标识符 (baseRefOid 和 headRefOid)，这些标识符是合并模拟的主要锚点。 For each pull request, we query the GitHub GraphQL API (GitHub, Inc., 2026b) to retrieve repository and pull request metadata, including the pull request state, timestamps, branch names, and the base and head commit object identifiers (baseRefOid and headRefOid), which serve as the primary anchors for merge simulation. 在大规模处理时，与 GitHub API 的交互会受到若干实际限制。 At scale, interacting with the GitHub API introduces several practical limitations. 具体而言，请求可能因速率限制 (HTTP 403) (GitHub, Inc., 2026c; Cosentino et al., 2017; Kalliamvakou et al., 2014)、暂时性服务器错误（例如 HTTP 502/503），或仓库被删除、访问受限等仓库层面的问题 (HTTP 404/410/451) (Kalliamvakou et al., 2014; Cosentino et al., 2017) 而失败。 In particular, requests may fail due to rate limiting (HTTP 403) (GitHub, Inc., 2026c; Cosentino et al., 2017; Kalliamvakou et al., 2014), transient server errors (e.g., HTTP 502/503), or repository-level issues such as deletion or restricted access (HTTP 404/410/451) (Kalliamvakou et al., 2014; Cosentino et al., 2017). 为应对这些挑战，我们的实现采用延迟逐次增加且次数有限的重试机制来缓解暂时性 API 故障，通过令牌轮换分散请求负载，并对 API 错误代码进行显式处理。 To mitigate these challenges, our implementation employs bounded retries with increasing delays to mitigate transient API failures, token rotation to distribute request load, and explicit handling of API error codes. 尽管采取了这些保障措施，一些 PR 仍因引用永久缺失或仓库无法访问而无法恢复。 Despite these safeguards, some PRs remain unrecoverable due to permanently missing references or inaccessible repositories. 我们识别出 35,626 个此类案例。 We identified 35,626 such cases. 我们使用结构化状态码显式记录其失败类型，并将这些实例排除在后续冲突分析之外，而非默默将其丢弃。 Instead of silently discarding them, we explicitly record failure modes using structured status codes and exclude these instances from downstream conflict analysis.
步骤 3：仓库准备。 Step 3: Repository Preparation. 在进行合并模拟之前，先在本地准备好每个仓库。 Before merge simulation, each repository is prepared locally. 我们使用 Git 的部分克隆（partial clone）机制（Git Project, 2026）将仓库克隆到持久缓存中，该机制会下载仓库历史，同时避免下载不必要的文件 blob 对象。 We clone repositories into a persistent cache using Git’s partial clone mechanism (Git Project, 2026), which downloads repository history while avoiding unnecessary file blobs. 同一仓库的后续 PR 会复用缓存中的克隆，并执行轻量级的 git fetch 以同步仓库状态。 Subsequent PRs belonging to the same repository reuse the cached clone and perform a lightweight git fetch to synchronize the repository state.
对于每个拉取请求，流水线会将工作树重置为干净状态，并检出由 baseRefOid 标识的基准提交。 For each pull request, the pipeline resets the working tree to a clean state and checks out the base commit identified by baseRefOid. 这一准备步骤确保每次合并模拟都从确定的仓库状态开始，并避免先前操作的干扰。 This preparation step ensures that every merge simulation begins from a deterministic repository state and avoids interference from previous operations.
步骤 4：确定性合并模拟。 Step 4: Deterministic Merge Simulation. 算法 1 概述了这一步骤。 Algorithm 1 summarizes this step. 为了确定拉取请求是否会产生文本合并冲突，我们使用 Git 在本地进行合并模拟。 To determine whether a pull request produces a textual merge conflict, we perform a local merge simulation using Git. 根据从 GitHub 获取的基准提交和头部提交的 OID，我们执行以下命令：git merge --no-commit --no-ff <headRefOid>。 Given the base and head commit OIDs retrieved from GitHub, we execute the following command: git merge --no-commit --no-ff <headRefOid>. 如果合并成功完成，则将该拉取请求标记为 merge_clean。 If the merge completes successfully, the pull request is labeled merge_clean. 如果合并失败，仓库将进入冲突状态，随后我们进行冲突提取。 If the merge fails, the repository enters a conflicted state and we proceed to conflict extraction.
模拟过程会因拉取请求的状态而略有不同。 The simulation procedure differs slightly depending on pull request state. 对于处于开放状态的 PR，我们使用 API 返回的当前基准提交和头部提交的 OID 来模拟合并。 For open PRs, we simulate the merge using the current base and head commit OIDs returned by the API. 对于已关闭但未合并的 PR，基准分支可能在关闭后继续推进；因此，我们会重建与拉取请求关闭时仓库状态相对应的基准提交，并基于该快照执行合并。 For closed but unmerged PRs, the base branch may have advanced after closure; therefore, we reconstruct the base commit corresponding to the repository state at the time the pull request was closed and perform the merge against that snapshot. 这一设计近似还原了开发者在关闭拉取请求时可能遇到的合并条件。 This design approximates the merge conditions that developers would have encountered at closure time.
某些合并模拟失败可能是由于仓库已被删除，或由于强制推送或历史重写导致历史提交不再可达（Bird et al., 2009; Businge et al., 2018; Rocha and Businge, 2022）。 Certain merge simulation failures may arise when repositories have been deleted or historical commits are no longer reachable due to force-pushes or history rewrites (Bird et al., 2009; Businge et al., 2018; Rocha and Businge, 2022). 这类情况会被明确标注结构化错误代码，并记录在数据集的运行日志中，使后续分析能够量化合并模拟的覆盖率。 Such cases are explicitly labeled with structured error codes and recorded in the dataset’s run log, allowing downstream analyses to quantify merge simulation coverage.

3.1. 模式概览3.1. Schema Overview
我们介绍图 2 所示的 AgenticFlict 模式。 We describe the schema of AgenticFlict, illustrated in Figure 2. 该模式由五个主要实体组成，下文将逐一说明。 The schema consists of five primary entities, which are explained below. 有关字段定义的更多细节以在线附录的形式提供于复现包中 (Ogenrwot and Businge, 2026a)。 Additional details on field definitions are provided in the replication package as an online appendix (Ogenrwot and Businge, 2026a).
Repository。 Repository. Repository 实体存储数据集中所引用仓库的上下文元数据，包括仓库名称、星标数、派生仓库数、主要编程语言以及仓库状态（例如，已归档或派生仓库）。 The repository entity stores contextual metadata about repositories referenced in the dataset, including repository name, star count, fork count, primary programming language, and repository status (e.g., archived or fork). 将这些信息单独存储，可避免多个 PR 来自同一仓库时产生冗余。 Separating this information avoids redundancy when multiple PRs originate from the same repository.
PullRequest。 PullRequest. PR 实体是数据集的核心组成部分，每个拉取请求（pull request）对应一条记录。 The PR entity is the central component of the dataset and contains one record per pull request. 它存储 GitHub 元数据，例如仓库标识符、拉取请求编号、状态、时间戳以及可合并性信号。 It stores GitHub metadata such as repository identifier, pull request number, state, timestamps, and mergeability signals. 此外，它还记录重建结果，包括是否发生冲突，以及冲突文件数、冲突区域数和冲突总行数等汇总严重程度指标。 In addition, it records reconstruction outcomes, including whether a conflict occurs and aggregate severity metrics such as the number of conflicting files, number of conflict regions, and total conflict lines.
ConflictFile。 ConflictFile. 该实体记录文件级别的冲突信息，并通过 pr_key 与拉取请求实体关联。 This entity captures file-level conflict information and is linked to the pull request entity via pr_key. 每条记录对应一个至少包含一个冲突区域的文件，并包含冲突区域数、冲突总行数、文件扩展名和冲突类型（例如，both-modified、modify/delete）等属性。 Each record corresponds to a file containing at least one conflict region and includes attributes such as the number of conflict regions, total conflict lines, file extension, and conflict type (e.g., both-modified, modify/delete).
ConflictRegion。 ConflictRegion. 提供细粒度的冲突详情。 Provides fine-grained conflict details. 每条记录表示文件中的单个冲突区域，并包含文件路径、区域索引以及行级边界（start_line、mid_line、end_line）。 Each record represents a single conflict region within a file and includes the file path, region index, and line-level boundaries (start_line, mid_line, end_line). 其他属性记录冲突双方各自的规模，以及冲突代码块的紧凑哈希表示。 Additional attributes capture the size of each side of the conflict and compact hash representations of the conflicting code blocks.
ConflictFileCommit。 ConflictFileCommit. 该实体将冲突文件与合并双方各自最近修改这些文件的提交关联起来。 This entity links conflicting files to the commits most recently modifying them on each side of the merge. 对于每个冲突文件，我们记录 head 分支和 base 分支上最后一次修改该文件的提交。 For each conflicting file, we record the last commit touching the file on the head and base branches. 这为冲突变更的来源提供了一种轻量级近似表示，并支持冲突溯源分析。 This provides a lightweight approximation of the origins of conflicting changes and enables analyses of conflict provenance.

5. 相关工作5. Related Work
基于拉取请求的开发与代码审查。 Pull-Based Development and Code Review. 基于拉取请求的开发已成为开源生态系统中占主导地位的贡献模式。 Pull-based development has become the dominant contribution model in open source ecosystems. Gousios 等人 (Gousios et al., 2014) 开展了最早一批针对拉取式模型（pull-based model）的大规模实证研究之一，分析了审查实践、接受率和集成动态。 Gousios et al. (Gousios et al., 2014) conducted one of the first large-scale empirical studies of the pull-based model, analyzing review practices, acceptance rates, and integration dynamics. 后续研究考察了审查质量、审查者行为以及影响拉取请求接受的因素 (Kononenko et al., 2016; Alami and Ernst, 2025; Gonçalves et al., 2025; Göçmen et al., 2025)。 Later work examined review quality, reviewer behavior, and factors influencing pull request acceptance (Kononenko et al., 2016; Alami and Ernst, 2025; Gonçalves et al., 2025; Göçmen et al., 2025). 尽管这些研究为理解协作工作流程提供了宝贵见解，但它们通常不会在提交层面重建合并结果。 While these studies provide valuable insight into collaborative workflows, they typically do not reconstruct merge outcomes at the commit level. 因此，大多数拉取请求数据集并未明确记录文本冲突造成的集成阻力。 As a result, integration friction due to textual conflicts is not explicitly captured in most pull request datasets.
AgenticFlict 通过引入可与审查和接受情况分析相结合的冲突感知元数据，补充了既有的 PR 研究，填补了理解现代自动化贡献和智能体贡献如何影响代码仓库健康状况方面的关键空白 (Watanabe et al., 2025)。 AgenticFlict complements prior PR research by introducing conflict-aware metadata that can be integrated with review and acceptance analyses, filling a critical gap in understanding how modern automated and agentic contributions impact repository health (Watanabe et al., 2025).

协作开发中的合并冲突。 Merge Conflicts in Collaborative Development.
长期以来，合并冲突一直被认为是分布式软件开发中协调开销的重要来源 (Mahmood et al., 2020; Brun et al., 2013)。 Merge conflicts have long been recognized as a significant source of coordination overhead in distributed software development (Mahmood et al., 2020; Brun et al., 2013). 合并冲突的影响超出了单个代码仓库的范围。 The impact of merge conflicts extends beyond individual repositories. 在大型软件生态系统中，结构上的相互关联意味着一个组件中的集成阻力可能广泛传播 (Ogenrwot et al., 2026)，这进一步凸显了系统研究引入冲突的贡献的必要性。 In large software ecosystems, structural interconnectedness means that integration friction in one component can propagate widely (Ogenrwot et al., 2026), reinforcing the need for systematic study of conflict-introducing contributions. Brun 等人 (2013) 表明，协作冲突频繁发生且代价高昂，并提出了早期检测机制以减轻其影响。 Brun et al. (2013) demonstrate that collaboration conflicts are frequent and costly, and propose early detection mechanisms to mitigate their impact. 后续研究分析了大规模代码仓库中合并冲突的原因和特征，强调了并发编辑、文件中心性和开发者协调模式的作用 (Brindescu et al., 2020; Vale et al., 2023)。 Subsequent studies have analyzed the causes and characteristics of merge conflicts in large-scale repositories, highlighting the role of concurrent edits, file centrality, and developer coordination patterns (Brindescu et al., 2020; Vale et al., 2023). 相关研究还探索了冲突预测和预防技术 (Brindescu et al., 2020)。 Research has also investigated conflict prediction and prevention techniques (Brindescu et al., 2020). 这些方法利用历史提交数据、代码所有权和文件修改模式，在合并之前估计发生冲突的可能性。 These approaches leverage historical commit data, code ownership, and file modification patterns to estimate the likelihood of conflicts prior to merging. 然而，现有冲突数据集主要关注人类编写的变更，并未明确考虑 AI 编码智能体生成的贡献，尽管近期证据表明，AI 助手可使提交频率提高约 13.55% (Cui et al., 2026)。 However, existing conflict datasets primarily focus on human-authored changes and do not explicitly consider contributions generated by AI coding agents, despite recent evidence that AI assistants can increase commit frequency by approximately 13.55% (Cui et al., 2026).
AgenticFlict 通过提供一个专门面向智能体 PRS 场景的可复现文本合并冲突数据集，拓展了这一研究方向。 AgenticFlict extends this line of research by providing a reproducible dataset of textual merge conflicts specifically in the context of Agentic PRS.
数据集与基准。 Datasets and Benchmarks. 现有合并冲突数据集大致可分为传统协作基准和新兴的以 AI 为中心的代码仓库。 Existing merge conflict datasets can be broadly categorized into traditional collaborative benchmarks and emerging AI-centric repositories. 传统基准关注大规模的人类编写代码所产生的冲突，例如 Ghiotto 等人 (2020) 研究了 2,731 个基于 Java 的项目，报告称近 20% 的合并需要人工干预；后续对 123 个 Java 项目中冲突结构的分析则揭示，冲突主要集中在共同修改的方法体内 (Accioly et al., 2018)。 Traditional benchmarks focus on human-authored conflicts at scale, such as the 2,731 Java-based projects studied by Ghiotto et al. (2020), reporting that nearly 20% of merges require manual intervention and subsequent analyses of conflict structure in 123 Java Projects, revealing that conflicts are primarily concentrated within shared method bodies (Accioly et al., 2018). 最近，ConflictBench (Shen and Meng, 2024) 被提出，作为专门用于评估合并工具的基准。 More recently, ConflictBench (Shen and Meng, 2024) was introduced as a dedicated benchmark specifically designed to evaluate merge tools. 它提供了一组经过筛选整理的冲突场景，并按编程语言和冲突类型进行分类。 It provides a curated collection of conflicting scenarios, categorized by programming language and conflict type. 类似地，SBCR (Campos Junior et al., 2025) 所使用的数据集等关注冲突解决结果与其父版本之间的文本相似性，为 1,062 个 Java 项目提供了近 10,000 个冲突块。 Similarly, datasets like those used in SBCR (Campos Junior et al., 2025) focus on the textual similarity between conflict resolutions and their parent versions, offering nearly 10,000 conflict chunks for 1,062 Java projects.
随着大语言模型（LLMs）的兴起，以 AI 为中心的数据集应运而生，用于记录开发者与 LLMs 之间的交互。 With the rise of Large Language Models (LLMs), AI-centric datasets have emerged to capture interactions between developers and LLMs. DevGPT (Xiao et al., 2024) 推出了一个数据集，收录了与 GitHub 制品关联的、公开分享的 ChatGPT 对话；随后，PatchTrack (Ogenrwot and Businge, 2025a; Ogenrwot and Businge, 2024) 通过添加更多 PR 扩展了该数据集，以研究 ChatGPT 对拉取请求决策以及开发者与 ChatGPT 对话生命周期的影响。 DevGPT (Xiao et al., 2024) introduced a dataset of shared ChatGPT conversations linked to GitHub artifacts, later extended by PatchTrack (Ogenrwot and Businge, 2025a; Ogenrwot and Businge, 2024) with additional PRs to study the influence of ChatGPT on pull request decision-making and developer-ChatGPT conversation lifecycle. 类似地，AIDev (Li et al., 2025) 提供了一个大规模集合，收录了多个 AI 编码智能体的贡献。 Similarly, AIDev (Li et al., 2025) provides a large-scale collection of contributions from multiple AI coding agents. 尽管这些数据集为理解 AI 生成的贡献如何创建和审查提供了有价值的见解，但它们主要关注接受率和讨论动态等高层次元数据。 While these datasets offer valuable insights into how AI-generated contributions are created and reviewed, they primarily focus on high-level metadata such as acceptance rates and discussion dynamics. 它们没有为文本合并冲突提供明确或可复现的标签，限制了我们系统性量化 AI 生成的变更所引入的集成阻力的能力。 They do not provide explicit or reproducible labels for textual merge conflicts, limiting our ability to systematically quantify the integration friction introduced by AI-generated changes.
6. 有效性威胁6. Threats to Validity
本节讨论可能影响 AgenticFlict 数据集有效性的因素。 In this section, we discuss potential threats to the validity of the AgenticFlict dataset.
首先，冲突检测基于确定性的本地合并模拟，所用提交标识符通过 GitHub GraphQL API 获取。 First, conflict detection is based on deterministic local merge simulation using commit identifiers retrieved via the GitHub GraphQL API. 在某些情况下，由于强制推送或删除等仓库变更，这些引用可能已不再可用。 In some cases, these references may no longer be available due to repository changes such as force pushes or deletions. 我们排除此类 PR，以避免错误的冲突标注，代价是覆盖范围有所缩小。 We exclude such PRs to avoid incorrect conflict labeling, at the cost of reduced coverage.
其次，我们利用 Git 在合并模拟过程中生成的文本冲突标记来捕获合并冲突。 Second, we capture merge conflicts using textual conflict markers produced by Git during merge simulation. 尽管这为集成问题提供了一种一致且广泛使用的代理指标，但它未涵盖逻辑不一致或合并后缺陷等更高层次的冲突形式。 While this provides a consistent and widely used proxy for integration issues, it does not account for higher-level forms of conflict such as logical inconsistencies or post-merge defects. 此外，我们的分析聚焦于处于开放状态以及已关闭（未合并）的 PR，这意味着我们可能遗漏已合并 PR 在其生命周期中曾遇到并解决的冲突。 Furthermore, our analysis focuses on open and closed (unmerged) PRs, which means we may miss conflicts that were previously encountered and resolved during the lifecycle of merged PRs. 我们采用这一设计是出于方法上的考虑：一旦 PR 被合并，Git 就不再保留合并前的冲突状态。 We adopt this design for a methodological reason: once a PR is merged, Git no longer preserves the pre-merge conflict state. 审查过程中出现的所有冲突都已在合并前解决，这意味着仅凭合并提交，无法事后恢复我们所提取的冲突标记、行范围和严重程度指标。 Any conflicts that arose during review were resolved prior to merging, meaning that the conflict markers, line spans, and severity metrics we extract cannot be recovered post-hoc from the merge commit alone. 重建这些信息需要对审查过程中的中间状态进行推测性重放，而我们为保证可复现性，有意避免这样做 Reconstructing them would require speculative replay of intermediate review states, which we deliberately avoid to preserve reproducibility
最后，AgenticFlict 基于 AIDev 数据集构建，因此也继承了其局限性。 Finally, AgenticFlict is constructed on top of the AIDev dataset and therefore inherits its limitations. 具体而言，该数据集聚焦于智能体生成的 PR（Agentic PRS），可能过多地包含积极采用 AI 工具的仓库。 In particular, the dataset focuses on Agentic PRS and may overrepresent repositories that actively adopt AI tools. 因此，我们的研究结果可能无法推广至所有开源项目或工业场景。 As a result, our findings may not generalize to all open-source projects or industrial settings. 扩展数据集以纳入人工编写的 PR 中的合并冲突，是未来工作的一个重要方向。 Extending the dataset to include merge conflicts from human-authored PRs is an important direction for future work. 此外，冲突行为可能因编程语言、仓库规模和开发实践的不同而有所差异。 In addition, conflict behavior may vary across programming languages, repository sizes, and development practices.
