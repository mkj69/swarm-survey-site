一句话

这篇二手解读的核心是：swarm 的扩展收益取决于协调架构，增加 agent 数量和单体能力并不自动带来更好的集体表现。

主要内容

  • 协调能改变搜索方向。 文中转述，漏洞发现实验通过共享论坛、同行评审和仲裁，让中间发现引导后续算力分配，而非仅将代码分片并行扫描。
  • 共享状态限制并行收益。 软件开发实验中的扁平、专家分工和层级团队均未稳定产出高质量软件；划分文件归属能减少冲突，但不能证明形成了有效协作。
  • 同质 agent 可能重复犯错。 相似模型、提示和环境会造成输出趋同，多数投票因而可能放大共同偏差。
  • 局部激励可能损害整体。 抢占任务引发高频轮询；冲突目标下，agent 甚至相互干扰。通信既支持合作，也可能促进串通或传播错误。
  • 作者据此主张，将资源调度、权限、证据溯源和冲突处理纳入系统设计，而不能仅靠角色设定。

证据与可信度

材料包含较完整的解读正文，但它是 Kye Gomez 对 Anthropic 研究的二手技术评论；此处未独立核验原始报告、实验设置或结果。

文中转述：独立搜索以 650 万 token 找到 21 个漏洞；协调配置含 45 个 agent，以 2700 万 token 找到 266 个漏洞，两组重合 12 个。按这些数字计算，漏洞数约为 12.7 倍，token 用量约为 4.2 倍，单位 token 产出约为 3.0 倍。这不是等预算比较，不能将全部差异归因于协调，也不能据此推出 agent 数量的扩展曲线。

其他转述包括：30 个 agent 中有 18 个独立选择同一分支名；任务队列产生约 240 万次请求，仅接受 117 个任务。前者支持行为趋同，尚不直接测量错误相关性；后者说明特定激励与资源约束下的拥塞失败。异构化、信誉机制等则主要是作者提出的设计建议，材料未提供其效果验证。

对 swarm scaling 的意义

这份材料更适合用于整理扩展瓶颈与失败机制，而非证明“规模越大越好”。它提示应区分搜索覆盖的扩展与共享状态下的协作扩展，并同时考察预算、重复计算、通信成本、冲突和错误相关性。真正需要验证的是：新增 agent 是否带来新增证据、搜索覆盖或验证能力，以及这些收益能否抵消协调成本。
