一句话

这是一份单人开发蜂群的实践自述：通过业务编排、隔离执行与自动验收提高交付吞吐，但尚不能证明增加 agent 就能稳定提升质量或商业收益。

主要内容

  • 两层分工：OpenClaw 编排者掌握客户资料、会议记录和历史决策，将需求转成任务；Codex、Claude Code 等执行者主要处理代码。作者把优势归于上下文分配。
  • 隔离与调度：每个执行者使用独立 worktree 和 tmux 会话；确定性脚本每 10 分钟检查会话、PR 与 CI，失败后最多重试 3 次。编排者会根据失败原因修改提示，而非简单重复运行。
  • 交付门槛：PR 需通过 CI、多模型审查，涉及 UI 时还须附截图，之后才通知作者审核。作者称人工审核通常耗时 5—10 分钟。
  • 经验沉淀：系统记录成功提示模式，以 CI、模型审查和人工合并作为反馈，也会从错误监控与会议记录主动生成任务。
  • 资源限制：作者称 16GB Mac mini 同时运行约 4—5 个 agent 就开始遇到内存压力，尤其在并行构建、类型检查和测试时。

证据与可信度

  • 作者报告最近四周平均每天约 50 次提交，单日最高 94 次，并举出 30 分钟产生 7 个 PR 的例子。这些是个人自报；材料未提供可复算的日志、任务规模或对照组，提交数和 PR 数也不等于有效交付量。
  • 月费约 190 美元来自 Claude 约 100 美元与 Codex 约 90 美元相加，未形成包含硬件等支出的完整成本核算。
  • “几乎所有中小任务一次完成”没有样本数和成功率口径；多模型审查效果也是个人判断。材料未给出缺陷率、回滚率或独立质量核验。
  • 128GB 新设备尚未到货，因此不能把采购计划当作扩容效果证据。收入增长与“一人百万美元公司”也缺少量化验证。

对 swarm scaling 的意义

案例提示，扩展蜂群需要同时设计上下文分工、任务隔离、失败恢复和验收流程，单纯增加执行者并不充分。

其具体价值是揭示端到端瓶颈：agent 增多会同步放大构建与测试的内存需求，产出的 PR 仍须经过验收。材料展示了一种可参考的工程组织方式，但没有测出并发数与交付速度、质量之间的关系，无法据此推导线性加速或最佳规模。
