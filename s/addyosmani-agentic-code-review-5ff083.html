一句话

Osmani认为，代码生成提速后，扩展瓶颈转向验证与理解；增加 agent 的收益，取决于审查系统能否承接新增产出。

主要内容

  • 审查强度应由故障影响、代码寿命和共同维护人数决定。个人原型可以依赖测试与轻量审查；长期运行、用户众多的系统需要更多验证层。
  • agent PR 常缺少目标、取舍和验证记录，审查者不得不补做意图重建。作者建议提交时附上决策说明、测试结果及执行证据，并保持改动较小。
  • AI 审查可用于分流和查错，但不能替代人判断需求是否正确、是否遗漏关键行为。作者用 Claude Code 或 Codex 为 PR 排风险优先级，合并决定仍由自己承担。
  • 多审查器的价值在于发现问题的互补性。作者主张高风险改动采用不同特点的审查器，并保留严格 CI、人类把关和抽查。

证据与可信度

  • 文中转述 Faros 对 22,000 名开发者、4,000 个团队的遥测：高 AI 采用伴随审查时长中位数增加 441.5%、零审查合并增加 31.3%。这是观察性关联，不能仅据此认定 AI 导致全部变化；Faros 也有商业利益。
  • GitClear 的约 4 倍原始产出与约 12% 生产率提升采用不同参照：前者比较使用者与非使用者，后者比较使用者自身上一年。不能直接相除得出价值转化率；材料也承认选择偏差。
  • 一位工程师在 146 个 PR 上并行使用四种审查工具，报告 617 个被标记位置中，93.4% 仅被一种工具发现。这支持“标记位置重合低”，但不等于这些发现都是真缺陷，也未证明组合后的净收益。
  • Anthropic 所报“低于 1% 的发现被标为错误”属于厂商内部反馈，不能当作通用准确率。全文同时包含作者个人经验和实践主张；所引研究未在本材料中独立核验，点赞与浏览量也不是效果证据。

对 swarm scaling 的意义

文章提示，swarm 扩容需要同时扩展验证、分流和责任机制，而非只增加执行者。异构审查可能扩大问题覆盖，但低重合本身不足以证明可靠性提升；同类模型还可能共享盲点。

材料中的个人案例以 20—30 个并行 agent、每天约 40 个 PR 展示一种工作方式：人提前写清计划，自动门禁检查，人处理升级问题。这是转述个案，不能外推为团队扩展规律。对 swarm 更有用的启示是：把意图、证据和风险分级纳入交接，并衡量审查负担与实际缺陷，而不只统计 PR 数量。
