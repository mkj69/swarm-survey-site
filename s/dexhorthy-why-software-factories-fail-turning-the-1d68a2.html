一句话

Horthy 主张把人工审查和设计决策前移，用小步可验证的实现控制返工；对 swarm scaling 而言，关键约束可能是人类审查能力，而非代码生成速度。

主要内容

  • 恢复人工质量判断。 作者认为当前模型不足以长期守住代码质量，增加工具约束、生成量或模型评审不能替代人读代码。
  • 分层消除歧义。 产品阶段明确用户问题和成功标准；架构阶段确定服务、接口与数据关系；程序设计进一步落实类型、方法签名、文件布局和调用流程。模型起草，人参与讨论，必要时提前邀请最终 PR 审查者。
  • 按纵向切片推进。 避免依次做完数据库、服务、API、前端才验证。作者更倾向从接口和模拟数据起步，逐步接通前端、服务与数据库，每一步都能实际操作和检查。
  • 按任务复杂度裁剪流程。 简单任务直接交给模型，中等任务合并设计文档，大任务采用完整阶段。作者通常一次交付模型处理 1—3 个切片，边做边审，尽早纠偏。
  • 减少返工比增加 PR 更重要。 作者把低质量提交带来的理解、修改和沟通负担视为效率损耗来源。

证据与可信度

这是带有 HumanLayer 产品推广的实践文章，主要证据是作者的工作经验与流程描述，没有对照实验、样本统计或独立核验。

约 40% 的任务可直接完成或仅需 1—2 轮轻反馈，是作者明确标注的估计；每次审查 100—200 行、分配 1—3 个切片属于个人做法。PR 返工比例 20%、AI 一次生成的 PR 接近 50%，也是经验判断。规划半小时节省数小时审查、提速 2—3 倍均未提供测量方法，后者同时用于产品宣传，不能视为已验证收益。

元数据中的点赞和浏览量只反映传播，不能证明流程有效；文末列出的外部资料也未在本材料中展开验证。

对 swarm scaling 的意义

文章没有比较不同 agent 数量，也未测量并行扩展效率。它提供的是一条值得检验的机制：生成吞吐增加后，需求歧义、设计偏差和人工审查可能限制最终交付速度。

据此推论，扩大 swarm 前，应先明确共享接口、代码结构和验收标准，再让任务以可检查的切片推进。其启发是优化“生成—验证—纠偏”的完整周期；但这种流程能支撑多大规模、是否抵消协调成本，本文没有答案。
