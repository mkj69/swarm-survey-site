单独通过，合并失败：并行 LLM 智能体开发中语义协调的基准评测Passes Alone, Fails Together: Benchmarking Semantic Coordination in Parallel LLM-Agent Development
摘要。Abstract.
并行编码智能体生成的补丁可能单独运行正常，但合并后却出现故障。 Parallel coding agents can produce patches that work alone but fail when merged. 当一个智能体更改了另一个智能体仍在依赖的接口或规则时，就会发生这种情况。 This happens when one agent changes an interface or rule that another agent still relies on. 我们使用语义协调基准 stale 来研究这类故障。 We study these failures with stale, a benchmark for semantic coordination. 我们的评估对每个补丁单独运行以及补丁组合运行时执行相同的测试，仅统计由补丁组合引入的故障。 Our evaluation runs the same tests on each patch alone and on their combination, counting only failures introduced by combining the patches. 我们采用三个层级：包含受控接口变更的合成任务、已合并拉取请求对，以及使用真实 Django 辅助函数构造的任务。 We use three tiers: synthetic tasks with controlled interface changes, pairs of merged pull requests, and constructed tasks that use real Django helpers. 在针对挖掘得到的 417 个 Django 拉取请求对进行的 834 次运行中，修正评分流程后，仅有一次出现了干扰。 Among 834 runs on 417 mined Django pairs, only one showed interference after correcting the grading procedure. 在使用 12 个 Django 辅助函数构造的任务中，97% 的运行出现了干扰。 On constructed tasks using 12 Django helpers, interference occurred in 97% of runs. 一条描述已完成的并发变更的消息使 82% 的运行恢复成功。 A message describing the completed concurrent change recovered 82% of runs. 经过审查的拉取请求中可能很少存在尚未解决的并行变更问题，即使智能体在使用真实代码的受控任务上会失败。 Reviewed pull requests may contain few unresolved parallel changes, even when agents fail on controlled tasks using real code. 构造任务中的故障率并不能估计这类问题在实践中出现的频率。 The constructed failure rates do not estimate how often these problems occur in practice.

1. 引言1. Introduction
并行多智能体系统采用不同的协调模型，包括共享状态、显式编排、异步更新，以及输出在事后合并的隔离工作智能体（Qian et al., 2024; Hong et al., 2024）。 Parallel multi-agent systems use different coordination models, including shared state, explicit orchestration, asynchronous updates, and isolated workers whose outputs are merged afterwards (Qian et al., 2024; Hong et al., 2024). 我们关注一种特定场景：工作智能体在执行任务期间不会收到其他工作智能体的更新。 We focus on a specific scenario where workers do not receive updates from their peers while on the job. 这种场景既可以作为一种完整的工作流程出现，也可以表现为协调系统中暂时的信息缺口。 This scenario can occur as a complete workflow or as a temporary information gap within a coordinated system. 对于相互独立的任务，这种方式高效且无害（Pan et al., 2025; Ogenrwot and Businge, 2026），但当一个补丁依赖于正在被并发修改的接口或不变式时，就存在风险。 It is efficient and harmless for independent tasks (Pan et al., 2025; Ogenrwot and Businge, 2026), but dangerous when one patch depends on an interface or invariant that is being changed concurrently. 此时，每个补丁单独运行都可能通过测试，但组合后却会失败。 Each patch may then pass in isolation while their composition fails. 我们将维护此类并发且相互耦合的变更之间一致性的问题称为语义协调（semantic coordination）。 We call the problem of maintaining consistency across such concurrent, coupled changes semantic coordination.

2. 基准测试设计2. Benchmark Design
任务与评估设置。Tasks and Evaluation Settings.
在挖掘层中，每个实例包含 $N$ 个相关的拉取请求（PR），$\{p_{i}\}_{i=1}^{N}$，并从同一个基础提交 $b$ 出发进行评估。 In the mined tier, each instance contains $N$ related pull requests (PRs), $\{p_{i}\}_{i=1}^{N}$ , evaluated from a shared base commit $b$ . 每个 PR 都提供任务描述、人工参考解决方案和隐藏的标准测试补丁。 Each PR provides a task description, a human reference solution, and a hidden gold test patch. 任务描述取自 issue 或 PR，其中解释解决方案的文本已被移除。 The task description comes from the issue or PR, with text explaining the solution removed. 标准测试编码了预期行为：它们在修复前失败，在修复后通过（从失败到通过的测试，$\mathrm{F2P}_{i}$）。 The gold tests encode the expected behavior: they fail before the fix and pass afterward (fail-to-pass tests, $\mathrm{F2P}_{i}$ ). 我们定义了三种评估设置： We define three evaluation settings:
solo( $p_{i}$ )：一个智能体独立解决 $p_{i}$，生成基线补丁。 solo( $p_{i}$ ): an agent solves $p_{i}$ alone, producing the baseline patch.
blind( $\{p_{i}\}$ )：各智能体在 $b$ 上独立解决分配给自己的任务，看不到其他智能体的修改，随后合并所生成的代码差异。 blind( $\{p_{i}\}$ ): agents solve their assigned tasks independently on $b$ , without seeing the other agents’ changes, and the resulting code diffs are merged.
informed( $p_{\pi(1)},\ldots,p_{\pi(N)}$ )：各智能体按顺序 $\pi$ 工作，每个智能体都能看到之前的智能体已完成的修改。 informed( $p_{\pi(1)},\ldots,p_{\pi(N)}$ ): agents work in order $\pi$ , each seeing the completed edits of earlier agents. 这就是顺序预言机。 This is the sequential oracle.
对于每个实例，我们都评估补丁单独应用（solo）和组合应用（blind）时的表现。 We evaluate patches alone (solo) and together (blind) on every instance. 在合成层中，我们还运行了 informed 条件（§4）。 On the synthetic tier, we also run the informed condition (§4). 已完成的修改为评估协调提供了理想可见性基线。 The completed edit provides an ideal-visibility baseline for evaluating coordination. 遵循 SWE-bench（Jimenez et al., 2024），我们使用人工 PR 中的隐藏测试来评测代码修改。 Following SWE-bench (Jimenez et al., 2024), we grade code changes using hidden tests from the human PRs. 评测前，我们会丢弃智能体对测试文件所作的任何修改，并应用标准测试补丁。 Before grading, we discard any test-file edits made by the agent and apply the gold test patches. 随后，我们在每种设置下运行由所有任务的测试合并而成的测试集。 We then run the combined test set from all tasks in every setting. 对单独应用的补丁和合并后的补丁使用不同测试，可能会造成存在干扰的假象（§4）。 Using different tests for individual and merged patches can falsely suggest interference (§4).

$\Delta_{\mathrm{blind}}$ 统计仅在组合补丁时才出现的测试失败数量。 $\Delta_{\mathrm{blind}}$ counts failures that appear only when the patches are combined. 任何在应用任一单独补丁时就已失败的测试均被排除。 A test that already fails with any individual patch is excluded. 在盲合并中，我们复用单独运行（solo）时的原样补丁，因此智能体不同运行之间的差异无法解释这一结果。 We reuse the exact patches from solo in the blind merge, so differences between agent runs cannot explain the result.
我们报告计数 $\Delta_{\mathrm{blind}}$，以及表示是否检测到任何干扰的指示变量 $I_{\mathrm{blind}}=\mathbf{1}[\Delta_{\mathrm{blind}}>0]$。 We report the count $\Delta_{\mathrm{blind}}$ and an indicator of whether any interference was detected, $I_{\mathrm{blind}}=\mathbf{1}[\Delta_{\mathrm{blind}}>0]$ . 例如，三个新出现的失败测试对应 $\Delta_{\mathrm{blind}}=3$ 和 $I_{\mathrm{blind}}=1$；它们不一定代表三个独立的缺陷。 For example, three newly failing tests give $\Delta_{\mathrm{blind}}=3$ and $I_{\mathrm{blind}}=1$ ; they need not represent three separate defects. 这两项度量均取决于测试覆盖率，而计数还取决于测试如何划分或重复设置。 Both measures depend on test coverage, and the count also depends on how tests are divided or duplicated. 因此，我们仅在使用相同测试集的情况下比较计数。 We therefore compare counts only with the same test set. 只有在使用合并测试套件进行评测时，每个智能体的补丁都通过其自身任务的测试，一个任务对才是可观测的，并有资格纳入我们的干扰分析。 A pair is observable, and eligible for our interference analysis, only when each agent’s patch passes its own task’s tests during grading on the combined suite.
三个基准层级。Three Benchmark Tiers.
合成层级通过改变发生变更的接口数量，同时保持任务和变更类型不变，来检验过时信息是否会导致干扰。 The synthetic tier tests whether stale information causes interference by varying the number of changed interfaces while keeping the task and type of change fixed. 挖掘层级使用经过审查的 PR，检验代码仓库历史中是否包含尚未解决的干扰实例。 The mined tier uses reviewed PRs to test whether repository history contains examples of unresolved interference. 真实代码衍生层级通过脚本对真实的 Django 辅助函数施加变更，以检验合成场景中的失败机制是否也会出现在现有代码中。 The real-derived tier applies scripted changes to real Django helpers to test whether the synthetic failure mechanism also occurs in existing code.
我们还评估一种通信条件 comm。 We also evaluate a communication condition, comm. 智能体会收到一条简短消息，描述另一名工作者已完成的变更。 The agent receives a short message describing the other worker’s completed change. 我们根据模板和已知的变换生成这条消息。 We generate this message from a template and the known transformation. 这是一条基于已完成变更的预知消息（oracle message）。 This is an oracle message based on a completed change. 我们不评估工作进行过程中生成的消息。 We do not evaluate messages generated during ongoing work.
3. 数据集构建3. Dataset Construction
我们基于 Django 构建大多数实例，因为它拥有成熟的工具，可用于可复现的智能体评测。 We build most instances from Django, which has established tools for reproducible agent evaluation. 对于 SymPy、xarray 和 seaborn，我们采用相同的确定性构建流程。 We use the same deterministic construction procedure for SymPy, xarray, and seaborn.
挖掘。Mining.
我们收集已合并的 PR，保留其中修改了 1–12 个运行时源文件的 PR（排除文档、CI 和格式调整），并将至少修改了一个共同源文件的 PR 组成候选对；这是一种寻找潜在相关变更的低成本方法（Chockchowwat et al., 2025）。 We collect merged PRs, keep those that change 1–12 runtime source files (excluding docs/CI/formatting), and form candidate pairs that edit at least one common source file, an inexpensive way to find potentially related changes (Chockchowwat et al., 2025). 修改同一个文件并不保证会产生干扰；我们在智能体研究中对此进行检验。 Sharing a file does not guarantee interference; we test for it in the agent study.
检查共享基线。Checking the Shared Base.
对于每个候选对，我们选择两个 PR 各自基线的合并基点，作为共享起始提交 $b$。 For each candidate pair, we choose the merge base of the two PR bases as the shared starting commit $b$ . 随后，我们应用两项筛选条件，先进行成本较低的检查。 We then apply two filters, starting with the cheaper check. (i) 无冲突合并：两个代码补丁均可应用于 $b$，且二者组合后不产生文本冲突。 (i) Clean merge: both code patches apply to $b$ , and their composition produces no textual conflict. (ii) 基线有效性：对于每个 PR，仅应用测试补丁时，其标准测试（gold tests）必须在 $b$ 上失败，而加入代码补丁后则必须通过。 (ii) Base validity: for each PR, its gold tests must fail on $b$ when only the test patch is applied and pass after adding the code patch. 标准测试补丁由人工提交的 PR 中新增或修改的行为测试组成。 The gold test patch comprises the behavioral tests added or modified by the human PR.
检查共享基线很重要，因为相关 PR 往往从不同的提交开始。 Checking the shared base matters because related PRs often start from different commits. 一个 PR 的基线可能已经包含另一个 PR 的部分解决方案，从而掩盖我们想要检验的交互作用。 One PR’s base may already contain part of the other PR’s solution, hiding the interaction we want to test. 例如，在一对涉及 HTTP 头的 PR 中，较晚 PR 的基线已经包含了较早 PR 添加的一个辅助函数。 In one HTTP-header pair, for example, the later PR’s base already contained a helper added by the earlier PR. 我们的检查会拒绝这样的基线，因为在应用候选修复之前，相关测试就已通过。 Our check rejects such a base because the relevant tests pass before we apply the candidate fix. 在一个具有代表性的批次中，无效基线约占被拒绝实例的三分之一。 In a representative batch, invalid bases accounted for about one third of rejections.
产出。Yield.
我们从挖掘得到的 685 个 Django PR 中组成了 4,262 个候选对；通过在一个 5 节点集群（320 核）上进行确定性验证，最终接受了其中 417 个，将其认定为有效的耦合实例。 From 685 mined Django PRs we formed 4,262 candidate pairs; deterministic validation across a 5-node cluster (320 cores) accepted 417 as valid coupled instances. 在一个具有代表性的批次中，${\sim}36\%$ 因两项变更存在文本冲突而未通过，${\sim}33\%$ 未通过基线有效性检查（漂移），${\sim}17\%$ 无法应用于同一基线，${\sim}14\%$ 被接受。 In a representative batch, ${\sim}36\%$ failed because the two changes textually conflict, ${\sim}33\%$ failed base validity (drift), ${\sim}17\%$ did not apply on a common base, and ${\sim}14\%$ were accepted. 我们仅对通过结构和文本筛选的配对运行测试，以控制验证成本。 We limit validation cost by running tests only on pairs that pass the structural and textual filters.

我们使用两个模型系列，评估了超过 $4{,}000$ 次经评分的任务求解（表 1）。 We evaluate more than $4{,}000$ graded task solves using two model families (Table 1). 合成实验测量接口变更数量增加时的干扰，并检验预言机消息能够在多大程度上防止干扰。 The synthetic experiments measure interference as more interfaces change and test how much an oracle message can prevent. 随后，我们检查经过审查的 PR 对是否存在干扰，并将受控变更应用于真实的 Django 辅助函数。 We then examine reviewed PR pairs for interference and apply the controlled changes to real Django helpers.
合成实验层级。Synthetic Tier.
每个合成实例都会向一份 Django 检出的代码中添加 $K{=}4$ 个辅助函数。 Each synthetic instance adds $K{=}4$ helper functions to a Django checkout. 智能体编写调用这些辅助函数的小型包装函数。 The agent writes small wrappers that call these helpers. 一个由脚本生成的并发补丁恰好更改 $d$ 个辅助函数接口，其中 $d\in\{0,\dots,4\}$ 为陈旧程度。 A scripted concurrent patch changes exactly $d$ helper interfaces, where $d\in\{0,\dots,4\}$ is the staleness degree. 它会重命名辅助函数、添加一个必需参数，或更改返回类型。 It either renames helpers, adds a required argument, or changes the return type. 包装函数的预期输出保持不变。 The expected wrapper output stays the same. 我们对每种设置运行八次试验。 We run eight trials per setting. 盲态智能体使用旧接口，因此我们预计，合并后，其包装函数会在 $d$ 个已更改的辅助函数上失败。 A blind agent uses the old interfaces, so we expect its wrappers to fail on the $d$ changed helpers after merging. 知情智能体在编写包装函数之前会看到新接口。 An informed agent sees the new interfaces before writing its wrappers.
重命名和必需参数变更的结果与预测一致。 Renames and required-argument changes matched the prediction. 盲态补丁在全部 $d$ 个已更改的辅助函数上均出现失败（$\Delta_{\mathrm{blind}}=d$，方差为零）。 Blind patches failed on all $d$ changed helpers ( $\Delta_{\mathrm{blind}}=d$ , with zero variance). 知情智能体没有出现失败。 The informed agent had no failures. 由于包装函数任务几乎没有采用其他实现方式的余地，因此该结果无法预测开放式开发中失败数量如何随变更规模增长。 Because the wrapper tasks leave little room for alternative implementations, the result does not predict how failures scale in open-ended development. 对于返回类型变更，尽管知情智能体看到了新接口，每次运行仍平均出现 $0.13$ 次失败。 For return-type changes, the informed agent still averaged $0.13$ failures per run despite seeing the new interface.

挖掘所得 PR 实验层级。Mined PR Tier.
对于挖掘得到的 PR 对，一个 GPT-5 级别的编程模型在共享的基线提交上，分别在独立和盲态条件下求解每项任务。 For the mined PR pairs, a GPT-5-class coding model solves each task in solo and blind conditions on the shared base. 我们分别使用 mini-swe-agent（Yang et al., 2024）这一精简的工具调用框架和 OpenHands（Wang et al., 2025）来运行该模型。 We run the model with mini-swe-agent (Yang et al., 2024), a minimal tool-calling harness, and with OpenHands (Wang et al., 2025). 两者均采用 SWE-bench 风格的评分方式。 Both use SWE-bench-style grading.
我们最初的评测流程产生了具有误导性的干扰计数，原因有二。 Our initial grading procedure produced misleading interference counts for two reasons. 首先，智能体有时会修改测试文件，这可能导致标准测试无法以一致的方式应用。 First, agents sometimes edited test files, which could prevent the gold tests from being applied consistently. 其次，我们仅使用各个补丁所属任务的测试来评测该补丁，却使用两个任务的测试来评测合并后的补丁。 Second, we tested each individual patch only on its own task’s tests, but tested merged patches on both tasks’ tests. 因此，一个补丁本身就可能导致另一任务的测试失败，但这种失败只有在合并评测中才会显现。 A patch could therefore break another task’s test on its own, yet the failure would appear only in the merged evaluation. 这两个问题都使 $\Delta_{\mathrm{blind}}$ 虚高（图 4）。 Both problems falsely increased $\Delta_{\mathrm{blind}}$ (Fig. 4).

基于真实 Django 辅助函数构造的任务。Constructed Tasks on Real Django Helpers.
我们对 12 个 Django 辅助函数应用三种接口变换，构造出 36 个实例（附录 C）。 We apply three interface transformations to 12 Django helpers to construct 36 instances (Appendix C). 每个辅助函数都关联着一对经过验证的 PR，该配对展示了通过共享符号形成的依赖关系。 Each helper is linked to a validated PR pair that illustrates a dependency through a shared symbol. 一个补丁通过脚本修改接口；另一个补丁由智能体编写，并使用该辅助函数。 One patch makes a scripted interface change; an agent writes the other patch, which uses the helper.
在盲测条件下，GPT-5.5 在 105/108 次运行（97%）中产生了干扰；尽管文本合并均无冲突，全部 12 个辅助函数上仍都出现了失败。 In the blind condition, GPT-5.5 produced interference in 105/108 runs (97%), with failures on all 12 helpers despite clean textual merges. 提供预言机消息（oracle message）后，89/108 次运行（82%）恢复成功。 With the oracle message, 89/108 runs (82%) were recovered. 在以该消息为条件生成且合并无冲突的补丁中，恢复率达到了 93%。 Recovery reached 93% among message-conditioned patches that merged cleanly. 这些比率适用于构造式 Django 任务。 These rates apply to the constructed Django tasks.
该挖掘流水线也适用于 Django 之外的项目。 The mining pipeline also works beyond Django. 使用同一套基于 pytest 的验证框架，它在 SymPy 中找到了 11 个有效配对，在 xarray 中找到了 12 个，在 seaborn 中找到了 7 个。 With the same pytest-based validation harness, it finds 11 valid pairs in SymPy, 12 in xarray, and 7 in seaborn. 大多数配对被排除的原因是文本冲突和不兼容的基底提交。 Textual conflicts and incompatible base commits account for most rejections. 在实践中，使用时间相近的 PR，并从 PR 自身的变更中选择测试时，构造效果最佳。 In practice, construction works best with PRs close in time and tests selected from the PR’s own changes. 运行修改过的整个测试文件可能引入无关或结果不稳定的测试用例。 Running entire modified test files can introduce unrelated or flaky cases.
有效性威胁。Threats to Validity.
主要的测量风险是将单个补丁的失败计为干扰。 The main measurement risk is counting an individual patch’s failure as interference. 为应对这一问题，我们移除智能体对测试的修改，在每种条件下运行相同的合并测试集，并要求每个补丁在独立运行时都能解决其自身任务。 We address this by discarding agent test edits, running the same combined test set in every condition, and requiring each patch to solve its own task in isolation. 与 SWE-bench (Jimenez et al., 2024) 一样，我们依靠标准测试来定义正确行为。 As in SWE-bench (Jimenez et al., 2024), we rely on the gold tests to define correct behavior. 我们还检查这些测试在应用人工修复之前，是否会在共享基底版本上失败。 We also check that those tests fail on the shared base before applying the human fix.
历史 PR 已经经过审查，而构造的任务则有意引入破坏兼容性的变更。 Historical PRs have been through review, while the constructed tasks deliberately introduce breaking changes. 后者使用一个由脚本生成的补丁，并要求智能体调用指定的辅助函数。 The latter use one scripted patch and constrain the agent to call selected helpers. 我们的智能体实验也仅限于 Django。 Our agent experiments are also limited to Django. 这些结果确立了该失败机制，并在 12 个真实辅助函数上展示了这一机制，但并未估计其在日常并行开发中的发生频率或严重程度。 The results establish the failure mechanism and demonstrate it on 12 real helpers, but do not estimate its frequency or severity in everyday parallel development.
通信实验的结果以对已完成变更的完整描述为前提；使用并行工作期间生成的消息能否实现恢复，尚未经过测试。 The communication results assume complete descriptions of finalized changes; recovery with messages generated during parallel work remains untested. 最后，测试可能漏检故障，而多个测试也可能检测到同一个缺陷。 Finally, tests can miss failures, and several tests can detect the same defect. 因此，我们仅在使用同一测试集的情况下解读干扰计数。 We therefore interpret interference counts only for a shared test set.
5. 正在开展的工作与开放问题5. Ongoing Work and Open Problems
这些实验尚未解决以下问题：审查前干扰发生的频率有多高，智能体在并行工作期间应如何通信，以及如何将结果推广到两个以上的任务。 The experiments leave open how often interference occurs before review, how agents should communicate during parallel work, and how the results extend to more than two tasks.
审查前的并行工作。Parallel Work Before Review.
要衡量实践中干扰发生的频率，我们需要并行智能体在审查或修复之前的执行记录。 To measure how often interference occurs in practice, we need execution records from parallel agents before review or repair. 这些记录应保留共同的起始提交、独立生成的补丁以及中间状态 (Li et al., 2024)。 These records should preserve a shared starting commit, independently generated patches, and intermediate states (Li et al., 2024). 这些记录将使我们能够比较采用隔离工作单元、异步更新、显式编排或共享状态的系统中的信息缺口。 These records would let us compare information gaps in systems with isolated workers, asynchronous updates, explicit orchestration, or shared state.
从预言机可见性到在线通信。From Oracle Visibility to Online Communication.
预言机消息使合成干扰减少了 $98\%$。 The oracle message reduces synthetic interference by $98\%$ . 然而，在运行中的系统里，智能体可能只能共享其计划、尚未完成的补丁或自动生成的摘要。 In a running system, however, agents may only be able to share their plans, an unfinished patch, or an automatically generated summary. 这些选项在完整性、延迟和隐私方面各不相同 (Xia and Park, 2026)。 These options differ in completeness, delay, and privacy (Xia and Park, 2026). 在相同的 token 预算下，与受影响符号列表和已完成的编辑进行比较，将揭示消息内容和发送时机如何影响恢复。 A comparison with affected-symbol lists and completed edits, using the same token budget, would show how message content and timing affect recovery.
规模。Scale.
我们的实验聚焦于成对任务。 Our experiments focus on pairs of tasks. 当有 $N>2$ 个任务时，即使每一对变更都能正常工作，也可能需要三个或更多变更同时出现才会引发故障。 With $N>2$ tasks, a failure may require three or more changes to occur together, even if every pair works correctly. 更大的任务集还会产生更多潜在的依赖关系。 Larger task sets also create more possible dependencies. 扩展该基准将检验成对任务的结果能否预测更大任务组的可靠性，以及我们能否在智能体开始工作之前，估计协调对于给定任务集的潜在提升空间。 Extending the benchmark would test whether results for pairs predict reliability for larger groups, and whether we can estimate coordination headroom for a given set of tasks before agents start work.
6. 结论6. Conclusion
基于同一代码库工作的智能体可能生成单独使用时通过测试、组合使用时却失败的补丁，即使合并时不存在文本冲突也是如此。 Agents working from the same codebase can produce patches that pass alone but fail together, even when the merge has no textual conflicts. 在 stale 中，我们使用同一测试集，分别对相同补丁进行单独测试和组合测试。 In stale, we test the same patches alone and together using a common test set. 将无法获知并发变更的智能体与能够看到已完成并发变更的智能体进行比较，可以估计协调能够带来多大帮助。 Comparing blind agents with agents that see the completed concurrent change estimates how much coordination could help.
合成任务用于隔离由过时接口引起的故障。 Synthetic tasks isolate failures caused by stale interfaces. 挖掘得到的 PR 对表明，经过审查的历史记录很少保留尚未解决的交互问题。 Mined PR pairs suggest that reviewed history rarely retains unresolved interactions. 构造任务在 12 个 Django 辅助函数上复现了这一机制，干扰率为 97%，使用预言机消息时的恢复率为 82%。 Constructed tasks reproduce the mechanism on 12 Django helpers, with 97% interference and 82% recovery using an oracle message. 这些在构造任务中得到的比率并不衡量现实世界中的普遍程度。 These constructed rates do not measure real-world prevalence. 下一步是在更多代码仓库中，使用智能体能够在执行期间生成的消息，研究审查前的并行工作。 The next step is to study parallel work before review, across more repositories, with messages that agents can generate during execution.
