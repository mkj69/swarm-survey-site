一句话

这份开发实录显示，多智能体可以改善代码完整性，但作者的对照实验没有证明提速或省钱；扩展的关键在于接口、合并、验收与恢复机制。

主要内容

  • 架构采用确定性编排与容器执行分离：Azure DTS 负责拆任务、并行调度和检查点，各智能体使用独立容器及 Git 分支。隔离减少工作区干扰，但增加部署和集成开销。
  • 两类“幽灵智能体”来自系统边界错误：任务编号类型不一致、工具名称归一化不一致，导致工具未挂载，智能体却仍报告完成。作者增加了零工具调用检查和重试。
  • 接口契约比单纯分工更重要。存储与 CLI 智能体曾分别选择 JSON 和 SQLite，模块各自合理却无法组合。预先规定接口后，作者报告冲突由六个分支中的三个降至四个中的零个，评分从 28 升至 68。
  • 合并优先使用 Git，遇到冲突才调用模型，合并耗时据报从七分钟降至三十秒以内。但模型仍曾删除实现或留下空函数，说明“合并成功”必须通过差异和功能检查验证。
  • 失败后改为在集成分支局部修补，避免全队重跑。一个案例中评分从 43 升至 89.5，修复耗时三分钟，对比重跑七分钟。

证据与可信度

  • 属于微软社区博客上的作者工程实录，兼有平台介绍。材料提供完整叙述，但本解读未独立检查其所称公开代码和实验记录。
  • 核心对照使用相同提示、相同 GPT-5-nano，由 Sonnet 4.6 按四项标准评分，覆盖短链接和工单系统两个任务。质量分别由 1.9 升至 2.5、2.3 升至 2.95，作者据此报告约 32% 和 28% 提升；这是模型裁判评分，不等于独立功能验收。
  • 对应耗时为 2.5→5.5 分钟、1.75→约八分钟；令牌为 7.7K→30K、11K→39K。按表中数值，多智能体约慢 2.2 和 4.6 倍，令牌约增至 3.9 和 3.5 倍，未提供货币成本对照。
  • 总计十余次评估不等于每组对照都充分重复；未见方差、显著性或完整消融。文中外部单智能体耗时来自不同实验，不能据此证明本系统更快。“三项赢两项”的表述也缺乏自身对照数据支持。

对 swarm scaling 的意义

材料支持的是有条件的质量收益，而非智能体越多越好。独立模块能并行开发，但接口偏差、共享文件冲突和虚假完成报告会把节省的时间转为集成成本。

可借鉴的路径是：先定义契约，用确定性工具处理常规操作，再验证实际产物，并按故障范围局部恢复。作者提出三个以上独立模块更适合 swarm，但这只是经验判断；本文没有智能体数量递增实验，尚不能建立规模与收益的关系。
