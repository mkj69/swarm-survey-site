一句话

Raft 提供的是故障条件下共享状态的一致性基础：多数派可用时推进，失去多数派时停止推进，同时保持已决定结果的一致性。

主要内容

  • Raft 将共识拆成相对独立的子问题，以便理解和实现；项目页称其容错能力与性能等同于 Paxos，但此处没有展开比较依据。
  • 共识用于让多个服务器对日志中的命令达成一致。对于同一日志位置，各状态机不能执行不同命令；按相同命令序列运行，才能得到一致状态。
  • 材料以 5 台服务器为例：其中 2 台故障后仍可继续运行；失去多数派后则停止推进。这体现了“能否继续工作”与“是否产生冲突结果”的区别。
  • 页面汇集论文、博士论文、TLA+ 规范、形式化验证研究、教学资源及实现入口。抓取内容到实现表头为止，未包含各实现的具体能力信息。

证据与可信度

这是项目官方说明，属于算法机制介绍，不是吞吐量、延迟或扩展效率的实测报告。5 台服务器容忍 2 台故障，是多数派规则的示例：仍有 3 台可用，并非实验测出的故障率。

“与 Paxos 性能等同”是项目方概括，所给内容没有基准配置或测试数据。页面列出了论文、形式规范和外部验证研究，可作为进一步核查入口；本次未核读这些链接，不能将链接存在视为已独立验证。元数据中的日期也不能直接当作算法发表日期。

对 swarm scaling 的意义

它为 swarm 的共享状态层提供参考：若多个 agent 需要共同维护已确认的任务状态或操作顺序，可以借鉴一致日志与复制状态机的思路。这是对材料的架构推论，页面没有展示 agent 系统实验。

关键边界是：服务器对命令达成一致，不等于 agent 的判断正确，也不等于任务完成质量提高。多数派规则解释了部分节点故障时如何继续协调，却不能证明增加 agent 会提升吞吐或智能水平。讨论 swarm scaling 时，应分别考察状态一致性、持续推进能力与任务收益。
