一句话

Cursor 的实验自述表明，多智能体编码能否扩展，关键在任务分工与协调机制；增加智能体数量本身并不保证吞吐提升。

主要内容

  • 最初采用平级自治：智能体通过共享文件认领任务、更新状态。锁机制带来等待、忘记释放及违规写入等问题，作者称 20 个智能体的有效吞吐降至两三个的水平。
  • 改用乐观并发控制后，状态更新更稳健，但责任分配仍有缺口：智能体倾向选择容易、安全的小改动，困难任务与端到端实现缺少承担者。
  • 后续架构分为规划者、执行者和裁判。规划者持续拆解任务，并可派生子规划者；执行者专注完成任务；裁判在周期末判断是否继续，下一轮重新开始。
  • 作者称该架构支持数百个执行者向同一分支提交，冲突较少。浏览器实验运行近一周，产出超过百万行代码、涉及约千个文件；Solid 到 React 的迁移持续三周以上，通过 CI 和初步检查，但仍待仔细审查。
  • 集中处理质量与冲突的集成者角色反而形成瓶颈，最终被移除。作者还强调按角色选模型、调整提示词及定期重启的重要性。

证据与可信度

这是 Cursor 对自身实验的厂商自报，材料未提供独立核验。上述吞吐、时长和代码规模均直接取自正文；抓取内容重复了一遍，不能算作重复实验或额外证据。

“20 个降至两三个”属于运行观察，但没有吞吐单位、任务基准或统计方法，无法据此计算可靠的扩展效率。代码行数、文件数和提交数反映产出规模，不能直接证明功能完整性或质量；迁移通过 CI 是有限验证，作者也明确保留人工审查要求。

模型优劣、提示词作用及角色设计效果主要属于团队经验判断，缺少受控对照。文中视频渲染提速 25 倍是具体功能优化结果，不能当作 swarm 的并行加速比。

对 swarm scaling 的意义

这份材料提供了一个有价值的失败机制：共享协调状态会产生等待，而平级自治还可能造成责任真空。优化并发控制，只解决了前一类问题。

规划与执行分离、递归拆解任务、减少集中集成环节，是值得复验的扩展路径。但现有证据支持的是“大规模持续协作具有可行性”，尚不足以证明线性加速或成本优势。评估此类系统，应同时关注完成质量、有效吞吐、协调开销和资源消耗，不能只看智能体数量与代码产量。
