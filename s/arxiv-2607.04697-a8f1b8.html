AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict RatesGitHub 上的 AI 智能体拉取请求：频率、结构与合并冲突率
Abstract.摘要。
AI coding agents may generate and submit Pull Requests (PRs) to the same repository at the same time. However, research concerning the extent of concurrent submission by AI coding agents to a common repository does not exist. This paper uses the AIDev-pop dataset (33,596 PRs in 2,807 repositories) to provide the first empirical examination of the prevalence of concurrent submission using PRs authored by agents. We report that when considering exact temporal overlap, 40.2% of repositories contain co-active agent-authored PR pairs; further, the co-active pairs account for 79.4% of all PRs generated by an AI agent. When we examine co-activity within a one week collaboration window, the percentages are increased to 53.4% and 95.0%, respectively. For the majority of the co-active PR pairs (underlying the vast majority of which are intra-agent authored), both PRs were authored by the same agent, while only 0.5% of co-active pairs were cross-agent, and occurred in only 122 out of 2807 total repositories examined (or approximately 4.3%). Additionally, we replayed actual three way git merges on 747 unique co-active pairs (one per repository), and computed the percentage of textual conflict encountered during the merge operation to combine the two PRs in each pair. We observed that the percentage of textual conflict encountered was significantly higher for cross-agent pairs compared to intra-agent pairs: 41.7% vs. 19.8%, respectively, with non-overlapping 95% confidence intervals. Lastly, we developed a classification system based on the detection of conflict reported by git, and determined that the majority of conflicts resulted from modifications to source code files (84.4% of conflicted files) and not dependency manifest files; further, nearly 42% of conflicts we observed were structural (i.e., modify/delete or add/add). Since these metrics are limited to the textual level of granularity, they represent conservative lower bounds on costs incurred due to the uncoordinated contributions of multiple AI teammates contributing to a single project.
AI 编程智能体可能同时向同一个代码仓库生成并提交拉取请求（Pull Requests，PRs）。然而，目前尚无研究探讨 AI 编程智能体向同一代码仓库并发提交的普遍程度。本文使用 AIDev-pop 数据集（涵盖 2,807 个代码仓库中的 33,596 个 PR），基于智能体创建的 PR，首次对并发提交的普遍程度进行实证考察。我们发现，按严格的时间重叠标准衡量，40.2% 的代码仓库包含同时处于活跃状态的智能体 PR 对；此外，属于这些同时活跃配对的 PR 占 AI 智能体生成的全部 PR 的 79.4%。当我们在一周的协作时间窗口内考察共同活跃情况时，这两个比例分别上升至 53.4% 和 95.0%。在大多数同时活跃的 PR 对中，两个 PR 均由同一个智能体创建（即绝大多数配对属于同一智能体内部配对）；只有 0.5% 的同时活跃配对涉及不同智能体，且这类配对仅出现在所考察的全部 2807 个代码仓库中的 122 个（约 4.3%）。此外，我们对 747 个不同的同时活跃配对（每个代码仓库选取一对）重放了实际的 git 三方合并操作，并计算了合并每对中的两个 PR 时出现文本冲突的比例。我们观察到，不同智能体之间的配对出现文本冲突的比例显著高于同一智能体内部的配对：分别为 41.7% 和 19.8%，且二者的 95% 置信区间互不重叠。最后，我们基于 git 报告的冲突检测结果建立了一个分类体系，并确定大多数冲突源于对源代码文件的修改（占发生冲突文件的 84.4%），而非依赖清单文件；此外，我们观察到的冲突中，近 42% 属于结构性冲突（即 modify/delete 或 add/add）。由于这些指标仅限于文本粒度，它们反映的是多个 AI 队友在缺乏协调的情况下向同一项目贡献代码所产生的成本的保守下界。

1. Introduction1. 引言
Engineering automation has undergone considerable progress since the first generation of linear, user-interaction-based auto-completion utilities. Today’s engineering agents operate independently and in real-time; they have complete environmental understanding and therefore can independently assess issues, write fixes for applications, conduct internal testing cycles, and submit pull requests (PRs) to the operational master branch [1] autonomously. Over the past few years, datasets such as the AIDev ecosystem data set [2], which includes an empirical collection of more than 932,000 pull requests submitted across 116,211 multi-scaled GitHub repositories, have demonstrated that automated developers are creating source code in unprecedented numbers, which indicates a shift toward hybrid or completely autonomous collaborative programming.
自第一代基于用户交互的线性自动补全工具问世以来，工程自动化已取得长足进步。如今的工程智能体能够独立、实时地运行；它们具备完整的环境理解能力，因此能够自主评估问题、编写应用程序修复代码、执行内部测试周期，并自主向实际运行的 master 分支提交拉取请求（PRs）[1]。过去几年中，AIDev 生态系统数据集 [2] 等数据集表明，自动化开发者正在以前所未有的规模创建源代码，这标志着编程正向人机混合或完全自主的协作模式转变；该数据集收集了来自 116,211 个不同规模 GitHub 代码仓库的超过 932,000 个已提交拉取请求的实证数据。
A structural issue of coordination between architecture and text arises due to the increased use of autonomous development of source code. In addition to having numerous agent instances—or various agent types—deployed to a single target project at the same time, the typical outcome is a large degree of overlap during each instance’s work. Even though standard branching models for git-based systems support two separate PRs targeting the same base commit being built, tested, and run independently after both are merged into a common destination branch, they can immediately cause failures in the application. While traditional version control tools (e.g., git) can identify conflicts between developers based upon specific lines of text when merging changesets, they cannot determine conflicting intent among multiple developers.
随着源代码自主开发的日益普及，架构与文本之间的协调出现了结构性问题。在同一目标项目中同时部署多个智能体实例或不同类型的智能体，通常还会导致各实例的工作期间存在大幅重叠。尽管基于 git 的系统所采用的标准分支模型支持对以同一基准提交为目标的两个独立 PR 分别进行构建、测试和运行，但当二者都合并到同一个目标分支后，便可能立即导致应用程序故障。虽然传统版本控制工具（如 git）能够在合并变更集时，根据具体的文本行识别开发者之间的冲突，但它们无法判定多个开发者的意图是否相互冲突。
The current literature contains much information concerning merge conflicts caused by human activity. This includes characterizing patterns of behavior based on social, structural, and evolutionary metrics across the globe in terms of open-source communities [8][9]. Furthermore, there is a growing body of evidence regarding individual coding agents updating repositories and how successful their updates are in peer review [6][7]. Recent studies have also quantitatively measured how frequently a single PR submitted by an agentic developer will conflict with its base branch [3]. However, there is very little known about the implications for structure of multiple agents working together on a single software project and developing PRs that will conflict with one another at approximately the same time—rather than conflicts between a single PR and its base. An empirical gap exists with respect to two critical variables: (i) the frequency at which concurrently developed agentic workflows exist on GitHub, (ii) and the overall likelihood that these workflows that are developed simultaneously will conflict with each other.
现有文献包含大量关于人类活动所引发的合并冲突的研究。其中包括基于社会、结构和演化指标，对全球开源社区的行为模式进行刻画 [8][9]。此外，关于单个编程智能体如何更新代码仓库，以及这些更新在同行评审中取得多大成功的实证证据也在不断增加 [6][7]。近期研究还定量测量了智能体开发者提交的单个 PR 与其基准分支发生冲突的频率 [3]。然而，对于多个智能体在同一软件项目中协作，并在大致相同的时间开发出彼此冲突的 PR 会产生何种结构性影响，目前所知甚少；这里关注的是 PR 之间的冲突，而非单个 PR 与其基准分支之间的冲突。关于两个关键变量，目前仍存在实证研究空白：(i) GitHub 上并发开展的智能体工作流出现的频率；(ii) 这些同时开展的工作流彼此发生冲突的总体可能性。
To address this gap, our study provides an empirical examination of the AIDev-pop dataset. From this dataset, we found that there were 2,807 active repositories where 33,596 pull requests were created by authors who were automated developers. Unlike previous research that used heuristically proxied methods to estimate conflict rates, we developed a fully automatic process that could simulate all merge operations using headless git merge tree functionality so as to obtain accurate measurements of actual conflict rates. Our study examines four foundational research questions:
为弥补这一空白，本研究对 AIDev-pop 数据集进行了实证分析。通过该数据集，我们发现，2,807 个活跃仓库中共有 33,596 个拉取请求由自动化开发者创建。以往研究采用启发式代理方法估计冲突率，与之不同，我们开发了一套全自动流程，利用无界面的 git merge tree 功能模拟所有合并操作，从而准确测量实际冲突率。本研究考察四个基础研究问题：
RQ1 (Frequency): For a given time horizon(s), how frequent do agentic PRs become temporally coactive (concurrently active) within a single repository?
RQ1（频率）：在给定的时间范围内，智能体创建的 PR 在同一仓库中出现时间上共同活跃（并发活跃）的频率有多高？
RQ2 (Composition): What percentage of co-active PR pairings occur from identical intra-agents vs. dissimilar cross-agents deployment scenarios?
RQ2（构成）：在共同活跃的 PR 配对中，来自相同智能体内部部署场景与不同智能体之间部署场景的配对各占多大比例？
RQ3 (Collision): How frequently do collisions occur when two or more concurrently operating agentic PRs are programmatically combined and merged into the main branch? What characteristics distinguish these conflicts structurally?
RQ3（碰撞）：当两个或更多并发运行的智能体 PR 通过程序组合并合并到主分支时，碰撞发生的频率有多高？这些冲突在结构上有哪些区别性特征？
RQ4 (Association): Which programming languages, sizes of repositories, and types of agents show association(s) with high levels of concurrency?
RQ4（关联）：哪些编程语言、仓库规模和智能体类型与高并发水平存在关联？
2. Background: The Three Layers of Conflict2. 背景：冲突的三个层次
To determine how much integration friction will exist from autonomous agents we have identified three structural levels of conflict that arise from taking the two independent modifications ( $P_{A}$ & $P_{B}$ ) and combining them into a single base branch ( $B_{\text{base}}$ ). These conflicts can be divided into three sequential, dependency layers.
为确定自主智能体会带来多大的集成阻力，我们识别了将两项独立修改（$P_{A}$ & $P_{B}$）合并到同一个基准分支（$B_{\text{base}}$）时产生的三个结构性冲突层次。这些冲突可划分为三个依次递进、相互依赖的层次。
Conflict Layer 1. Textual Conflicts. The first layer of conflict arises either through the overlap of modifications made by $P_{A}$ and $P_{B}$ to lines of code contained in the same source file; or through a modification that deletes an entire block of code, or an entire file that has also been modified by the other agent. When this type of conflict occurs, the delta-matching engine cannot find a determinate merge path for the two modifications. In these cases, the merge-engine raises a flag indicating a failed merge, generates conflict-markers to the source-file, and stops processing further.
冲突层次 1。文本冲突。第一层冲突产生于以下情况：$P_{A}$ 和 $P_{B}$ 对同一源文件中的代码行所作的修改存在重叠；或者，一项修改删除了另一智能体也曾修改过的整个代码块或整个文件。发生此类冲突时，差异匹配引擎无法为这两项修改找到确定的合并路径。在这些情况下，合并引擎会设置表示合并失败的标志，在源文件中生成冲突标记，并停止后续处理。
Conflict Layer 2. Build Conflicts. The second level of conflict is produced when $P_{A}$ and $P_{B}$ pass through the textual-merging process without raising a failure-flag indicating a failed merge, but upon passing to the compilation stage fail to successfully compile, or fail static-analysis. Typically, this occurs with statically-typed programming languages. For example, $P_{A}$ modifies the definition of a global function to require an additional input-parameter, while $P_{B}$ introduces a call to that function using its previous signature [11][13]. Each individual modification is correct individually; as a whole, however, they generate a faulty Abstract Syntax Tree (AST).
冲突层次 2。构建冲突。第二层冲突产生于以下情况：$P_{A}$ 和 $P_{B}$ 通过了文本合并过程，未触发表示合并失败的标志，但在进入编译阶段后无法成功编译，或未能通过静态分析。这种情况通常发生在静态类型编程语言中。例如，$P_{A}$ 修改了一个全局函数的定义，使其需要额外的输入参数，而 $P_{B}$ 则引入了一个使用该函数原有签名的调用 [11][13]。每项修改单独来看都是正确的；然而，它们组合后会生成错误的抽象语法树（AST）。
Conflict Layer 3. Semantic Conflict. The last layer represents the deepest form of interference: after generating a valid textual merge with no compilation errors, there exists logical contradiction(s) between the functional execution assumptions/state-invariant produced by $P_{A}$ and those created by $P_{B}$ —the Interference Problem Formalized in Classical Program Integration Theory [10][12].
冲突层次 3。语义冲突。最后一层代表最深层次的干扰：在完成有效的文本合并且没有编译错误后，$P_{A}$ 所产生的功能执行假设或状态不变式与 $P_{B}$ 所产生的相应假设或不变式之间仍存在逻辑矛盾——这就是经典程序集成理论中形式化描述的干扰问题 [10][12]。
This research focuses on evaluating the textual-layer. Due to their lack of knowledge of language-runtimes, environment variables or external mock database configurations textual-conflict detection provides a higher degree of both reproducibility and scalability than build- or semantic-conflict detection. Most important; since no build- or semantic-conflict can occur until a successful textual-conflict has occurred, the empirically determined conflict-rate here is conservative lower-bound of the total amount of system-wide friction.
本研究重点评估文本层面的冲突。由于文本冲突检测无需了解语言运行时、环境变量或外部模拟数据库配置，因此其可复现性和可扩展性均高于构建冲突检测或语义冲突检测。最重要的是，由于只有在成功发生文本冲突之后才可能发生构建冲突或语义冲突，因此此处通过实证确定的冲突率是整个系统集成阻力总量的保守下界。
3. Previous Research3. 既有研究
Our research sits at the intersection of long-standing research in the area of repository mining and rapidly developing research in the use of large language models (LLM’s) for software development.
本研究位于两个研究领域的交汇处：一是历史悠久的软件仓库挖掘研究，二是快速发展的利用大语言模型（LLM）进行软件开发的研究。
Human merge-conflict experience research. Over the past twenty years, numerous researchers have investigated the ways humans experience issues involving merge conflicts in software repositories. Specifically, Ghiotto et al. created a definitive classification scheme of text-based collision types based upon thousands of open-source Java projects [8]. Speculative merging tools developed by Brun et al. were designed to reduce “human friction” associated with resolving merge-conflicts by identifying potential conflicts in advance via workspace analysis, separating out these conflicts prior to reaching the central origin repository [9]. These works provide foundational knowledge for understanding human experience during software maintenance. However, they make assumptions about human limitations: that developers will review code in increments, adhere to a pre-determined shift schedule, and be limited by the rate of their typing/cognitive processing abilities.
人类合并冲突经历研究。过去二十年来，众多研究者考察了人类在软件仓库中遭遇合并冲突相关问题的情况。具体而言，Ghiotto 等人基于数千个开源 Java 项目，建立了一套权威的文本碰撞类型分类体系 [8]。Brun 等人开发的推测性合并工具旨在通过工作区分析提前识别潜在冲突，并在这些冲突进入中央远程仓库之前将其分离出来，从而减少解决合并冲突所带来的“人际摩擦” [9]。这些工作为理解软件维护过程中人类的经历提供了基础知识。然而，它们对人类的局限性作出了一些假设：开发者会逐步审查代码、遵守预先确定的轮班安排，并受到其打字速度和认知处理能力的限制。
Quantitative assessments of output quality of autonomous agents. As coding agents continue to evolve towards greater sophistication (Devin, Claude Code, GitHub Copilot Workspace, etc.), there is increasing pressure to quantitatively assess the quality of code generated by these agents. Traditionally, most quantitative evaluations of coding agents have evaluated the accuracy of individual patches generated by coding agents, or the likelihood that individual PRs will be rejected by human maintainers [4, 5]. More recently, researchers have reported increases in both local code churn and message–code inconsistencies within code rewritten by LLMs [6, 7]. A critical void in this literature remains the assessment of interactive concurrency—how these autonomous agents interact competitively or cooperatively when deployed simultaneously across shared source code.
自主智能体输出质量的定量评估。随着编码智能体不断向更高的成熟度演进（Devin、Claude Code、GitHub Copilot Workspace 等），对这些智能体生成的代码进行质量定量评估的需求日益迫切。传统上，大多数针对编码智能体的定量评估都侧重于评估其生成的单个补丁的准确性，或单个 PR 被人类维护者拒绝的可能性 [4, 5]。近期，研究人员报告称，LLM 重写的代码中，局部代码变动量和消息与代码之间的不一致性均有所增加 [6, 7]。现有文献仍存在一个关键空白，即对交互式并发的评估——当这些自主智能体同时部署于共享源代码上时，它们如何以竞争或合作的方式相互作用。
Agent-based merge conflicts. Most analogous to our current investigation, Ogenrwot and Businge created AgenticFlict—a very large-scale dataset that resulted from simulating the merge of every agentic PR against its base branch, reporting that 27.67% of agentic PRs conflicted with their bases [3]. The authors describe their results in terms of how far a single PR has deviated from a continuously evolving trunk. Our investigation seeks to address a complementary question about collaboration: how often do two concurrently open agentic PRs conflict with one another when merged? To date we are aware of no prior work that evaluates inter-PR conflict among concurrently open agentic PRs; identifies the proportion of intra-agent vs. cross-agent pairs involved in such instances; or develops a taxonomy that describes what types of inter-PR conflicts exist.
基于智能体的合并冲突。与本研究最为相近的是，Ogenrwot 和 Businge 创建了 AgenticFlict，这是一个通过模拟将每个智能体生成的 PR 合并到其基分支而构建的超大规模数据集；他们报告称，27.67% 的智能体生成的 PR 与其基分支存在冲突 [3]。作者从单个 PR 偏离持续演进的主干的程度这一角度描述其结果。本研究旨在回答一个有关协作的互补问题：两个同时处于开放状态的智能体生成的 PR 在合并时，彼此发生冲突的频率有多高？截至目前，据我们所知，尚无研究评估同时处于开放状态的智能体生成的 PR 之间的冲突，确定此类冲突中同智能体配对与跨智能体配对所占的比例，或建立描述 PR 间冲突类型的分类体系。
4. Evaluation Pipeline4. 评估流水线
The evaluation pipeline utilized in this project utilizes the AIDev-pop dataset [2]; extracting a core analysis window consisting of 33,596 unique agentic pull requests mapped across 2,807 unique repositories.
本项目的评估流水线使用 AIDev-pop 数据集 [2]，从中提取一个核心分析窗口，其中包含分布于 2,807 个不同代码仓库中的 33,596 个不同的智能体生成的拉取请求。
4.1. Formalizing Co-activity (RQ1–RQ2)4.1. 共同活跃的形式化定义（RQ1–RQ2）
A pull request can be formally expressed as follows:
拉取请求可形式化表示如下：
$$P_{i}=(R_{j},\,A_{i},\,T_{\text{open}},\,T_{\text{close}})$$
Where $R_{j}$ represents the specific host repository where the pull request resides; $A_{i}$ represents the agent model that authored the pull request; $T_{\text{open}}$ represents the point in time when the pull request was created; and $T_{\text{close}}$ represents the time at which the pull request was finally resolved (i.e., successfully merged, closed). In order for two pull requests located within the same repository to be considered co-active with respect to a given $k$ -day time-padding window, they must overlap in their effective activities windows:
其中，$R_{j}$ 表示拉取请求所在的具体托管仓库；$A_{i}$ 表示创建该拉取请求的智能体模型；$T_{\text{open}}$ 表示拉取请求的创建时间；$T_{\text{close}}$ 表示拉取请求最终得到处理（即成功合并或关闭）的时间。对于给定的 $k$ 天时间扩展窗口，同一仓库中的两个拉取请求若要被视为共同活跃，其有效活动时间窗口必须重叠：
$$I_{i}=[\,T_{\text{open}}-k,\;T_{\text{close}}+k\,].$$
If a PR had not yet been resolved at the time of data cut-off, then $T_{\text{close}}$ is bounded to the global data-cut off epoch. Intra-agent pairs consist of two pull requests authored by the same agent-model; cross-agent pairs are defined as all pairs for which $A_{1}\neq A_{2}$ . The interval-sweep is applied to the entirety of sample-space; and prevalence is computed for each of four different threshold values for $k$ : $k\in\{0,1,3,7\}$ .
如果某个 PR 在数据截止时尚未得到处理，则将 $T_{\text{close}}$ 限定为全局数据截止时间点。同智能体配对由同一智能体模型创建的两个拉取请求组成；跨智能体配对则定义为所有满足 $A_{1}\neq A_{2}$ 的配对。对整个样本空间应用区间扫描算法，并分别针对 $k$ 的四个不同阈值计算共同活跃的普遍程度：$k\in\{0,1,3,7\}$。
4.2. Large-Scale Merge Replay (RQ3)4.2. 大规模合并重放（RQ3）
We developed an automated process to find conflicts on the repositories in our corpus. This process is a merge-replay, multi-threaded, unattended. We selected a stratified sampling of pairs of co-active repositories. The reason we chose this method is that it would keep a few very highly active repositories from skewing the results. There are two strata:
我们开发了一套自动化流程，用于发现语料库中各代码仓库的冲突。该流程采用合并重放方式，支持多线程运行，无需人工值守。我们对共同活跃的代码仓库配对进行了分层抽样。选择这种方法的原因是，它能够避免少数活跃度极高的代码仓库使结果产生偏斜。共有两个分层：
Stratum A: intra-agents, i.e., same agent, there are 625 distinct repositories. Each repository will contribute one pair of co-active.
分层 A：同智能体，即相同的智能体，共有 625 个不同的代码仓库。每个代码仓库将提供一组共同活跃的配对。
Stratum B: Cross-Agents, i.e., different agents, since only 122 repositories out of the entire corpus show some degree of cross-agent activity (See Section 5.2), we included all of those and created one pair per repository. Thus we have a total of 747 pairs.
分层 B：跨智能体，即不同的智能体；由于整个语料库中仅有 122 个代码仓库表现出一定程度的跨智能体活动（见第 5.2 节），我们将其全部纳入，并为每个代码仓库创建一组配对。因此，我们总共有 747 组配对。

5.1. RQ1 – Concurrency Prevalence5.1. RQ1 – 并发的普遍程度
The five main agents are OpenAI Codex (21,799 pull requests), Github Copilot (4,970), Devin (4,827), Cursor (1,541) and Claude Code (459). An interval sweep verifies that concurrent agentic activity is commonplace in automated environments. Of the 2807 repositories monitored by our study, 56.1% (1574 of 2807) had at least two pull requests generated by an agent. When examining concurrency using the strictest definition based on time ( $k=0$ )—i.e. both branches are open at the exact same time—1129 of 2807 repositories have parallel workflows: 40.2% of all repositories demonstrate this behavior (CI 95% [38.4%, 42.0%]). At the pull request level, 79.4% of all pull requests submitted by agents (26691 of 33596) are open concurrently with another pull request authored by another agent.
五个主要智能体分别为 OpenAI Codex（21,799 个拉取请求）、Github Copilot（4,970）、Devin（4,827）、Cursor（1,541）和 Claude Code（459）。区间扫描验证了智能体并发活动在自动化环境中十分普遍。在本研究监测的 2807 个仓库中，56.1%（2807 个中的 1574 个）至少有两个由智能体生成的拉取请求。采用最严格的基于时间的定义（$k=0$）考察并发时，即两个分支在完全相同的时间处于开放状态，2807 个仓库中有 1129 个存在并行工作流：所有仓库中有 40.2% 表现出这种行为（95% 置信区间 [38.4%, 42.0%]）。在拉取请求层面，智能体提交的所有拉取请求中，有 79.4%（33596 个中的 26691 个）与另一个智能体创建的另一个拉取请求同时处于开放状态。
Adding temporal padding to this definition of concurrency shows large increases in these percentages. When defining concurrency as happening in a window of $\pm 1$ day ( $k=\pm 1$ ), the percentage of pull requests being opened contemporaneously jumps to 93.3%. 5.2. RQ2 – Composition Profile5.2. RQ2 – 构成特征
The distribution of co-active pairs demonstrates the homogeneity of contemporary agentic workflows. At the rigid baseline of $k=0$ , only 2,896 of 580,913 co-active pairs represent cross-agent interactions (only 0.50% of all concurrent pairs), distributed among only 122 of the 2,807 total repositories. Additionally, the density of cross-agent interaction is heavily weighted toward OpenAI Codex, which—by virtue of its volume—acts as the majority anchor of concurrent activity (Cursor–Codex = 1,476 pairs; Devin–Codex = 407; Copilot–Codex = 369; Figure 1b). Therefore, multi-agent deployments today do not represent a heterogeneous combination of agents working in tandem; rather, the current concurrency burden comes from a single agent platform creating multiple automated PRs concurrently.
共同活动配对的分布体现了当前智能体工作流的同质性。在 $k=0$ 的严格基线下，580,913 个共同活动配对中仅有 2,896 个属于跨智能体交互（仅占所有并发配对的 0.50%），且仅分布在总计 2,807 个仓库中的 122 个仓库内。此外，跨智能体交互高度集中于 OpenAI Codex；凭借其数量优势，它成为并发活动中占主导地位的核心参与者（Cursor–Codex = 1,476 对；Devin–Codex = 407；Copilot–Codex = 369；图 1b）。因此，当今的多智能体部署并不体现为不同智能体协同工作的异质组合；当前的并发负担主要来自单一智能体平台同时创建多个自动化 PR。

What Causes Conflict? Contrary to the common assumption that dependency files will be involved in conflicts most frequently, conflicts fall predominantly in source code: 84.4% of the files involved in conflicts are source files while the remaining percentage are divided equally between assets (5.1%) configuration and CI files (4.0%), dependency manifests and lockfiles (3.9%) and documentation (2.6%). When calculating by pair rather than by file, 66.5% of the conflicting pairs contain source files while 19.2% of the conflicting pairs include either a dependency manifest or lockfile—a real but certainly second-order phenomenon.
什么导致了冲突？与依赖文件最常涉及冲突这一普遍假设相反，冲突主要发生在源代码中：涉及冲突的文件中，84.4% 是源文件，其余则均分于资源文件（5.1%）、配置和 CI 文件（4.0%）、依赖清单和锁文件（3.9%）以及文档（2.6%）。按配对而非文件计算时，66.5% 的冲突配对涉及源文件，而 19.2% 的冲突配对涉及依赖清单或锁文件——这确实是一种存在的现象，但显然居于次要地位。
How It Collides. Using the classification defined by git as well as reporting conflict type, 57.6% of conflict reports are content-conflicts (two different updates to the same area of a file) while a great deal of structural conflict also takes place: specifically, modify/delete conflicts account for 26.8% (one agent has updated a file while the other has removed it) and add/add conflicts account for 15.1% (each agent has added a version of the same file but with differing contents). This structural representation is an identifiable characteristic of un-coordinated parallel agents: they do not simply update the same lines—they often disagree as to whether a file should exist at all and/or independently create versions of the same new file.

5.4. RQ4 – Associations with Concurrency5.4. RQ4 – 与并发性的关联
Co-activity also appears to rise as a repository’s internal throughput increases. When categorizing repositories by their internal agentic volume—i.e., how many PRs occur within a repository over time—PR-level co-activity rose as well. Approximately 53% of low-throughput repositories ( $<6$ total agent PRs) exhibited PR-level co-activity; however, the rate of PR-level co-activity increased across all other bins: approximately 68% in intermediate-throughput repositories (6–20 agent PRs); approximately 85% in high-throughput repositories (21–100 agent PRs); and approximately 90% in the highest-throughput repositories ( $>100$ agent PRs).
随着仓库内部吞吐量的增加，同时活跃程度似乎也会上升。按照仓库内部的智能体活动量——即一段时间内仓库中产生的 PR 数量——对仓库进行分类时，PR 层面的同时活跃程度也随之上升。约 53% 的低吞吐量仓库（智能体 PR 总数 $<6$）表现出 PR 层面的同时活跃现象；而在其余各分组中，PR 层面的同时活跃率逐级上升：中等吞吐量仓库（6–20 个智能体 PR）约为 68%；高吞吐量仓库（21–100 个智能体 PR）约为 85%；吞吐量最高的仓库（智能体 PR 数量 $>100$）约为 90%。
As for authoring agents, the rates of PR-level co-activity vary significantly. Devin achieved the highest rates of PR-level co-activity at 82.5%, followed by OpenAI Codex at 80.9%, Copilot at 76.7%, Cursor at 69.8%, and Claude Code at 39.7%. Differences in the rates of PR-level co-activity among different authoring-agent platforms appear to be largely influenced by the manner in which they have been deployed rather than any properties inherent to those platforms.
就创建 PR 的智能体而言，PR 层面的同时活跃率存在显著差异。Devin 的 PR 层面同时活跃率最高，为 82.5%，其次依次为 OpenAI Codex（80.9%）、Copilot（76.7%）、Cursor（69.8%）和 Claude Code（39.7%）。不同 PR 创建智能体平台之间在 PR 层面同时活跃率上的差异，似乎主要受到部署方式的影响，而非这些平台的任何固有属性。

6. Discussion6. 讨论
6.1. The Reality of Autonomous Software Engineering6.1. 自主软件工程的现实
Our findings alter how we view automated software development. Much current research on multi-agent orchestration views the concept from a theoretical perspective of an eventual future with heterogeneous, multi-vendor agent systems. In contrast, our composition data (RQ2) reveals that intra-agent concurrency is the dominant mode of composition at present. Thus, the most significant operational issue is not coordination among different vendors’ tools, but rather management of the high-frequency output of a single agent framework.
我们的研究发现改变了我们对自动化软件开发的看法。当前有关多智能体编排的许多研究，都是从未来终将出现异构、多供应商智能体系统这一理论视角来审视该概念的。相比之下，我们的组成数据（RQ2）表明，同类智能体内部的并发是目前占主导地位的组成模式。因此，最重要的运行问题并非协调不同供应商的工具，而是管理单一智能体框架的高频输出。
Additionally, the results of our large-scale merge-replay analysis reveal that these parallel workflows create considerable integration friction. The textual conflict rate for identical agent instances was 19.8%, indicating that currently deployed agents do not have even the most basic level of horizontal awareness. Agents operate independently and in isolation, without knowledge that other agents of the same type are simultaneously accessing and altering the same files.
此外，我们的大规模合并重放分析结果表明，这些并行工作流会造成相当大的集成阻力。相同智能体实例之间的文本冲突率为 19.8%，表明当前部署的智能体甚至不具备最基本的横向感知能力（horizontal awareness）。智能体彼此独立、相互隔离地运行，并不知道其他同类型智能体也在同时访问和修改相同的文件。
Finally, the taxonomy shows that the majority of these conflicts occur at the source-code level, as opposed to the dependency-manifest and lockfile level. Further, approximately 42% of conflict signals are structural (modify/delete or add/add operations), indicating that agents are not only editing the same lines, but also disagreeing about whether a file should exist at all.
最后，该分类体系表明，这些冲突大多发生在源代码层面，而非依赖清单和锁文件层面。此外，约 42% 的冲突信号属于结构性冲突（修改/删除或添加/添加操作），表明智能体不仅在编辑相同的代码行，而且对于某个文件究竟是否应该存在也存在分歧。

This lack of coordination likely results in significant additional overhead downstream. In this paper we do not measure CI/CD logs, token usage, or maintainer time; therefore, the examples provided below are hypothesized outcomes of the conflict rates that we measured, as opposed to findings based on direct observation:
这种协调缺失很可能在后续环节造成显著的额外开销。本文未测量 CI/CD 日志、token 使用量或维护者投入的时间；因此，下文提供的示例是根据我们测得的冲突率推测出的结果，而非基于直接观察得出的发现：
Lost CI/CD compute: testing suites consume compute cycles validating multiple feature branches simultaneously that can never merge, due to conflicts inherent from the moment each was created in parallel.
CI/CD 计算资源浪费：测试套件消耗计算周期，同时验证多个永远无法合并的功能分支，因为这些分支从并行创建的那一刻起就存在固有冲突。
Token budget depletion: when a conflict arises, an agent pipeline will either stall or invoke another agent instance to resolve the conflict markers, resulting in increased overall token cost.
token 预算耗尽：发生冲突时，智能体流水线要么停滞，要么调用另一个智能体实例来处理冲突标记，从而增加总体 token 成本。
Maintainer fatigue: human maintainers are likely required to reconcile overlapping changes to the same source files—and files modified by one agent instance and deleted by another—thereby undermining the purpose of automating engineering.
维护者疲劳：人工维护者很可能需要协调对同一源文件的重叠修改，以及一个智能体实例修改而另一个实例删除的文件，从而削弱工程自动化的意义。
Quantifying these potential costs is a logical subsequent research topic.
量化这些潜在成本是顺理成章的后续研究课题。
7. Threats to Validity7. 效度威胁
Construct Validity. We treat temporal co-activity as a proxy for the occurrence of concurrent work, and to prevent arbitrary threshold decisions we provide the sensitivity of co-activity from 0 through 7 days. Textual conflict is calculated using true three-way merges with git merge-tree—exactly how git reports integration—but this captures only the surface layer; no tracking is done for deeper build or semantic conflicts. Our results therefore provide a conservative lower bound.
构念效度。我们将时间上的共同活跃作为并发工作发生的代理指标，并提供共同活跃情况在 0 至 7 天范围内的敏感性分析，以避免任意设定阈值。文本冲突通过 git merge-tree 执行真正的三方合并来计算，这与 git 报告集成结果的方式完全一致，但这只能捕捉表层冲突；我们未追踪更深层的构建冲突或语义冲突。因此，我们的结果提供了一个保守的下界。
Internal Validity. The total number of co-active pairs is extremely biased toward a very small subset of highly active repositories (the top ten account for 91.4% of all raw pairs). To address this bias, we normalize prevalence at both the repository and pull-request levels and enforce one co-active pair per distinct repository within the merge-replay sample. The cross-agent stratum is limited by the amount of data available: only 122 repositories exhibited any form of cross-agent co-activity; it therefore uses a much smaller sample ( $N=115$ ) than the intra-agent stratum ( $N=601$ ), while 716 of the 747 pairs (95.8%) were evaluable. Associations found in RQ4 are descriptive, uncontrolled, and should not be interpreted as causal.
内部效度。共同活跃配对总数极度偏向少数高度活跃的代码仓库（前十个仓库占全部原始配对的 91.4%）。为消除这种偏差，我们在代码仓库和拉取请求两个层面对出现率进行归一化，并在合并重放样本中限定每个不同的代码仓库仅包含一个共同活跃配对。跨智能体分层受到可用数据量的限制：仅有 122 个代码仓库呈现出某种形式的跨智能体共同活跃；因此，该分层使用的样本（$N=115$）远小于同智能体分层（$N=601$），而 747 个配对中有 716 个（95.8%）可供评估。RQ4 中发现的关联属于描述性结果，未控制其他因素，不应将其解释为因果关系。
External Validity. The findings reported here are constrained by the AIDev-pop dataset: open-source projects and five agent profiles, all over a fixed time frame (December 2024–July 2025). It is possible that the low rates of cross-agent concurrency also reflect the methods used to collect AIDev, since AIDev mined each agent independently, and because this study examines an initial period in which multi-vendor usage had only begun. These patterns may differ in proprietary enterprise code bases with stricter branching rules.
外部效度。本文报告的研究发现受 AIDev-pop 数据集的限制：该数据集涵盖开源项目和五种智能体类型，且均处于固定时间范围内（2024 年 12 月至 2025 年 7 月）。跨智能体并发率较低，也可能反映了 AIDev 所采用的数据收集方法，因为 AIDev 分别独立挖掘各个智能体的数据，而且本研究考察的是多供应商使用模式刚刚起步的初期阶段。在采用更严格分支规则的企业专有代码库中，这些模式可能有所不同。
8. Conclusion and Next Steps8. 结论与后续步骤
This research was the largest empirical study yet conducted into simultaneous concurrent AI-agent pull requests on GitHub. Concurrent execution is almost universally found in automated software development—it has been demonstrated by this data set that: 79.4% of agent pull requests execute in a state of temporal overlap with other pull requests and for the majority of cases this occurs within an intra-agent (agent-specific) environment and not in cross-vendor deployments. Through the very large-scale merge replay of 747 unique pairs we have shown that when the various pull request work flows run independently of one another they generate textual merge conflicts for 19.8% of homogeneous (pull requests executed by same-agent) scenarios and 41.7% of cross-agent deployments; there is no overlap between the two confidence intervals. A taxonomy of actual git conflict output indicates that these conflicts occur primarily in source code (84.4% of all files involved in a conflict are source code files vs. 3.9% dependency manifests and locks); further, we have determined that 42% of the conflicts were structural (modify/delete or add/add) whereas 58% were content-based merges.
本研究是迄今为止针对 GitHub 上 AI 智能体拉取请求同时并发开展的最大规模实证研究。并发执行在自动化软件开发中几乎普遍存在——该数据集表明：79.4% 的智能体拉取请求在执行期间与其他拉取请求存在时间重叠，而且在大多数情况下，这发生在同智能体（特定智能体）环境中，而非跨供应商部署中。通过对 747 个不同配对进行超大规模合并重放，我们表明，当各个拉取请求工作流彼此独立运行时，19.8% 的同质场景（由相同智能体执行拉取请求）和 41.7% 的跨智能体部署会产生文本合并冲突；两者的置信区间没有重叠。对实际 git 冲突输出的分类表明，这些冲突主要发生在源代码中（所有涉及冲突的文件中，84.4% 为源代码文件，而依赖清单和锁文件占 3.9%）；此外，我们确定 42% 的冲突属于结构性冲突（修改/删除或添加/添加），而 58% 属于基于内容的合并冲突。
This demonstrates conclusively that uncoordinated reactive development paradigms will continue to fail to provide adequate support for development. Research going forward should develop programmatic orchestration mechanisms, define formalized live workspace communication protocols for active agents, and expand merge-replay pipeline methodologies to include sandboxed runtime environments such that there will exist a systematized approach to measure build failure, semantic failure and the long-term operational cost (CI compute, token spend, etc.) that has only been hypothesized thus far.
这充分证明，缺乏协调的反应式开发范式将持续无法为开发工作提供充分支持。未来的研究应开发程序化编排机制，为活跃智能体定义形式化的实时工作空间通信协议，并扩展合并重放流水线方法，使其涵盖沙箱化运行时环境，从而形成一种系统化的方法，用于衡量构建失败、语义失败以及迄今仅停留在假设层面的长期运行成本（CI 计算资源消耗、词元开销等）。
