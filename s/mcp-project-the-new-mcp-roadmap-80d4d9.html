一句话

MCP 正从工具调用接口扩展为支持长任务、事件交互和智能体身份委托的协议，但路线图尚不能证明 swarm 扩大后会获得性能收益。

主要内容

  • 已发布的基础改造：据项目介绍，2026-07-28 规范移除了协议级会话和初始化握手，使服务端可无状态横向扩容；增加能力发现与列表缓存，并以多轮请求模式支持无状态交互。
  • 消息机制继续完善：计划通过 webhook、通道等服务端事件减少轮询，并审查任务、订阅和进度通知能否协同工作。Tasks 目前是官方扩展，路线图希望推动其进入规范。
  • 身份与委托成为重点：面向无人值守的云端智能体，以及用户向智能体、智能体向子智能体授予权限的场景，计划结合工作负载身份联合、令牌交换和持有证明机制，建立标准化信任路径。
  • 控制工具规模带来的负担：提出渐进式发现，让服务先暴露较小入口，再随需求展开工具目录；同时统一工具结果契约，改善 SDK 与文档。

证据与可信度

这是 MCP 项目发布的官方路线图，能直接说明维护者的方向与优先级；已交付能力及扩容效果仍属于项目自述，材料未提供独立核验或性能测试。文中的“一百个工具”是解释上下文负担的示例，并非实验样本；没有吞吐、延迟、成本或多智能体成功率数据。应区分已发布规范、现有扩展与未来计划。

对 swarm scaling 的意义

它触及 swarm 扩展的几类基础约束：服务端状态、长任务通信、子智能体授权，以及工具目录膨胀。无状态服务有利于扩容承载层，事件机制可能减少轮询，身份委托可为分层协作提供权限边界，渐进式发现则试图控制工具选择负担。但这些是协议层支撑，不能据此推断更多智能体会带来更高任务质量、更低成本或更好的协作效率。
